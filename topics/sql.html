Section 01

Core Query Anatomy

Every SQL query is evaluated in a logical order that differs from how it's written — understanding that order explains why you can't reference a SELECT alias in WHERE, but can in ORDER BY.

Logical processing order

FROM / JOIN — build the working row set
WHERE — filter individual rows
GROUP BY — collapse rows into groups
HAVING — filter groups
SELECT — compute output columns / aliases
ORDER BY — sort the result
LIMIT / OFFSET — page the result
Why you can't use a SELECT alias in WHERE WHERE runs before SELECT in logical order, so an alias defined in SELECT doesn't exist yet. ORDER BY runs last, so aliases (and even column positions like ORDER BY 2) are valid there.

Basic SELECT

SELECT DISTINCT department, salary
FROM employees
WHERE salary > 50000
  AND department IN ('Engineering', 'Sales')
ORDER BY salary DESC
LIMIT 10 OFFSET 20;      -- skip the first 20, return the next 10 (pagination)

Pattern matching & ranges

SELECT * FROM employees WHERE name LIKE 'A%';        -- starts with A
SELECT * FROM employees WHERE name LIKE '%son';       -- ends with "son"
SELECT * FROM employees WHERE name ILIKE '%SMITH%';   -- case-insensitive (Postgres)
SELECT * FROM employees WHERE hire_date BETWEEN '2024-01-01' AND '2024-12-31';
SELECT * FROM employees WHERE manager_id IS NULL;     -- never use = NULL

CASE expressions

SELECT
  name,
  salary,
  CASE
    WHEN salary >= 100000 THEN 'Senior'
    WHEN salary >= 60000  THEN 'Mid'
    ELSE 'Junior'
  END AS band
FROM employees;
Section 02

Joins

Joins combine rows from two or more tables based on a related column. The join type controls what happens to rows on either side that have no match.

Join types

Join Returns
INNER JOIN Only rows with a match on both sides
LEFT JOIN All left rows; unmatched right columns are NULL
RIGHT JOIN All right rows; unmatched left columns are NULL
FULL OUTER JOIN Union of left and right; unmatched side is NULL
CROSS JOIN Cartesian product — every left row paired with every right row
SELF JOIN A table joined to itself (via aliases) — e.g., employee ↔ manager 
-- INNER JOIN — only employees that have a matching department
SELECT e.name, d.dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.dept_id;

-- LEFT JOIN — every employee, department is NULL if unassigned
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;

-- Find rows with NO match — the "anti-join" pattern
SELECT e.name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id
WHERE d.dept_id IS NULL;                 -- employees with no department

-- SELF JOIN — employees and their managers, side by side
SELECT emp.name AS employee, mgr.name AS manager
FROM employees emp
LEFT JOIN employees mgr ON emp.manager_id = mgr.emp_id;
WHERE vs the ON clause with outer joins Putting a filter on the right-hand table in WHERE (e.g. WHERE d.active = true) silently turns a LEFT JOIN into an INNER JOIN, because NULL rows fail the WHERE filter. Conditions on the joined-in table that should still allow unmatched rows belong in the ON clause instead.
Section 03

Aggregation, GROUP BY & HAVING

Aggregate functions collapse many rows into one value per group. WHERE filters rows before grouping; HAVING filters groups after aggregation. 

SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM employees
WHERE hire_date >= '2020-01-01'    -- filters ROWS before grouping
GROUP BY department
HAVING COUNT(*) > 5                -- filters GROUPS after aggregation
ORDER BY avg_salary DESC;

Aggregate functions

COUNT(*)              -- all rows, including NULLs
COUNT(column)          -- non-NULL values only
COUNT(DISTINCT column) -- distinct non-NULL values
SUM(salary), AVG(salary), MIN(salary), MAX(salary)
STRING_AGG(name, ', ')       -- Postgres/SQL Server: concatenate group values
GROUP_CONCAT(name SEPARATOR ', ')  -- MySQL equivalent
Every non-aggregated SELECT column must be in GROUP BY Standard SQL requires that any column in SELECT that isn't wrapped in an aggregate function appear in GROUP BY — otherwise which row's value would it show for a group of many rows? MySQL's legacy ONLY_FULL_GROUP_BY-off mode is the one notable exception, and relying on it produces nondeterministic results.
Section 04

Subqueries & CTEs

Common Table Expressions (WITH) name a query so it can be referenced like a table — improving readability over deeply nested subqueries, and enabling recursion.

Scalar, row, and correlated subqueries

-- Scalar subquery — single value used inline
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- Correlated subquery — re-evaluated per outer row
SELECT e.name, e.salary, e.dept_id
FROM employees e
WHERE e.salary = (
  SELECT MAX(salary) FROM employees e2 WHERE e2.dept_id = e.dept_id
);                                          -- highest earner in each department

-- EXISTS — often faster than IN for correlated existence checks
SELECT d.dept_name
FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);

CTEs (WITH)

WITH dept_avg AS (
  SELECT dept_id, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY dept_id
)
SELECT e.name, e.salary, d.avg_salary
FROM employees e
JOIN dept_avg d ON e.dept_id = d.dept_id
WHERE e.salary > d.avg_salary;             -- earns more than their dept average

-- Multiple CTEs chained together
WITH high_earners AS (
  SELECT * FROM employees WHERE salary > 100000
),
by_dept AS (
  SELECT dept_id, COUNT(*) AS n FROM high_earners GROUP BY dept_id
)
SELECT * FROM by_dept ORDER BY n DESC;

Recursive CTE — org chart / hierarchy traversal

WITH RECURSIVE org_chart AS (
  -- anchor member: the top-level row(s)
  SELECT emp_id, name, manager_id, 1 AS level
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- recursive member: joins back to the CTE itself
  SELECT e.emp_id, e.name, e.manager_id, oc.level + 1
  FROM employees e
  JOIN org_chart oc ON e.manager_id = oc.emp_id
)
SELECT * FROM org_chart ORDER BY level, emp_id;
Recursive CTE structure Every recursive CTE has an anchor query (the base case), a UNION ALL, and a recursive query that references the CTE's own name — the engine repeats the recursive step until it returns zero new rows.
Section 05

Window Functions

Window functions compute a value across a set of related rows (the "window") without collapsing them the way GROUP BY does — each input row keeps its place in the output.

Ranking functions

SELECT
  name, department, salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num,
  RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rnk
FROM employees;
Function Behavior on ties
ROW_NUMBER() Always unique, sequential (1, 2, 3, 4...) — ties broken arbitrarily
RANK() Ties share a rank; the next rank skips (1, 2, 2, 4...)
DENSE_RANK() Ties share a rank; no gap in the sequence (1, 2, 2, 3...)

Offset functions — LAG / LEAD

SELECT
  order_date, revenue,
  LAG(revenue, 1)  OVER (ORDER BY order_date) AS prev_day_revenue,
  LEAD(revenue, 1) OVER (ORDER BY order_date) AS next_day_revenue,
  revenue - LAG(revenue, 1) OVER (ORDER BY order_date) AS day_over_day_change
FROM daily_sales;

Frame-based aggregates — running totals & moving averages

SELECT
  order_date, revenue,
  SUM(revenue) OVER (ORDER BY order_date
                      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
  AVG(revenue) OVER (ORDER BY order_date
                      ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS trailing_7day_avg,
  FIRST_VALUE(revenue) OVER (PARTITION BY DATE_TRUNC('month', order_date)
                              ORDER BY order_date) AS month_first_day_revenue
FROM daily_sales;
Window functions run after GROUP BY / HAVING, before ORDER BY You can use an aggregate and a window function in the same query — e.g. SUM(x) OVER (...) alongside a plain GROUP BY aggregate — because windowing is evaluated in the SELECT stage over the (possibly already grouped) result set.
Section 06

Set Operations & NULL Logic

Set operators combine the results of two queries with the same column shape. NULL introduces three-valued logic (TRUE / FALSE / UNKNOWN) that trips up filters and comparisons in predictable ways.

UNION / INTERSECT / EXCEPT

SELECT city FROM customers
UNION                          -- combine + de-duplicate
SELECT city FROM suppliers;

SELECT city FROM customers
UNION ALL                      -- combine, KEEP duplicates (faster — no dedup pass)
SELECT city FROM suppliers;

SELECT customer_id FROM orders_2024
INTERSECT                      -- rows present in BOTH queries
SELECT customer_id FROM orders_2023;

SELECT customer_id FROM orders_2024
EXCEPT                         -- rows in the first query, NOT in the second
SELECT customer_id FROM orders_2023;

NULL — three-valued logic

NULL = NULL          -- UNKNOWN, not TRUE — never matches with =
NULL <> NULL         -- also UNKNOWN
1 = NULL             -- UNKNOWN
NULL IS NULL         -- TRUE — the only correct way to test for NULL
COALESCE(a, b, 0)    -- first non-NULL value in the list
NULLIF(a, 0)         -- returns NULL if a = 0, else returns a (guards against /0)
a / NULLIF(b, 0)     -- safe division pattern
WHERE NOT IN silently returns zero rows if the subquery has a NULL WHERE id NOT IN (SELECT ref_id FROM t) returns an empty result set if any row in t.ref_id is NULL, because x <> NULL is UNKNOWN for every comparison, not FALSE. Prefer NOT EXISTS, which doesn't have this trap.
Section 07

Indexes & Query Performance

An index is a separate, ordered data structure (typically a B-tree) that lets the engine locate rows without scanning the whole table — at the cost of extra storage and slower writes.

Reading an execution plan

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;

-- Look for:
--  Seq Scan   → full table scan, no usable index (slow on large tables)
--  Index Scan → uses an index to jump straight to matching rows
--  Index Only Scan → satisfies the query from the index alone, no table lookup

Index types & when they help

Index Good for
Single-column B-tree Equality and range filters on one column (WHERE col = ?, BETWEEN)
Composite (a, b) Filters on a alone, or a AND b together — order matters, doesn't help a lone b filter
Unique index Enforces uniqueness and speeds up equality lookups (primary/foreign keys)
Covering index Includes every column the query needs — enables index-only scans
Partial index Indexes only rows matching a condition (e.g. WHERE active = true) — smaller, faster for skewed data
Indexes aren't free Every INSERT/UPDATE/DELETE must also update every index on the table. Index the columns your read queries actually filter/join/sort on — indexing everything slows down writes for no benefit.

Common performance killers

-- Function on an indexed column defeats the index (can't seek, must scan + compute)
WHERE YEAR(order_date) = 2026            -- bad: scans every row
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01'   -- good: sargable

-- Leading wildcard defeats a B-tree index
WHERE name LIKE '%smith'                 -- bad — can't use the index's sort order
WHERE name LIKE 'smith%'                 -- good — index can seek to the "smith" range
Section 08

Transactions & Isolation

A transaction groups statements into one atomic unit. Isolation levels trade off consistency guarantees against concurrency — stricter levels prevent more anomalies but block more.

ACID

Atomicity

All statements in the transaction succeed, or none do — ROLLBACK undoes everything.

Consistency

A transaction moves the database from one valid state to another, respecting constraints.

Isolation

Concurrent transactions don't see each other's uncommitted changes (to a degree set by the isolation level).

Durability

Once committed, changes survive a crash — written to durable storage.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                       -- both updates persist together, or...
-- ROLLBACK;                  -- ...neither does, if something failed

Isolation levels & the anomalies they prevent

Level Dirty read Non-repeatable read Phantom read
READ UNCOMMITTED Possible Possible Possible
READ COMMITTED Prevented Possible Possible
REPEATABLE READ Prevented Prevented Possible (MySQL InnoDB actually prevents this too)
SERIALIZABLE Prevented Prevented Prevented
Default isolation level varies by engine PostgreSQL and Oracle default to READ COMMITTED; MySQL's InnoDB defaults to REPEATABLE READ. Higher isolation reduces anomalies but increases lock contention and the chance of serialization failures that require a retry.
Section 09

Tricky Interview Questions I — Ranking & Duplicates

Assume a table employees(emp_id, name, salary, dept_id, manager_id) unless a question states otherwise.

Q1. Find the Nth highest salary

Three common approaches, in order of preference:

-- 1. DENSE_RANK — correctly handles duplicate salaries (ties share a rank)
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) t
WHERE rnk = 3;                       -- 3rd highest, ties count once

-- 2. OFFSET/FETCH — simple, but treats each ROW as distinct (duplicates count separately)
SELECT DISTINCT salary FROM employees
ORDER BY salary DESC
OFFSET 2 ROWS FETCH NEXT 1 ROWS ONLY;  -- N-1 offset for the Nth value

-- 3. Correlated subquery — portable to engines without window functions
SELECT MAX(salary) FROM employees e1
WHERE 2 = (
  SELECT COUNT(DISTINCT e2.salary) FROM employees e2 WHERE e2.salary > e1.salary
);                                     -- exactly 2 distinct salaries above → 3rd highest
The classic mistake: LIMIT/OFFSET without DISTINCT ORDER BY salary DESC LIMIT 1 OFFSET 2 gives the 3rd row, not the 3rd distinct value — if two people tie for 1st, this returns the 2nd-highest salary twice instead of skipping past the tie. Always clarify with the interviewer whether ties should count once or per-row.

Q2. Top N salaries per department

SELECT * FROM (
  SELECT
    name, dept_id, salary,
    DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk <= 3;                      -- top 3 earners in EACH department

Q3. Find duplicate rows (e.g., duplicate emails)

-- Which values are duplicated, and how many times
SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

-- Delete duplicates, keeping the lowest id per email
DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email
);

-- Same idea with a window function (works even without a unique id trick)
WITH ranked AS (
  SELECT id, email, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
  FROM users
)
DELETE FROM users WHERE id IN (SELECT id FROM ranked WHERE rn > 1);

Q4. Employees who earn more than their manager

SELECT emp.name AS employee, emp.salary, mgr.name AS manager, mgr.salary AS mgr_salary
FROM employees emp
JOIN employees mgr ON emp.manager_id = mgr.emp_id
WHERE emp.salary > mgr.salary;
Section 10

Tricky Interview Questions II — Sequences & Time

Q5. Rising temperature — compare each row to the previous day

Table weather(id, record_date, temperature). Find dates where the temperature was higher than the previous calendar day (dates may have gaps). 

SELECT w1.id
FROM weather w1
JOIN weather w2 ON w1.record_date = w2.record_date + INTERVAL '1 day'
WHERE w1.temperature > w2.temperature;

-- LAG() alternative — also correctly needs a gap check if dates aren't contiguous
SELECT id FROM (
  SELECT
    id, temperature, record_date,
    LAG(temperature) OVER (ORDER BY record_date) AS prev_temp,
    LAG(record_date) OVER (ORDER BY record_date) AS prev_date
  FROM weather
) t
WHERE temperature > prev_temp AND record_date = prev_date + INTERVAL '1 day';

Q6. Find three (or more) consecutive rows with the same value

Table logs(id, num) with sequential ids — find every num that appears at least 3 times in a row. 

SELECT DISTINCT l1.num
FROM logs l1
JOIN logs l2 ON l2.id = l1.id + 1 AND l2.num = l1.num
JOIN logs l3 ON l3.id = l1.id + 2 AND l3.num = l1.num;

Q7. Gaps and islands — group consecutive dates into ranges

Table sessions(user_id, activity_date) — one row per active day. Collapse consecutive days into (start_date, end_date) ranges per user. 

WITH numbered AS (
  SELECT
    user_id, activity_date,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY activity_date) AS rn
  FROM sessions
),
grouped AS (
  SELECT
    user_id, activity_date,
    activity_date - (rn * INTERVAL '1 day') AS island_key   -- constant within a run
  FROM numbered
)
SELECT user_id, MIN(activity_date) AS start_date, MAX(activity_date) AS end_date
FROM grouped
GROUP BY user_id, island_key
ORDER BY user_id, start_date;
The "gaps and islands" trick Subtracting a strictly increasing row number from a strictly increasing date produces a constant value for every row inside one consecutive run, and a different constant for each separate run — turning "find consecutive groups" into an ordinary GROUP BY.

Q8. Running total & percent of total

SELECT
  order_date, revenue,
  SUM(revenue) OVER (ORDER BY order_date) AS running_total,
  ROUND(100.0 * revenue / SUM(revenue) OVER (), 2) AS pct_of_grand_total
FROM daily_sales
ORDER BY order_date;
Section 11

Tricky Interview Questions III — Pivoting & Medians

Q9. Pivot rows into columns without a PIVOT operator

Table sales(region, quarter, amount) — produce one row per region with a column per quarter. 

SELECT
  region,
  SUM(CASE WHEN quarter = 'Q1' THEN amount ELSE 0 END) AS q1,
  SUM(CASE WHEN quarter = 'Q2' THEN amount ELSE 0 END) AS q2,
  SUM(CASE WHEN quarter = 'Q3' THEN amount ELSE 0 END) AS q3,
  SUM(CASE WHEN quarter = 'Q4' THEN amount ELSE 0 END) AS q4
FROM sales
GROUP BY region;

Q10. Median without a built-in MEDIAN function

-- Portable: average the middle one or two values after ranking
WITH ordered AS (
  SELECT
    salary,
    ROW_NUMBER() OVER (ORDER BY salary) AS rn,
    COUNT(*) OVER () AS n
  FROM employees
)
SELECT AVG(salary) AS median
FROM ordered
WHERE rn IN (FLOOR((n + 1) / 2.0), CEIL((n + 1) / 2.0));

-- Postgres shortcut
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median
FROM employees;

Q11. Second highest salary WITHOUT LIMIT/OFFSET or window functions

Useful when asked to solve it in "plain SQL-92":

SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- Returns NULL if there's no second distinct salary — often the expected edge case

Q12. Cumulative distinct count ("how many new customers each month")

Table orders(customer_id, order_date) — for each month, count customers who are ordering for the very first time. 

WITH first_order AS (
  SELECT customer_id, MIN(order_date) AS first_order_date
  FROM orders
  GROUP BY customer_id
)
SELECT
  DATE_TRUNC('month', first_order_date) AS month,
  COUNT(*) AS new_customers
FROM first_order
GROUP BY 1
ORDER BY 1;
Interview tip Interviewers are usually testing whether you reach for ROW_NUMBER/DENSE_RANK and PARTITION BY before falling back to self-joins or correlated subqueries — mention the window- function approach first, then the portable fallback, and call out how ties/duplicates/NULLs change the answer.
