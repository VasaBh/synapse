SECTION 01

Core Architecture Fundamentals

Senior architects are expected to reason about distributed systems trade-offs, not just implement features. CAP theorem, consistency models, and distributed patterns are the vocabulary of these discussions.

CAP Theorem

A distributed system can guarantee at most two of the three properties simultaneously:

Consistency (C)

Every read receives the most recent write or an error. All nodes see the same data at the same time.

Availability (A)

Every request receives a (non-error) response, but it may not be the most recent data.

Partition Tolerance (P)

The system continues operating even when network partitions cause message loss between nodes.

The real trade-off is C vs A during partitions Network partitions happen in any distributed system. So the real choice is: when a partition occurs, do you stop serving requests to maintain consistency (CP), or serve potentially stale data to maintain availability (AP)?
SystemCAP TypeBehaviour on Partition
PostgreSQL (single primary)CPReplication lag; followers may serve stale reads
CassandraAP (tunable)Serves stale data; eventual consistency
ZooKeeper / etcdCPLeader election; pauses if quorum lost
DynamoDB (eventual)APAvailable; might return stale data
CockroachDBCPDistributed SQL with Raft consensus

PACELC Extension

PACELC extends CAP by noting that even in the absence of a partition (Else), systems must trade off Latency vs Consistency. A system like DynamoDB (AP/EL) sacrifices consistency for low latency even under normal operation. This is why "what consistency level does your system need?" is the first question in any data architecture discussion.

Consistency Models

ModelGuaranteeLatencyExample
Strong (Linearisable)Every read sees the latest write globallyHigh (requires quorum)etcd, ZooKeeper
SequentialAll processes see operations in same order, not necessarily real-timeMediumRaft-based systems
CausalCausally related operations seen in order; concurrent writes may differLow-mediumMongoDB causal sessions
EventualAll replicas converge if no new writesLowDNS, Cassandra default

Domain-Driven Design (DDD) Concepts

Bounded Context

A linguistic boundary within which a domain model is defined and applicable. The natural unit for microservice boundaries.

Aggregate

A cluster of domain objects treated as a single unit for data changes. Aggregate root is the only entry point. Enforces invariants within the boundary.

Domain Event

Something meaningful that happened in the domain (OrderPlaced, PaymentFailed). The communication currency between bounded contexts.

SECTION 02

Microservices Deep Dive

Microservices solve organisational and deployment scalability problems, not just technical ones. The patterns in this section address the hard problems that emerge once you split the monolith.

When NOT to Use Microservices

Start with a modular monolith A small team building a new product should start with a well-structured monolith. Premature decomposition into microservices adds network latency, operational overhead, and distributed transactions before you understand your domain boundaries. Extract services when a module's deployment frequency, team ownership, or scalability needs diverge.

Service Communication Patterns

Synchronous (Request-Response)

REST (HTTP/1.1 JSON), gRPC (HTTP/2 protobuf), GraphQL. Caller waits for response. Simple but creates temporal coupling — if the callee is down, the caller fails.

Asynchronous (Event-Driven)

Kafka, RabbitMQ, AWS SQS. Producer fires and forgets. Decouples availability — consumer processes when ready. Adds complexity: ordering, idempotency, dead-letter handling.

Saga Pattern — Distributed Transactions

Distributed ACID transactions across services are impractical. The Saga pattern coordinates a sequence of local transactions, each publishing events that trigger the next step. On failure, compensating transactions undo completed steps.

  Choreography-based Saga (event-driven)
  ──────────────────────────────────────
  OrderService         PaymentService        InventoryService
      |                      |                      |
      |-- OrderCreated ----->|                      |
      |                   Charge card               |
      |                      |-- PaymentDone ------>|
      |                      |                   Reserve stock
      |                      |                      |-- StockReserved
      |                      |                      |
  [failure path]
      |                      |<-- PaymentFailed ---|
      |                   Refund card               |
      |<-- OrderCancelled ---|

CQRS — Command Query Responsibility Segregation

Separate the write model (commands that change state) from the read model (queries that return data). The read model is a denormalised projection optimised for query patterns, updated asynchronously from the write model via events.

// Command side: enforces invariants, persists to write store
POST /orders { items: [...] }  --> OrderAggregate.place() --> OrderPlaced event

// Query side: denormalised view, updated by event handler
GET /orders/{id}  -->  OrderReadModel (MongoDB doc with all fields pre-joined)

// Eventual consistency: read model may lag write model by milliseconds

Event Sourcing

Instead of storing current state, store the sequence of events that led to it. Current state is derived by replaying events. The event log is immutable and becomes the source of truth.

  • Audit log for free: complete history of every state change
  • Time travel: replay to any point in time
  • Projections: build any read model from the event log
  • Complexity: snapshots needed for long-lived aggregates; schema evolution is hard

API Gateway Pattern

Request Routing

Single entry point routes to correct service by path/header. Hides internal topology from clients.

Cross-Cutting Concerns

Auth/authz, rate limiting, SSL termination, request logging — centralised at gateway, not duplicated in every service.

BFF (Backend for Frontend)

Dedicated gateway per client type (mobile, web, partner). Each BFF aggregates and transforms data for its specific consumer's needs.

Circuit Breaker

Prevents cascading failures. After N consecutive failures to a backend, the circuit opens and returns fast-fail responses for a cooldown period.

Resilience Patterns

PatternProblem SolvedImplementation
Circuit BreakerCascading failure when downstream is slowResilience4j, Istio outlier detection

OpenShift Routing & Load Balancing

A senior architect must be able to describe the full traffic path from the internet to a pod, and choose the right layer for each concern: security, routing, load balancing, and observability.

The Full Traffic Stack

  Internet
      |
  GSLB (F5 GTM / Route 53) ---- DNS-level failover between sites
      |
  External LB (F5 BIG-IP / AWS ALB) ---- WAF, SSL offload, DDoS
      |
  OpenShift HAProxy Router ---- Route matching, weight-based LB
      |
  kube-proxy / IPVS ---- ClusterIP to Pod IP NAT
      |
  (Optional) Istio Envoy Sidecar ---- mTLS, circuit break, telemetry
      |
  Application Pod (FastAPI)

Route-Based Traffic Splitting

apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
  annotations:
    haproxy.router.openshift.io/balance: leastconn
    haproxy.router.openshift.io/timeout: 60s
spec:
  to:
    kind: Service
    name: payment-v1
    weight: 90        # 90% stable
  alternateBackends:
  - kind: Service
    name: payment-v2
    weight: 10        # 10% canary

IngressController Multi-Tenancy

apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: team-payments
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  routeSelector:
    matchLabels:
      team: payments          # only routes with this label
  namespaceSelector:
    matchLabels:
      env: production
  endpointPublishingStrategy:
    type: LoadBalancerService
Architect insight Running multiple IngressControllers lets you isolate high-traffic teams on dedicated routers, apply different HAProxy configs per team, and prevent a misconfigured route from one team affecting another team's ingress performance.

OpenShift Scaling Strategies

At the senior architect level, the question isn't just "how do I configure HPA?" but "how do I design a system that scales gracefully under load spikes while remaining cost-efficient at idle?"

Scaling Stack

  Application metric (queue depth, req/s) ---- KEDA ScaledObject
  CPU / Memory                             ---- HPA v2
  Concurrency                              ---- Knative KPA
                        |
                        v
               Pod replica count changes
                        |
                        v
  Pending pods can't schedule? ---- Cluster Autoscaler
  Node idle for 10+ min?        ---- Cluster Autoscaler removes it

Architecting for Scale-to-Zero

Scale-to-zero reduces infrastructure cost for bursty workloads but introduces cold-start latency. Design decisions:

  • Startup time matters: Python/JVM apps may take 5–30s. Optimise startup: lazy imports, connection pools initialised on first request not on boot
  • Pre-pulling images: ImagePullPolicy: IfNotPresent with images pre-seeded on nodes avoids registry pull during cold start
  • Knative activator buffering: First request held in activator buffer while pod starts. Buffer timeout must exceed cold start time
  • Warm pool: Set minScale: 1 for latency-sensitive services; accept the idle cost

Capacity Planning Formula

# Target replicas to handle peak load with headroom
maxReplicas = ceil(peakRequestsPerSec / requestsPerPodPerSec) * safetyFactor(1.3)

# Example: 1000 req/s peak, each pod handles 100 req/s, 1.3x safety
maxReplicas = ceil(1000/100) * 1.3 = 13 pods

# Minimum replicas: handle baseline load + absorb initial spike before HPA reacts
# HPA reaction time: 15s metrics lag + 15s stabilisation = 30s
# Baseline traffic at minReplicas must handle 30s of spike growth
minReplicas = ceil(baselineRPS / requestsPerPodPerSec) * 1.5

PodDisruptionBudget — Non-Negotiable

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
spec:
  selector:
    matchLabels:
      app: payment-api
  minAvailable: 2   # always keep 2 pods up during node drain / CA scale-down

SECTION 05

MCP Protocol

The Model Context Protocol (MCP) is an open standard (Anthropic, 2024) that defines how AI models connect to external data sources, tools, and services — analogous to USB-C for AI integrations.

What Problem MCP Solves

Before MCP, every AI application required custom integration code for each data source (database connector, API client, file reader). Each LLM provider had different function-calling formats. MCP standardises the interface so a tool written once works with any MCP-compatible model host.

  Without MCP                          With MCP
  ────────────                         ────────────────────────────
  App  --custom--> GitHub API          MCP Host (Claude Desktop / IDE)
  App  --custom--> PostgreSQL                     |
  App  --custom--> Jira                    MCP Protocol (JSON-RPC 2.0)
  App  --custom--> Slack             /         |         |        \
  (4 integrations, all different)   GitHub  Postgres   Jira    Slack
                                    MCP     MCP        MCP     MCP
                                    Server  Server     Server  Server

MCP Architecture

MCP Host

The application running the LLM (Claude Desktop, VS Code extension, custom app). Manages connections to MCP servers, mediates security boundaries.

MCP Client

Protocol client inside the host. Maintains 1:1 connections with MCP servers, handles capability negotiation and sampling requests.

MCP Server

Lightweight process exposing Resources (data), Tools (actions), and Prompts (templates) via the MCP protocol. Runs locally or remotely.

MCP Primitives

PrimitiveDirectionPurposeExample
ResourcesServer → ClientExpose data / contextFile contents, DB schema, API docs
ToolsClient → ServerExecute actionsRun SQL, call REST API, write file
PromptsServer → ClientReusable prompt templates"Explain this error" with context pre-filled
SamplingServer → ClientServer requests LLM completionServer uses model to process data server-side

Building an MCP Server (Python SDK)

from mcp.server import Server
from mcp.server.models import InitializationOptions
import mcp.types as types

app = Server("database-mcp")

@app.list_tools()
async def list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="execute_query",
            description="Execute a read-only SQL query against the analytics DB",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string", "description": "SQL SELECT statement"}
                },
                "required": ["query"]
            }
        )
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict) -> list[types.TextContent]:
    if name == "execute_query":
        results = await db.execute(arguments["query"])
        return [types.TextContent(type="text", text=str(results))]

MCP Transport Layers

stdio (Local)

Server launched as child process. Communication via stdin/stdout. Used by Claude Desktop for local MCP servers. Simplest, most secure.

HTTP + SSE (Remote)

Server runs as HTTP service. Client connects via Server-Sent Events for streaming. Enables remote MCP servers, multi-tenant deployments.

SECTION 06

Agentic AI Architecture

Agentic AI systems go beyond single-turn LLM calls — they execute multi-step reasoning loops, use tools, maintain state, and delegate to sub-agents. Designing these systems requires both ML and distributed systems thinking.

What Makes a System "Agentic"?

Tool Use

The model can call external functions (search, code execution, database queries) and incorporate results into subsequent reasoning steps.

Multi-Step Reasoning

The system loops: think → act → observe → think again. Commonly implemented as ReAct (Reasoning + Acting) or Chain-of-Thought.

Memory

State persists across steps: working memory (context window), episodic memory (conversation history), semantic memory (vector store), procedural (tool definitions).

Planning

Decompose a complex task into subtasks, delegate to specialised agents, reassemble results. Requires a planner/orchestrator agent.

LangGraph — State Machine Approach

LangGraph models agentic workflows as directed graphs where nodes are agent steps (LLM calls, tool calls) and edges define control flow including conditional branching and cycles.

from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]
    plan: str
    research: str
    draft: str

def planner(state: AgentState) -> AgentState:
    response = llm.invoke([SystemMessage(content="Create a research plan"), *state["messages"]])
    return {"plan": response.content}

def researcher(state: AgentState) -> AgentState:
    results = search_tool.invoke(state["plan"])
    return {"research": results}

def writer(state: AgentState) -> AgentState:
    draft = llm.invoke(f"Write based on: {state['research']}")
    return {"draft": draft.content}

# Build the graph
graph = StateGraph(AgentState)
graph.add_node("planner", planner)
graph.add_node("researcher", researcher)
graph.add_node("writer", writer)

graph.set_entry_point("planner")
graph.add_edge("planner", "researcher")
graph.add_edge("researcher", "writer")
graph.add_edge("writer", END)

app = graph.compile()

Safety & Guardrails

Agentic systems require explicit safety design
  • Minimal footprint: request only necessary permissions, prefer reversible actions
  • Human-in-the-loop: interrupt for confirmation before irreversible actions (file delete, send email)
  • Tool call validation: validate all tool parameters before execution; reject obviously harmful requests
  • Rate limiting: cap tool calls per step to prevent runaway loops
  • Audit logging: log every tool call, arguments, and result for post-hoc review
  • Prompt injection defence: treat all external data (web pages, file contents, API responses) as untrusted; never let them override system instructions

RAG Architecture

# Retrieval-Augmented Generation pipeline
async def answer_with_rag(question: str) -> str:
    # 1. Embed the question
    query_embedding = await embeddings.embed_query(question)

    # 2. Retrieve relevant chunks from vector store
    relevant_docs = await vectorstore.similarity_search(
        query_embedding, k=5, score_threshold=0.75
    )

    # 3. Construct context-augmented prompt
    context = "\n\n".join(doc.page_content for doc in relevant_docs)
    prompt = f"Context:\n{context}\n\nQuestion: {question}\n\nAnswer:"

    # 4. Generate answer
    response = await llm.ainvoke(prompt)
    return response.content
SECTION 07

Interview Q&A Cheat Sheet

Model answers for the architectural questions senior engineers face in principal/staff-level interviews. Show reasoning, not just answers.

Architecture Design Questions

QuestionKey Points
How do you decide microservice boundaries?DDD bounded contexts: deploy independently, team ownership, different scaling needs, avoid shared databases between services
How do you handle distributed transactions?Avoid 2PC. Use Saga (choreography for simple flows, orchestration for complex). Design for eventual consistency. Idempotent operations + compensating transactions.
How do you scale a read-heavy system?Read replicas, CQRS read projections, caching layers (Redis, CDN), eventual consistency acceptable. Profile before optimising.
How do you handle a database becoming a bottleneck?Connection pooling (PgBouncer), read replicas, caching hot data, vertical scale, then shard if needed. Event sourcing removes update contention. CQRS separates read/write load.
What is your approach to API versioning?URL path versioning (/v1/) for REST. Header versioning for internal services. Never break clients — add fields, deprecate don't remove. API Gateway routes by version.
How do you prevent cascading failures?Circuit breaker (stop calling failing service), timeout (don't wait forever), bulkhead (isolate failure), retry with backoff + jitter, fallback (cached/default response).

OpenShift / Platform Questions

QuestionKey Points
Describe your autoscaling strategyKEDA for event-driven (Kafka lag), HPA for HTTP (custom metrics), VPA for right-sizing, Cluster Autoscaler for nodes. PDB prevents zero-replica situations.
How do you do zero-downtime deployments?Rolling update with maxUnavailable: 0, readiness probes, PDB, terminationGracePeriodSeconds aligned with LB drain window. Blue-green for high-risk releases. Canary for gradual rollout.
How would you design multi-tenant OpenShift?Namespace per team + RBAC, NetworkPolicy for isolation, LimitRange + ResourceQuota per namespace, dedicated IngressController per team, separate node pools via taints for noisy-neighbour isolation.
Explain a production incident you'd diagnose with high latency1) Check HPA — is it at maxReplicas? 2) Check pod CPU/memory. 3) Check HAProxy stats (queue depth). 4) Distributed traces for per-service latency. 5) Check downstream dependencies. 6) Check node resource pressure.

AI / MCP Questions

QuestionKey Points
What is MCP and why does it matter?Open standard for AI-to-tool integration. Solves N*M integration problem (N models, M tools). Defines Resources, Tools, Prompts. JSON-RPC 2.0 over stdio or HTTP/SSE.
How do you prevent an agent from going rogue?Minimal permissions, reversible-first actions, human-in-the-loop on irreversible steps, tool call rate limits, prompt injection defence, full audit log, kill switch.
RAG vs fine-tuning?RAG: knowledge changes frequently, need up-to-date data, audit trail needed, faster to deploy. Fine-tuning: baking in style/behaviour, small model, offline knowledge only. Most production use RAG + minimal fine-tuning.
How do you handle LLM non-determinism in production?Structured outputs (JSON schema enforcement), output validation with Pydantic, retry on parse failure, temperature=0 for deterministic tasks, versioned prompts, shadow testing before rollout.

The "10x" Architect Mindset

Simplicity first

The best architecture is the simplest one that meets requirements. Complexity is technical debt that compounds. Start simple, evolve under real load.

Make it observable

If you can't measure it, you can't improve it. Traces, metrics, structured logs from day one. Alert on SLOs, not arbitrary thresholds.

Embrace failure

Design for partial failure. Every service will fail. Degrade gracefully — return cached data, skip non-critical calls, serve a useful partial response.

Automate toil

If humans do it more than twice, automate it. GitOps, auto-scaling, automated rollback, chaos engineering — the system should heal itself.
