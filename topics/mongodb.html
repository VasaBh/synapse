Section 01

Document Model & BSON

MongoDB stores data as flexible, JSON-like documents encoded in BSON (Binary JSON) — a binary-encoded superset of JSON that adds types like dates, binary data, and 64-bit integers, and supports fast traversal and encoding.

┌─────────────────────────────────────────────────────────────┐ │ MongoDB → RDBMS equivalent │ │ Database → Database │ │ Collection → Table │ │ Document → Row │ │ Field → Column │ │ Embedded document → Join (denormalised inline) │ │ _id (ObjectId) → Primary key │ └─────────────────────────────────────────────────────────────┘

A Document

{
  "_id": ObjectId("64f1a2b3c4d5e6f7a8b9c0d1"),
  "name": "Priya Sharma",
  "email": "priya@example.com",
  "age": 29,
  "tags": ["engineer", "backend"],
  "address": {
    "city": "Bengaluru",
    "zip": "560001"
  },
  "createdAt": ISODate("2026-01-15T10:00:00Z")
}

BSON Type Comparison

TypeExampleNotes
ObjectIdObjectId("64f1...")12 bytes: 4-byte timestamp + 5-byte random + 3-byte counter. Sortable by creation time.
DateISODate("2026-...")Stored as int64 ms since Unix epoch, UTC.
Decimal128NumberDecimal("19.99")Exact decimal for currency — avoids float rounding errors.
BinaryBinData(0, "...")Raw bytes — files, hashes, encrypted fields.
Array[1, 2, 3]Ordered list, can hold mixed types, indexable per-element (multikey index).
Schema-flexible, not schemaless Documents in a collection don't need identical fields, but production systems almost always enforce structure via JSON Schema validation (db.createCollection with $jsonSchema) or an ODM like Mongoose. "Flexible schema" means evolving structure without migrations, not "no structure."
Section 02

CRUD Operations

MongoDB's query API is document-shaped: filters are documents describing conditions, and updates use operators like $set and $inc rather than full-document overwrites.

Create & Read

// Insert
db.users.insertOne({ name: "Priya", age: 29, city: "Bengaluru" })
db.users.insertMany([{ name: "Arjun", age: 34 }, { name: "Mei", age: 27 }])

// Find
db.users.find({ age: { $gte: 25, $lt: 35 } })
db.users.find({ city: "Bengaluru" }).sort({ age: -1 }).limit(10).skip(20)
db.users.findOne({ email: "priya@example.com" })

// Projection — only return name and age
db.users.find({ age: { $gt: 25 } }, { name: 1, age: 1, _id: 0 })

Update & Delete

// Update operators
db.users.updateOne(
  { _id: ObjectId("64f1...") },
  { $set: { city: "Mumbai" }, $inc: { loginCount: 1 } }
)
db.users.updateMany({ status: "inactive" }, { $set: { archived: true } })

// Array updates
db.users.updateOne({ _id: id }, { $push: { tags: "senior" } })
db.users.updateOne({ _id: id }, { $addToSet: { tags: "backend" } }) // no duplicates
db.users.updateOne({ _id: id }, { $pull: { tags: "junior" } })

// Upsert — insert if no match
db.users.updateOne({ email: "new@x.com" }, { $set: { visits: 1 } }, { upsert: true })

// Delete
db.users.deleteOne({ _id: id })
db.users.deleteMany({ status: "archived" })

Common Query Operators

OperatorMeaningExample
$eq / $neequals / not equals{ status: { $ne: "closed" } }
$gt / $gte / $lt / $lterange comparisons{ age: { $gte: 18 } }
$in / $ninvalue in / not in list{ role: { $in: ["admin", "editor"] } }
$and / $or / $norlogical combinators{ $or: [{ a: 1 }, { b: 2 }] }
$existsfield presence{ deletedAt: { $exists: false } }
$elemMatcharray element matches multiple conditions{ scores: { $elemMatch: { $gt: 80, $lt: 90 } } }
$regexpattern match (uses index only if anchored){ name: { $regex: "^Pri" } }
updateOne vs save vs replaceOne updateOne with operators patches specific fields — the standard choice. replaceOne overwrites the whole document (loses unlisted fields). Never load-modify-save a full document in high-concurrency code — use atomic operators to avoid lost updates.
Section 03

Indexing

MongoDB indexes are B-trees (like most RDBMSs). Without a supporting index, a query performs a COLLSCAN — a full collection scan. Index design is the single highest-leverage performance lever in MongoDB.

Index Types

TypeUse CaseExample
Single fieldEquality/range on one fielddb.users.createIndex({ email: 1 })
CompoundQueries filtering/sorting on multiple fields{ city: 1, age: -1 }
MultikeyAuto-created when indexing an array fielddb.posts.createIndex({ tags: 1 })
TextFull-text search with stemmingdb.posts.createIndex({ body: "text" })
Geospatial (2dsphere)Location queries, $near, $geoWithindb.places.createIndex({ loc: "2dsphere" })
WildcardUnknown/dynamic field namesdb.logs.createIndex({ "metadata.$**": 1 })
TTLAuto-expire documents (sessions, logs)createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
UniqueEnforce uniqueness constraintcreateIndex({ email: 1 }, { unique: true })

The ESR Rule for Compound Indexes

Compound index field order: Equality → Sort → Range Query: find({ status: "active", age: { $gt: 25 } }).sort({ createdAt: -1 }) Index: { status: 1, createdAt: -1, age: 1 } ↑Equality ↑Sort ↑Range Equality fields first (narrows most), then sort fields (avoids in-memory sort), then range fields last (range scans can't use fields after them).

Explain & Query Diagnostics

db.users.find({ city: "Bengaluru", age: { $gt: 25 } })
  .explain("executionStats")

// Key fields to check:
// stage: "IXSCAN"  → good, used an index
// stage: "COLLSCAN" → bad, full scan — add an index
// totalDocsExamined vs nReturned → close to 1:1 is ideal
// executionTimeMillis → wall-clock cost
Anti-patternProblemFix
Index every fieldSlows writes (each index updates on write), wastes RAMIndex only fields used in filters/sorts on hot queries
Leading low-selectivity field{ isActive: 1, email: 1 } — boolean first is nearly uselessPut high-cardinality/equality fields first (ESR)
Unbounded regex{ $regex: "sharma" } can't use an indexAnchor with ^ or use a text index
Ignoring covered queriesFetches full document when only indexed fields are neededProject only indexed fields → index-only scan, no doc fetch
Covered queries If every field in the query filter and projection is in the index (including _id: 0 to exclude it), MongoDB never touches the actual documents — it answers entirely from the index. This is the fastest possible read path.
Section 04

Aggregation Framework

The aggregation pipeline processes documents through a sequence of stages — each stage transforms the stream and passes it to the next, similar to Unix pipes or SQL's GROUP BY/JOIN combined.

Collection │ ├─► $match (filter — push early, uses indexes) ├─► $group (aggregate — sum, avg, count per key) ├─► $sort (order results) ├─► $project (reshape output fields) └─► $limit (cap result size) │ ▼ Result cursor

Worked Example — Orders by Customer

db.orders.aggregate([
  { $match: { status: "completed", orderDate: { $gte: ISODate("2026-01-01") } } },
  { $group: {
      _id: "$customerId",
      totalSpent: { $sum: "$amount" },
      orderCount: { $sum: 1 },
      avgOrder:   { $avg: "$amount" }
  }},
  { $match: { totalSpent: { $gt: 1000 } } },     // filter on aggregated result
  { $sort: { totalSpent: -1 } },
  { $limit: 10 },
  { $lookup: {                                     // join to another collection
      from: "customers",
      localField: "_id",
      foreignField: "_id",
      as: "customer"
  }},
  { $unwind: "$customer" },
  { $project: { _id: 0, name: "$customer.name", totalSpent: 1, orderCount: 1 } }
])

Key Stages

StagePurpose
$matchFilters documents — SQL WHERE. Place as early as possible to use indexes.
$groupGroups by _id expression, computes accumulators ($sum, $avg, $max, $push).
$lookupLeft outer join to another collection — MongoDB's equivalent of SQL JOIN.
$unwindFlattens an array field into one document per element.
$projectReshapes documents — include/exclude/compute fields.
$facetRuns multiple sub-pipelines in parallel (e.g., results + total count in one round trip).
$bucketGroups documents into ranges (histograms).
$merge / $outWrites pipeline output to a collection (materialised views).
Pipeline optimisation The query planner auto-reorders some stages, but you should still hand-place $match and $sort as early as possible and $project/$unwind late — every stage processes the full document stream unless it reduces it first.
Section 05

Schema Design Patterns

MongoDB schema design is driven by query patterns, not normalisation rules. The central decision is embed vs. reference — get it wrong and you either bloat documents past the 16MB limit or pay N+1 query costs.

Embed vs Reference

Embed (nest inside document)Reference (separate collection + $lookup)
Best for1:few, data always read together, bounded growth1:many/many:many, independently queried, unbounded growth
ReadsSingle document fetch — fastestRequires $lookup or a second round trip
WritesAtomic within one documentMulti-document — needs a transaction for atomicity
Risk16MB document limit, unbounded array growthExtra query cost, data can go stale if denormalised
ExampleBlog post + comments (few, always shown together)Customer + orders (unbounded, queried independently)

Common Patterns

Subset Pattern

Embed only the most recent/relevant N sub-documents (e.g., last 10 reviews) inline; keep the full set in a separate collection.

Bucket Pattern

Group time-series readings into fixed-size buckets (e.g., one document per sensor per hour) instead of one document per reading — fewer, larger documents reduce index overhead.

Extended Reference

Duplicate a few frequently-read fields (e.g., customer name) into the referencing document to avoid a $lookup on hot paths — accept eventual staleness.

Polymorphic Pattern

Store different "shapes" of related entities (e.g., payment types) in one collection with a type discriminator field.

Computed Pattern

Pre-compute and store expensive aggregates (e.g., totalViews) instead of recalculating on every read; update via app logic or triggers.

Outlier Pattern

Handle rare documents that would break the subset/bucket pattern (a celebrity with 10M followers) with a flag and fallback query path.

The 16MB document limit A single BSON document cannot exceed 16MB. Unbounded embedding (e.g., pushing every order into a customer.orders array forever) will eventually hit this wall. Use the Subset or Bucket pattern, or move to references, before that happens.
Section 06

Replication

A MongoDB replica set is a group of mongod processes maintaining the same data set, providing high availability and read scaling through automatic failover.

┌─────────────┐ │ PRIMARY │ ← accepts all writes │ (mongod #1) │ ← writes recorded to oplog └──────┬───────┘ replicate │ (oplog tailing) ┌──────────┼──────────┐ ▼ ▼ ┌─────────────┐ ┌─────────────┐ │ SECONDARY │ │ SECONDARY │ ← replicate async by default │ (mongod #2) │ │ (mongod #3) │ ← can serve reads (readPref) └─────────────┘ └─────────────┘ If PRIMARY fails → remaining members hold an election → majority vote elects new PRIMARY (typically <12s failover)

Write & Read Concerns

Write ConcernMeaningTrade-off
{ w: 1 }Acknowledged by primary onlyFastest, can lose data on primary crash before replication
{ w: "majority" }Acknowledged by majority of voting membersDefault in modern drivers — durable across failover
{ w: 0 }Fire-and-forget, no acknowledgmentFastest, no durability guarantee at all
readConcern: "majority"Reads only see majority-committed dataPairs with w: majority for read-your-writes consistency

Read Preferences

  • primary (default) — always read from primary, strongest consistency
  • primaryPreferred — primary if available, else a secondary
  • secondary — always read from a secondary, scales read throughput, may be stale
  • nearest — lowest network latency member, regardless of role
Replication lag is real Secondaries apply the primary's oplog asynchronously by default. Reading from secondaries under secondary preference can return stale data — never use it for read-your-own-write flows (e.g., "show the order I just placed") unless you also use readConcern: majority with causal consistency sessions.
Section 07

Sharding

Sharding horizontally partitions data across multiple replica sets (shards) so the dataset and write throughput can scale beyond a single machine's capacity.

┌───────────┐ App ─────────► │ mongos │ (query router — stateless, scale-out) └─────┬─────┘ │ consults ┌─────▼─────┐ │ Config │ (stores chunk → shard mapping) │ Server RS │ └───────────┘ ┌──────────────────┼──────────────────┐ ▼ ▼ ▼ ┌───────────┐ ┌───────────┐ ┌───────────┐ │ Shard 1 │ │ Shard 2 │ │ Shard 3 │ ← each is its own │ (replica │ │ (replica │ │ (replica │ replica set │ set) │ │ set) │ │ set) │ └───────────┘ └───────────┘ └───────────┘

Shard Key Selection

Shard Key PropertyWhy It Matters
High cardinalityToo few distinct values → chunks can't split finely → hot shards
Low frequency (even distribution)Avoid keys where one value dominates the dataset (e.g., country: "US" for a US-only app)
Non-monotonic (or hashed)Monotonically increasing keys (timestamps, auto-increment) concentrate all writes on one shard — the "hot shard" problem
Matches query patternQueries without the shard key must broadcast (scatter-gather) to every shard — slow

Hashed vs Ranged Sharding

// Ranged — good for range queries, risk of hot shard on monotonic keys
sh.shardCollection("app.orders", { customerId: 1 })

// Hashed — even write distribution, but loses range-query locality
sh.shardCollection("app.events", { deviceId: "hashed" })

// Compound — combine a low-cardinality field with a high-cardinality one
sh.shardCollection("app.orders", { region: 1, orderId: 1 })
The classic hot-shard mistake Sharding a time-series collection on { timestamp: 1 } sends every new write to whichever shard owns the latest chunk — the other shards sit idle. Use a hashed shard key, or compound with a high-cardinality prefix like deviceId, so writes spread evenly.
Section 08

Transactions & Consistency

Single-document writes in MongoDB are always ACID-atomic. Multi-document ACID transactions (since v4.0 for replica sets, v4.2 for sharded clusters) exist for the cases where an operation must span more than one document or collection.

Multi-document Transaction

const session = client.startSession();
try {
  session.startTransaction({
    readConcern: { level: "snapshot" },
    writeConcern: { w: "majority" }
  });

  await accounts.updateOne(
    { _id: "A" }, { $inc: { balance: -100 } }, { session }
  );
  await accounts.updateOne(
    { _id: "B" }, { $inc: { balance: 100 } }, { session }
  );

  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction();
  throw err;
} finally {
  session.endSession();
}
Prefer schema design over transactions Because a single document's write is already atomic, the idiomatic MongoDB fix for "I need atomicity across two things" is usually to embed those two things in one document (Section 05), not to reach for a multi-document transaction. Transactions have real overhead (locking, snapshot retention) — use them for genuinely cross-entity invariants like the ledger transfer above.

Change Streams

// Real-time, resumable feed of data changes — powers CDC / event-driven apps
const changeStream = db.collection("orders").watch([
  { $match: { operationType: { $in: ["insert", "update"] } } }
]);

changeStream.on("change", (event) => {
  console.log(event.operationType, event.fullDocument);
});
ConceptGuarantee
Single-document writeAlways atomic, even across nested fields/arrays
Multi-document transactionACID — snapshot isolation, all-or-nothing commit
Change streamsAt-least-once delivery, resumable via resumeToken, ordered per shard
Causal consistencySession-scoped — guarantees read-your-own-writes across a session
Section 09

Interview Questions

Frequently asked MongoDB interview questions, with the reasoning an interviewer is actually listening for.

"When would you choose MongoDB over a relational database?"

When the data is naturally document-shaped (nested, variable structure), when you need horizontal write scaling via sharding, when schema evolves rapidly (early-stage products), or when read patterns consistently need the same nested data together (avoiding joins). Avoid it when you need complex multi-table joins/reporting, strict cross-entity ACID everywhere, or heavy ad-hoc analytical querying — an RDBMS or warehouse fits better there.

"How does MongoDB achieve high availability?"

Replica sets: one primary accepts writes, secondaries replicate via the oplog, and if the primary becomes unreachable the set holds a majority-vote election to promote a new primary — typically under 12 seconds. Combine with w: "majority" write concern so acknowledged writes survive failover.

"What's the difference between $lookup and embedding — when do you pick which?"

Embedding is denormalisation for read speed and atomicity within one document, ideal for bounded 1:few relationships read together. $lookup is a runtime join for unbounded or independently-queried relationships. The decision hinges on access pattern, not "correctness" — MongoDB has no normal-form obligation.

"Explain the ESR rule."

Order compound index fields as Equality → Sort → Range: equality fields narrow the index range first, sort fields let Mongo return results already ordered (avoiding an in-memory sort), and range fields go last because a range scan can't use any indexed field that comes after it.

"How would you design a shard key for a multi-tenant SaaS app?"

Prefer a compound key like { tenantId: 1, _id: 1 } — tenantId gives natural query isolation (queries always filter by tenant, avoiding scatter-gather) and, combined with a high-cardinality suffix, avoids both hot shards and unbounded jumbo chunks from a single huge tenant.

Follow-up trap: "Is MongoDB schemaless?" The honest answer is no — it's schema-flexible. Production systems enforce structure through $jsonSchema validators, an ODM (Mongoose), or application-layer contracts. "Schemaless" as a selling point is a common misconception interviewers like to probe.
