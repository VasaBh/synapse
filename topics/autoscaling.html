SECTION 01

Scaling Fundamentals

Autoscaling adjusts compute resources dynamically in response to load. Understanding when to scale horizontally vs vertically, and at what layer (pod vs node), is the foundation for designing cost-efficient, resilient systems.

Horizontal vs Vertical Scaling

Horizontal Scaling (Scale Out)

Add more pod replicas to distribute load. Stateless services scale this way naturally. HPA and KEDA implement this. No downtime — new pods start alongside existing ones.

Vertical Scaling (Scale Up)

Give each pod more CPU / memory. Necessary for memory-bound or single-threaded workloads. VPA implements this — requires pod restart which causes brief disruption.

Autoscaling Layers in OpenShift

  ┌─────────────────────────────────────────────────┐
  │              APPLICATION LAYER                   │
  │  HPA — scales pod replicas on CPU/memory        │
  │  VPA — right-sizes pod requests/limits          │
  │  KEDA — scales on any external metric           │
  │  Knative — scale-to-zero serverless             │
  └──────────────────────┬──────────────────────────┘
                         │ Pods need more nodes
                         ▼
  ┌─────────────────────────────────────────────────┐
  │              INFRASTRUCTURE LAYER                │
  │  Cluster Autoscaler — adds/removes nodes        │
  │  Machine Autoscaler — scales MachineSets        │
  └─────────────────────────────────────────────────┘

Stabilisation and Cooldown

All autoscalers implement hysteresis to prevent thrashing — rapidly scaling up and down in response to transient spikes. Key parameters:

  • Scale-up stabilisation window: How long the autoscaler waits before acting on a scale-up trigger (default: 0s for HPA)
  • Scale-down stabilisation window: How long to wait before scaling down — prevents premature removal of recently scaled pods (default: 300s for HPA)
  • Scale rate limits: Maximum pods added/removed per period to prevent runaway scaling
Interview Insight The most common autoscaling failure is scaling down too aggressively. A 5-minute scale-down stabilisation window means a traffic spike must subside for 5 minutes before pods are removed. This is intentional — it costs more but prevents yo-yo oscillation.
SECTION 02

Horizontal Pod Autoscaler (HPA)

HPA automatically adjusts the number of pod replicas in a Deployment, ReplicaSet, or StatefulSet based on observed metrics. It is the primary autoscaling mechanism for stateless services in Kubernetes.

HPA Algorithm

HPA calculates the desired replica count using:

desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]

For example, with 4 replicas at 80% CPU against a 50% target: ceil[4 × (80/50)] = ceil[6.4] = 7 replicas.

HPA v2 — Multi-Metric Scaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60    # scale when avg CPU > 60%
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 512Mi       # scale when avg memory > 512Mi
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "100"       # custom metric via Prometheus Adapter
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 60        # allow doubling every 60s
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 2
        periodSeconds: 60        # remove at most 2 pods per 60s

Resource Requests — Critical Prerequisite

HPA Requires Resource Requests HPA calculates utilisation as actual / requested. If a pod has no CPU request, HPA cannot compute utilisation and will refuse to scale. Always set resources.requests.cpu and resources.requests.memory on every container.

Custom Metrics via Prometheus Adapter

The Prometheus Adapter bridges Prometheus metrics into the custom.metrics.k8s.io API, making them available to HPA:

# prometheus-adapter config rule
rules:
- seriesQuery: 'http_requests_total{namespace!="",pod!=""}'
  resources:
    overrides:
      namespace: {resource: "namespace"}
      pod: {resource: "pod"}
  name:
    matches: "^(.*)_total$"
    as: "${1}_per_second"
  metricsQuery: 'rate(<<.Series>>{<<.LabelMatchers>>}[2m])'

HPA with KEDA (Recommended)

KEDA creates HPA objects under the hood but adds a richer ScaledObject abstraction that supports scale-to-zero and 60+ event sources. Prefer KEDA over raw HPA v2 for anything beyond basic CPU/memory scaling.

SECTION 03

Vertical Pod Autoscaler (VPA)

VPA adjusts the CPU and memory requests/limits of running pods based on historical usage. It solves the "I don't know what to set for resource requests" problem and prevents OOMKill events on memory-hungry pods.

VPA Components

Recommender

Watches pod resource usage via metrics-server and computes Lower Bound, Target, Upper Bound, and Uncapped Target recommendations.

Updater

Evicts pods whose current requests are outside the recommended range (when updateMode: Auto). The pod is recreated with new requests by the Admission Controller.

Admission Controller

Mutating webhook that patches resource requests/limits at pod creation time with VPA's recommendation.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: payment-api-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api
  updatePolicy:
    updateMode: "Auto"   # Off | Initial | Recreation | Auto
  resourcePolicy:
    containerPolicies:
    - containerName: payment-api
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 4
        memory: 4Gi
      controlledResources: ["cpu", "memory"]

VPA Update Modes

ModeBehaviourUse When
OffRecommendations only — no changes appliedRead-only analysis, initial tuning
InitialApply at pod creation, never evict running podsPrefer stability, tolerate stale values
RecreationEvict pods when out of range, new pod gets new valuesBatch jobs, pods that can tolerate restarts
AutoSame as Recreation today (In-place update planned)Stateless services where brief restart is OK

VPA + HPA Conflict

Do NOT combine VPA and HPA on the same metric If both VPA and HPA target CPU, they fight: VPA increases requests (raising the denominator for HPA utilisation), causing HPA to scale down, causing CPU per pod to rise, causing VPA to increase requests again — an unstable loop. Safe combination: VPA manages memory + HPA scales on custom metrics (e.g., requests/s).

Reading VPA Recommendations

kubectl describe vpa payment-api-vpa

  Recommendation:
    Container Recommendations:
      Container Name:  payment-api
      Lower Bound:
        Cpu:     100m
        Memory:  262144k
      Target:             ← apply this as requests
        Cpu:     587m
        Memory:  524288k
      Uncapped Target:    ← without minAllowed/maxAllowed constraints
        Cpu:     587m
        Memory:  524288k
      Upper Bound:        ← set as limits
        Cpu:     1
        Memory:  1Gi
SECTION 04

Custom Metrics Autoscaler (KEDA)

KEDA (Kubernetes Event-Driven Autoscaling) extends HPA to support scale-to-zero and 60+ event sources including Kafka, RabbitMQ, Prometheus, Azure Service Bus, Redis, and more — without writing custom Prometheus adapter configs.

KEDA Architecture

  External Source            KEDA                    Kubernetes
  ─────────────          ──────────────            ──────────────
  Kafka topic     ──▶   ScaledObject     ──▶   HorizontalPodAutoscaler
  RabbitMQ queue  ──▶   (ScaledJob)      ──▶   Deployment replicas
  Prometheus      ──▶   Metrics Server   ──▶   0 replicas (scale-to-zero)
  AWS SQS                (GRPC bridge)

ScaledObject — Deployment Scaling

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: payment-processor-scaler
spec:
  scaleTargetRef:
    name: payment-processor
  minReplicaCount: 0          # scale-to-zero when idle
  maxReplicaCount: 50
  cooldownPeriod: 300
  pollingInterval: 15
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka.svc:9092
      consumerGroup: payment-group
      topic: payment-events
      lagThreshold: "100"     # 1 replica per 100 messages of lag
      offsetResetPolicy: latest
  - type: prometheus
    metadata:
      serverAddress: http://prometheus.monitoring:9090
      metricName: payment_queue_depth
      query: sum(payment_queue_depth)
      threshold: "50"

ScaledJob — Batch Job Scaling

For batch workloads, KEDA can trigger individual Job runs per event rather than scaling a long-running Deployment:

apiVersion: keda.sh/v1alpha1
kind: ScaledJob
metadata:
  name: report-generator
spec:
  jobTargetRef:
    template:
      spec:
        containers:
        - name: report-gen
          image: report-generator:latest
        restartPolicy: OnFailure
  minReplicaCount: 0
  maxReplicaCount: 10
  triggers:
  - type: rabbitmq
    metadata:
      queueName: report-requests
      queueLength: "1"          # 1 job per message

Popular KEDA Scalers

ScalerTrigger MetricCommon Use Case
KafkaConsumer group lagEvent-driven microservices
PrometheusAny PromQL queryCustom application metrics
RabbitMQQueue depthTask queues, async processing
AWS SQSNumber of messagesCloud-native batch jobs
Redis ListsList lengthBackground job workers
CronTime schedulePre-scale before known traffic spikes
CPU / MemorySame as HPADrop-in HPA replacement with scale-to-zero

Scale-to-Zero Behaviour

When minReplicaCount: 0, KEDA scales the Deployment to zero when there are no events. The first event arriving causes KEDA to scale from 0→1 immediately (cold start). This cold-start latency (typically 5–30 seconds for container pull + JVM/Python startup) must be acceptable for your use case. For latency-sensitive services, set minReplicaCount: 1.

SECTION 05

Cluster and Machine Autoscaler (Node Scaling)

Pod autoscalers (HPA/VPA/KEDA) scale workloads within the existing node pool. When pods cannot be scheduled due to insufficient node capacity, the Cluster Autoscaler provisions new nodes — and removes them when idle.

Cluster Autoscaler (CA)

CA monitors for pods in Pending state due to insufficient resources. It simulates adding nodes from each MachineSet and picks the one that would schedule the pending pods with the least waste.

  Pod cannot schedule (Pending) — "Insufficient CPU"
         │
         ▼
  Cluster Autoscaler checks MachineSet capacity
         │
         ▼
  New Machine provisioned (cloud API call)
         │  ~3–5 minutes (bare metal: longer)
         ▼
  Node joins cluster, pods scheduled
         │
  [Idle node for 10 min]
         │
         ▼
  CA drains node (evicts pods), removes Machine
    
apiVersion: autoscaling.openshift.io/v1
kind: ClusterAutoscaler
metadata:
  name: default
spec:
  resourceLimits:
    maxNodesTotal: 24
    cores:
      min: 8
      max: 96
    memory:
      min: 4
      max: 384
  scaleDown:
    enabled: true
    delayAfterAdd: 10m       # wait before considering scale-down
    delayAfterDelete: 5m
    unneededTime: 10m        # node must be idle for 10 min
    utilizationThreshold: "0.5"  # below 50% = idle

Machine Autoscaler

The Machine Autoscaler targets a specific MachineSet and defines its min/max bounds. CA uses these bounds when deciding which MachineSet to scale:

apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: worker-us-east-1a
  namespace: openshift-machine-api
spec:
  minReplicas: 2
  maxReplicas: 10
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: cluster-worker-us-east-1a

Node Selectors and Taints for Scale Groups

In heterogeneous clusters, use node taints to reserve GPU or high-memory nodes for specific workloads. CA will only scale a MachineSet when a pod exists that tolerates its taint and cannot schedule elsewhere:

# GPU MachineSet taint
spec:
  template:
    spec:
      taints:
      - key: nvidia.com/gpu
        effect: NoSchedule

# GPU pod toleration
tolerations:
- key: nvidia.com/gpu
  operator: Exists
  effect: NoSchedule

Scale-Down Safety

  • Pods with PodDisruptionBudget that would be violated are not evicted
  • Pods with local storage (emptyDir, hostPath) are not evicted by default
  • System pods in kube-system namespace block node removal unless annotated
  • Nodes with cluster-autoscaler.kubernetes.io/scale-down-disabled: "true" are never removed
SECTION 06

OpenShift Serverless (Knative) Autoscaling

OpenShift Serverless is built on Knative Serving and provides true scale-to-zero with request-based autoscaling. Unlike HPA which polls metrics, Knative's activator intercepts requests and buffers them during cold start.

Knative Serving Architecture

  Incoming Request
        │
        ▼
  Knative Ingress (Kourier / Istio)
        │
        ├── Pods running? ──Yes──▶ Route to pod directly
        │
        └── No (0 replicas)
              │
              ▼
        Activator (buffers request, ~100ms)
              │
              ▼
        Autoscaler scales 0 → 1
              │
              ▼
        Pod ready → Activator forwards buffered request

Knative Service

apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: inference-api
  namespace: ml-serving
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "0"          # scale to zero
        autoscaling.knative.dev/maxScale: "20"
        autoscaling.knative.dev/target: "10"           # 10 concurrent requests/pod
        autoscaling.knative.dev/targetUtilizationPercentage: "70"
        autoscaling.knative.dev/window: "60s"          # metrics averaging window
        autoscaling.knative.dev/panicWindowPercentage: "10.0"
        autoscaling.knative.dev/panicThresholdPercentage: "200.0"
    spec:
      containers:
      - image: inference-api:latest
        resources:
          requests:
            cpu: 500m
            memory: 1Gi

Knative Autoscaler Algorithms

KPA (Knative Pod Autoscaler)

Default. Scales on concurrent requests per pod. Has panic mode: when load spikes 200%+ of target within 10% of the window, it over-provisions immediately then normalises.

HPA (Kubernetes HPA)

Knative can delegate to standard HPA. Use when you need CPU/memory-based scaling or when KPA's concurrency model doesn't fit (e.g., CPU-intensive batch per request).

Traffic Splitting (Revision-Based)

spec:
  traffic:
  - revisionName: inference-api-v1
    percent: 80
    tag: stable
  - revisionName: inference-api-v2
    percent: 20
    tag: canary

Cold Start Mitigation

  • Set minScale: 1 for latency-sensitive endpoints — no cold start, but no cost saving from zero-scaling
  • Use minScale: 0 + initialise containers fast (avoid heavy imports at startup)
  • Pre-pull images via ImagePullPolicy: IfNotPresent on all worker nodes
  • Use readiness probes conservatively — activator will hold requests until ready
SECTION 07

FastAPI: Publishing Metrics for Autoscaling

FastAPI applications can expose Prometheus metrics that feed directly into HPA via the Prometheus Adapter or into KEDA's Prometheus scaler. This closes the loop: application-level signals drive infrastructure scaling.

Instrumenting with prometheus-fastapi-instrumentator

from fastapi import FastAPI
from prometheus_fastapi_instrumentator import Instrumentator
from prometheus_client import Gauge, Counter, Histogram

app = FastAPI()

# Auto-instruments: request count, latency histogram per route
Instrumentator().instrument(app).expose(app, endpoint="/metrics")

# Custom business metric
active_jobs = Gauge("active_processing_jobs", "Number of jobs currently being processed")
job_queue_depth = Gauge("job_queue_depth", "Messages waiting in queue")
processing_errors = Counter("processing_errors_total", "Total processing errors", ["error_type"])
processing_duration = Histogram(
    "processing_duration_seconds",
    "Time to process a job",
    buckets=[0.1, 0.5, 1.0, 2.5, 5.0, 10.0]
)

@app.post("/process")
async def process_job(job: JobRequest):
    active_jobs.inc()
    with processing_duration.time():
        try:
            result = await do_work(job)
            return result
        except Exception as e:
            processing_errors.labels(error_type=type(e).__name__).inc()
            raise
        finally:
            active_jobs.dec()

ServiceMonitor — Prometheus Scrape Config

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: payment-api-monitor
  labels:
    release: prometheus   # matches Prometheus operator selector
spec:
  selector:
    matchLabels:
      app: payment-api
  endpoints:
  - port: http
    path: /metrics
    interval: 15s
    scrapeTimeout: 10s

Prometheus Adapter Rule

rules:
- seriesQuery: 'job_queue_depth{namespace!="",pod!=""}'
  resources:
    overrides:
      namespace: {resource: "namespace"}
      pod: {resource: "pod"}
  name:
    as: "job_queue_depth"
  metricsQuery: 'avg(<<.Series>>{<<.LabelMatchers>>})'

HPA Using Custom Metric

metrics:
- type: Pods
  pods:
    metric:
      name: job_queue_depth
    target:
      type: AverageValue
      averageValue: "5"    # scale so each pod handles ≤5 queued jobs

KEDA ScaledObject Using Prometheus

triggers:
- type: prometheus
  metadata:
    serverAddress: http://prometheus-operated.monitoring:9090
    metricName: job_queue_depth
    query: sum(job_queue_depth{namespace="production"})
    threshold: "50"        # 1 replica per 50 queued jobs
Best Practice Expose metrics at /metrics on a dedicated port (not the API port) and secure the API port but leave /metrics accessible only within the cluster via NetworkPolicy. This prevents leaking internal state externally while allowing Prometheus to scrape.
SECTION 08

What is NOT Possible — Limitations

Understanding what autoscaling cannot do is as important as knowing what it can. These are the hard constraints and common misconceptions you must be able to articulate in an interview.

HPA Limitations

Cannot scale StatefulSets safely

HPA can target StatefulSets but scaling stateful pods without application-level support (e.g., cluster rebalancing for Kafka/Cassandra) causes data imbalance or unavailability.

Cannot scale to zero

HPA minimum is 1 replica. Use KEDA or Knative for scale-to-zero semantics.

Metric lag

HPA polls metrics every 15 seconds. A sudden 10× traffic spike may take 30–60s to trigger scaling, during which the existing pods may be overwhelmed.

No predictive scaling

HPA is purely reactive. For predictable load patterns (daily peaks), use KEDA's Cron scaler to pre-scale before the load arrives.

VPA Limitations

  • Pod restart required: VPA (Auto/Recreation mode) evicts pods to apply new resource values — causes brief disruption
  • No in-place update (yet): Kubernetes 1.27+ supports in-place pod resize but VPA's in-place mode is still alpha
  • History window: VPA needs several days of data for accurate recommendations — not useful for brand-new deployments
  • Cannot exceed node capacity: If maxAllowed is larger than any single node, pods will pend indefinitely

Cluster Autoscaler Limitations

Node provisioning latency Cloud VMs take 2–5 minutes to join the cluster. Bare-metal machines may take 10–20 minutes. HPA scales pods in seconds — if all existing nodes are full, pods will pend for minutes during node provisioning. Design with buffer capacity to absorb traffic spikes before CA catches up.
  • CA will NOT remove a node with any non-DaemonSet pod that cannot be rescheduled elsewhere
  • Pods with local-storage volumes block node scale-down
  • CA does not rebalance — a node may remain under-utilised if moving its pods would violate PodDisruptionBudgets

General Autoscaling Anti-Patterns

Anti-PatternProblemFix
No resource requests setHPA cannot compute utilisation; pods get BestEffort QoS (first evicted)Always set requests and limits
maxReplicas too lowService saturates during spikes even though autoscaler works correctlyCapacity plan — set max to handle peak × 2
HPA + VPA on CPUConflicting feedback loop (see Section 3)Use VPA for memory only; HPA on custom metrics
minReplicas: 0 for latency-sensitive APICold start on first request after idle periodKeep minReplicas ≥ 1
No PodDisruptionBudgetCA may evict all pods of a deployment simultaneously during scale-downSet PDB: minAvailable ≥ 1

Decision Guide — Which Autoscaler to Use?

Choose the right autoscaler based on workload type, scaling signal, and latency tolerance.

Decision Matrix

Workload TypeScaling SignalRecommendedNotes
Stateless HTTP APICPU utilisationHPA (CPU)Simple, widely understood
Stateless HTTP APIRequest rateHPA + Prometheus AdapterMore accurate than CPU
Event-driven consumerKafka/SQS lagKEDAScale-to-zero when no events
Batch / one-shot jobsQueue message countKEDA ScaledJobJob per message semantics
ML inference endpointConcurrent requestsKnative (KPA)Scale-to-zero + panic mode
Memory-bound serviceMemory utilisationVPA (recommendation mode)Right-size requests, monitor
Unknown resource needsHistorical usageVPA (Off mode)Read recommendations, set manually
Pre-known traffic peakTime scheduleKEDA Cron scalerPre-warm before traffic arrives

Combining Autoscalers Safely

Safe Combinations
  • HPA (requests/s) + VPA (memory only) + Cluster Autoscaler — the recommended production stack
  • KEDA + Cluster Autoscaler — KEDA scales pods, CA provides nodes as needed
  • Knative + Cluster Autoscaler — Knative handles pod lifecycle, CA handles node lifecycle

Interview Quick Answers

"How do you scale to zero?"

KEDA with minReplicaCount: 0, or Knative Serving. Standard HPA minimum is 1.

"HPA isn't scaling fast enough"

Reduce stabilisation window, switch trigger metric to leading indicator (queue depth) rather than lagging (CPU), or pre-scale with KEDA Cron.

"Pods are stuck Pending"

Cluster Autoscaler not configured, maxNodesTotal reached, or node provisioning in progress. Check CA logs: oc logs -n openshift-machine-api.

"VPA keeps restarting my pods"

Switch to updateMode: Initial or Off. Read recommendations and apply them manually to stabilise, then re-enable Auto.

End-to-End Autoscaling Architecture

A production autoscaling stack combines pod-level autoscalers feeding off application metrics with node-level autoscalers that ensure capacity is always available. This section shows how all the pieces connect.

PodDisruptionBudgets — The Safety Net

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
spec:
  selector:
    matchLabels:
      app: payment-api
  minAvailable: 2          # at least 2 pods always running
  # OR: maxUnavailable: 1  # at most 1 pod down at a time

PDBs are honoured by both CA (node drain) and VPA (pod eviction). Without a PDB, a scale-down event could simultaneously evict all replicas of a deployment that happens to be running on a single node.

Observability Checklist

  • Alert on HPA at maxReplicas — means autoscaler is saturated, needs a higher max or more efficient code
  • Alert on pods stuck Pending > 5 minutes — CA may have hit its node limit
  • Dashboard: replica count over time overlaid with request rate — validate autoscaling efficiency
  • Track VPA recommendations weekly — update requests/limits if Target drifts significantly
  • Monitor CA logs for "cannot remove node" messages — indicates PDB or local storage blocks
