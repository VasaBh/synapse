6. Load Balancing Between Production and COB/DR Environments

When an organisation operates a Production OpenShift cluster and a separate COB (Continuity of Business) or DR (Disaster Recovery) OpenShift cluster, traffic must be intelligently routed between these environments. This is where Global Server Load Balancing (GSLB) comes into play.

6.2 GSLB — Global Server Load Balancing

GSLB operates at the DNS layer. When a client resolves a hostname, the GSLB-enabled DNS server makes an intelligent decision about which site IP to return, based on health checks, geographic proximity, site load, or configured policies. If the primary (Production) site becomes unhealthy, GSLB automatically returns the COB/DR site IP, achieving failover.

How GSLB works step-by-step:

  • Client application makes a DNS query for api.mycompany.com.
  • DNS query reaches the GSLB authoritative name server.
  • GSLB checks health of both Production and COB sites via configured health monitors.
  • GSLB applies the configured algorithm (Active-Passive, Weighted, Geo-based).
  • GSLB returns the IP of the chosen healthy site to the client.
  • Client connects to that IP, reaching the External LB at the chosen site.

6.5 Example: F5 GTM Active-Passive for Prod-COB

In this setup, F5 GTM (now called BIG-IP DNS) manages the DNS resolution for api.mycompany.com. Production pool has higher priority; COB pool is backup.

# F5 GTM Configuration (Conceptual)
# Step 1: Define Data Centers
gtm datacenter DC-PROD { }
gtm datacenter DC-COB { }
# Step 2: Define Servers (the LTM/VIPs at each site)
gtm server PROD-LTM {
datacenter DC-PROD
virtual-servers {
prod-api-vip {
destination 172.16.1.100:443
}
}
}
gtm server COB-LTM {
datacenter DC-COB
virtual-servers {
cob-api-vip {
destination 172.16.2.100:443
}
}
}
# Step 3: Define Pools
gtm pool a prod-pool {
load-balancing-mode global-availability
members {
PROD-LTM:prod-api-vip { order 0 }
}
monitor https_readyz
}
gtm pool a cob-pool {
load-balancing-mode global-availability
members {
COB-LTM:cob-api-vip { order 0 }
}
monitor https_readyz
}
# Step 4: Define Wide IP (the DNS entry)
gtm wideip a api.mycompany.com {
pool-lb-mode global-availability
pools {
prod-pool { order 0 }      # Primary - always preferred
cob-pool  { order 1 }      # Backup - used only if prod fails
}
}
# Step 5: Health Monitor
gtm monitor https https_readyz {
interval 10
timeout 30
send "GET /healthz/ready HTTP/1.1\r\nHost: api.mycompany.com\r\n\r\n"
recv "200 OK"
}

6.6 Canary Testing Between Prod and COB

Before a full DR test or to continuously validate COB readiness, you can use GSLB weighted routing to send a small percentage of live production traffic to the COB environment:

Canary Between Prod and COB
GSLB DNS
/         \
95% /           \ 5%
/             \
+--------+    +--------+
|  PROD  |    |  COB   |
| Cluster|    | Cluster|
+--------+    +--------+
Phase 1: 95/5   (validate COB)
Phase 2: 80/20  (stress test COB)
Phase 3: 50/50  (full DR validation)
Phase 4: 0/100  (complete failover test)

This approach provides:

  • Continuous validation: COB is constantly tested with real production traffic, not just synthetic tests.
  • Confidence: Before a planned DR test, you already know COB is handling live requests correctly.
  • Gradual failover: During planned maintenance on Prod, you can gradually shift traffic to COB rather than a sudden cutover.

F5 GTM weighted configuration for canary between sites:

# Weighted round-robin between Prod and COB
gtm wideip a api.mycompany.com {
pool-lb-mode ratio
pools {
prod-pool { ratio 95 }
cob-pool  { ratio 5  }
}
}
# AWS Route 53 equivalent:
# Weighted routing policy records:
#   api.mycompany.com -> prod-alb.us-east-1.amazonaws.com  Weight: 95
#   api.mycompany.com -> cob-alb.eu-west-1.amazonaws.com   Weight: 5
