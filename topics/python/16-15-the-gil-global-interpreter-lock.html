15. The GIL (Global Interpreter Lock)

The GIL is a mutex in CPython that allows only one thread to execute Python bytecode at a time. Understanding it is critical for writing performant concurrent Python.

15.1 Why the GIL Exists

  • CPython’s memory management (reference counting) is not thread-safe
  • The GIL simplifies C extension development
  • It protects internal interpreter state from corruption
  • Removing it was historically too expensive (slower single-threaded performance)

15.2 Impact on Concurrency

Workloadthreadingmultiprocessingasyncio
CPU-bound (math, ML)No speedup (GIL blocks)Full parallelismNo speedup
I/O-bound (network, disk)Good (GIL released during I/O)Overkill, high overheadBest choice

15.3 Workarounds

# 1. multiprocessing — true parallelism
from multiprocessing import Pool
with Pool(8) as pool:
results = pool.map(cpu_intensive_fn, data_chunks)
# 2. concurrent.futures — unified interface
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor
with ProcessPoolExecutor(max_workers=8) as executor:
futures = [executor.submit(task, arg) for arg in args]
results = [f.result() for f in futures]
# 3. C extensions release GIL (NumPy, Pandas, scikit-learn)
# NumPy operations run in C and release the GIL automatically
# 4. Python 3.13+ free-threaded mode (experimental)
# python3.13t --disable-gil script.py

15.4 Python 3.13+ Free-Threaded Mode

PEP 703 introduced an experimental build of CPython without the GIL. This enables true multi-threaded parallelism for CPU-bound Python code. It requires recompiling Python and some C extensions may need updates.

# Check if GIL is disabled
import sys
print(sys._is_gil_enabled())  # False in free-threaded build
# Now threading gives real parallelism for CPU-bound work
import threading
threads = [threading.Thread(target=cpu_task, args=(chunk,))
for chunk in chunks]
for t in threads: t.start()
for t in threads: t.join()  # actually runs in parallel!
