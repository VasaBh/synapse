Section 01

Architecture

Snowflake's core innovation is a three-layer architecture that fully separates storage, compute, and services — each scales independently, which is what makes multiple teams able to query the same data concurrently without contending for resources.

┌─────────────────────────────────────────────────────────────────┐ │ CLOUD SERVICES LAYER │ │ Query optimizer · Metadata · Security/Auth · Result cache │ │ Infrastructure mgmt · Transaction mgmt (ACID) │ └──────────────────────────┬──────────────────────────────────────┘ │ ┌────────────────────────┼────────────────────────┐ ▼ ▼ ▼ ┌─────────┐ ┌─────────┐ ┌─────────┐ │Warehouse │ │Warehouse │ │Warehouse │ ← COMPUTE LAYER │ (ETL) │ │ (BI) │ │(Data Sci)│ independent, │ X-Small │ │ Large │ │ Medium │ elastic clusters └────┬────┘ └────┬────┘ └────┬────┘ └──────────────────────┼──────────────────────┘ ▼ ┌───────────────────────────┐ │ STORAGE LAYER │ ← single copy of data, │ Columnar, compressed, │ on cloud object store │ micro-partitioned │ (S3 / Azure Blob / GCS) └───────────────────────────┘

Why the Separation Matters

Traditional MPP (shared-nothing)Snowflake
Storage and compute bound to the same nodesStorage is independent of any warehouse
Scaling compute means reshuffling dataSpin up/down warehouses instantly — no data movement
One workload's load slows down others sharing the clusterEach team/workload gets its own warehouse — zero contention
Data duplicated per cluster for isolationSingle copy of data shared by every warehouse
Cloud Services layer does more than you'd think It holds all table metadata (not the query engine), handles authentication/RBAC, optimises and compiles queries, and serves the result cache — an identical repeated query can return in milliseconds with zero warehouse compute cost.
Section 02

Virtual Warehouses

A virtual warehouse is an independent MPP compute cluster used to execute queries. Warehouses can be resized, suspended, resumed, and scaled out into multi-cluster groups — all without touching the underlying data.

Warehouse Sizing

SizeServers (credits/hr)Typical Use
X-Small1 (1 credit/hr)Dev, small ETL, ad-hoc queries
Small → Medium2–4 credits/hrStandard BI dashboards, moderate ETL
Large → X-Large8–16 credits/hrHeavy transforms, large joins
2X-Large → 6X-Large32–512 credits/hrMassive batch loads, huge aggregations

Doubling warehouse size doubles compute (and cost) linearly and typically halves query time for parallelisable workloads — but does not help a query bottlenecked by something other than raw compute (e.g., a poor join order or excessive scanning).

Creating & Tuning a Warehouse

CREATE WAREHOUSE etl_wh
  WAREHOUSE_SIZE = 'MEDIUM'
  AUTO_SUSPEND = 60            -- seconds idle before suspend (billing stops)
  AUTO_RESUME = TRUE           -- wake automatically on next query
  INITIALLY_SUSPENDED = TRUE
  MIN_CLUSTER_COUNT = 1
  MAX_CLUSTER_COUNT = 4        -- multi-cluster: scale OUT for concurrency
  SCALING_POLICY = 'STANDARD'; -- vs 'ECONOMY' (favors cost over latency)

Scale Up vs Scale Out

Scale Up (bigger warehouse)

Use when a single query is slow — more servers per cluster means more parallelism for one statement. Fixes latency.

Scale Out (multi-cluster)

Use when many concurrent users queue behind each other on the same warehouse. Snowflake spins up additional identically-sized clusters automatically. Fixes queuing, not per-query speed.

Auto-suspend is the #1 cost lever Billing is per-second (min 60s) while a warehouse is running, regardless of load. A warehouse left AUTO_SUSPEND-disabled or set too high (e.g., 30 minutes) burns credits sitting idle. Most workloads should suspend after 60–300 seconds of inactivity.
Section 03

Micro-partitions & Clustering

Snowflake automatically divides every table into micro-partitions — immutable, columnar-compressed blocks of 50–500MB uncompressed data. Metadata about the min/max values in each column of each micro-partition drives pruning, Snowflake's core query-acceleration mechanism.

Table "orders" (100M rows) ├─ Micro-partition 1 [order_date: 2026-01-01 → 2026-01-03] ├─ Micro-partition 2 [order_date: 2026-01-03 → 2026-01-05] ├─ Micro-partition 3 [order_date: 2026-01-05 → 2026-01-07] ... └─ Micro-partition N [order_date: 2026-06-28 → 2026-06-30] Query: WHERE order_date = '2026-01-04' → optimizer reads partition metadata (min/max), only scans partition 2 → "PRUNING" — never touches the other N-1 partitions

Clustering Keys

-- Snowflake auto-clusters small/medium tables on natural load order.
-- For very large tables (100GB+) with poor natural ordering on the
-- filtered column, define an explicit clustering key:

ALTER TABLE events CLUSTER BY (event_date, tenant_id);

-- Check clustering health
SELECT SYSTEM$CLUSTERING_INFORMATION('events', '(event_date, tenant_id)');
-- returns avg_overlaps / avg_depth — lower is better
ConceptDetail
Partition pruningSkips micro-partitions whose min/max range can't satisfy the filter — the single biggest performance win available
Clustering depthHow many overlapping partitions must be scanned for a given value — automatic reclustering (background, billed) reduces it over time
Automatic clusteringSnowflake re-sorts partitions in the background as data changes — no manual OPTIMIZE needed, but consumes credits
When to add a clustering keyOnly on large (100GB+) tables where queries consistently filter/join on a column whose natural order has drifted (e.g., frequent updates)
Don't over-cluster Clustering keys add ongoing background re-clustering cost. Most tables need none — Snowflake's natural micro-partition pruning on load order is often sufficient. Add a clustering key only after confirming (via query profile) that pruning is poor on a genuinely large table.
Section 04

Semi-structured Data

Snowflake natively stores and queries JSON, Avro, Parquet, ORC, and XML via the VARIANT type — no separate NoSQL system needed. VARIANT columns are automatically columnarized and pruned like any other column.

Loading & Querying VARIANT

CREATE TABLE raw_events (payload VARIANT);

INSERT INTO raw_events
SELECT PARSE_JSON('{
  "user_id": 42,
  "event": "purchase",
  "items": [{"sku": "A1", "qty": 2}, {"sku": "B7", "qty": 1}],
  "meta": {"source": "mobile", "app_version": "3.2"}
}');

-- Dot notation + array indexing, fully queryable with SQL
SELECT
  payload:user_id::INT               AS user_id,
  payload:event::STRING              AS event,
  payload:meta.source::STRING        AS source,
  payload:items[0].sku::STRING       AS first_sku
FROM raw_events;

-- FLATTEN explodes nested arrays into rows (like $unwind in Mongo)
SELECT r.payload:user_id::INT AS user_id, i.value:sku::STRING AS sku, i.value:qty::INT AS qty
FROM raw_events r, LATERAL FLATTEN(input => r.payload:items) i;

Structured vs Semi-structured Storage

ApproachQuery SpeedFlexibilityUse When
VARIANT columnFast (auto-columnarized + pruned)High — schema can driftIngest-first, schema-on-read, evolving event payloads
Extracted relational columnsFastestLow — needs migration on schema changeStable, high-QPS analytical columns — extract via a view or stream
Hybrid (VARIANT + generated columns)Fast for hot fieldsHighBest of both — ALTER TABLE ADD COLUMN sku STRING AS (payload:items[0].sku::STRING)
No separate document DB required Because VARIANT is pruned and columnarized under the hood, teams often land raw JSON straight into Snowflake (schema-on-read) and materialise relational views on top — skipping a separate MongoDB/DynamoDB staging hop entirely for analytical workloads.
Section 05

Time Travel & Cloning

Because storage is immutable micro-partitions, Snowflake can cheaply retain historical versions of data (Time Travel) and create instant, storage-free copies (Zero-Copy Cloning) by just referencing existing partitions.

Time Travel — Query & Restore the Past

-- Query data as of a point in time (up to 90 days on Enterprise, 1 day Standard)
SELECT * FROM orders AT (TIMESTAMP => '2026-07-10 09:00:00'::TIMESTAMP);
SELECT * FROM orders BEFORE (STATEMENT => '8e5d3f2a-...');

-- Undo an accidental DELETE/UPDATE without a backup restore
UNDROP TABLE orders;                          -- table dropped by mistake
CREATE OR REPLACE TABLE orders AS
  SELECT * FROM orders AT (OFFSET => -3600);   -- 1 hour ago

Zero-Copy Cloning

-- Instant, metadata-only copy — no data is physically duplicated
CREATE TABLE orders_dev CLONE orders;
CREATE SCHEMA analytics_staging CLONE analytics;
CREATE DATABASE full_prod_copy CLONE prod;

-- Storage cost is $0 until the clone diverges (copy-on-write)
-- Diverged blocks are billed only for the delta, not the full copy
FeatureMechanismTypical Use
Time TravelRetains prior micro-partition versions for a retention windowUndo mistakes, audit historical state, point-in-time queries
Fail-safeAdditional 7-day Snowflake-managed recovery period after Time Travel expiresDisaster recovery only — not user-queryable, Snowflake support required
Zero-copy cloneNew table/schema/DB pointing at the same micro-partitions until writes divergeSpin up a full prod-like dev/test/staging environment in seconds
Time Travel has a storage cost Retaining changed/deleted data for the Time Travel window means storage isn't freed immediately. High-churn tables with long retention (up to 90 days) can meaningfully inflate storage billing — tune DATA_RETENTION_TIME_IN_DAYS per table to what's actually needed.
Section 06

Streams, Tasks & Snowpipe

Streams capture row-level changes for CDC, Tasks schedule SQL execution, and Snowpipe continuously ingests files as they land — together they let you build ELT pipelines entirely inside Snowflake with no external orchestrator.

Files land in S3/Azure/GCS stage │ ▼ (event notification, near-real-time) SNOWPIPE ──► raw_events table (auto-ingest, serverless compute) │ ▼ (row-level change capture) STREAM ──► tracks INSERT/UPDATE/DELETE since last consumed offset │ ▼ (scheduled or chained execution) TASK ──► MERGE into curated table, on a cron or after upstream task

Streams — Change Data Capture

CREATE STREAM orders_stream ON TABLE raw_orders;

-- Stream exposes METADATA$ACTION / METADATA$ISUPDATE / METADATA$ROW_ID
SELECT * FROM orders_stream;   -- consuming a stream in a DML advances its offset

MERGE INTO curated_orders t
USING orders_stream s ON t.order_id = s.order_id
WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' THEN DELETE
WHEN MATCHED AND s.METADATA$ACTION = 'INSERT' THEN UPDATE SET t.amount = s.amount
WHEN NOT MATCHED THEN INSERT (order_id, amount) VALUES (s.order_id, s.amount);

Tasks — Scheduled/Chained SQL

CREATE TASK refresh_curated
  WAREHOUSE = etl_wh
  SCHEDULE = 'USING CRON */10 * * * * UTC'   -- every 10 minutes
  WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')  -- skip run if nothing changed
AS
  MERGE INTO curated_orders t USING orders_stream s ON t.order_id = s.order_id
  WHEN MATCHED THEN UPDATE SET t.amount = s.amount
  WHEN NOT MATCHED THEN INSERT (order_id, amount) VALUES (s.order_id, s.amount);

ALTER TASK refresh_curated RESUME;   -- tasks are created suspended

Snowpipe — Continuous Ingestion

CREATE PIPE raw_events_pipe AUTO_INGEST = TRUE AS
  COPY INTO raw_events
  FROM @my_s3_stage
  FILE_FORMAT = (TYPE = 'JSON');

-- Cloud storage event notification (SNS/Event Grid/Pub-Sub) triggers Snowpipe
-- automatically — files typically visible in the table within ~1 minute,
-- billed per-file on serverless compute (no warehouse required)
Streams + Tasks = ELT without Airflow For pipelines that live entirely inside Snowflake, Streams (what changed) chained to Tasks (when to act) replace a lot of what teams reach for an external orchestrator to do — with the tradeoff of less cross-system coordination and observability than a dedicated orchestrator provides.
Section 07

Data Sharing

Secure Data Sharing lets one Snowflake account grant another account live, read-only access to data — no data copying, no ETL, no FTP. The consumer queries the provider's data directly against the provider's storage.

PROVIDER account CONSUMER account ┌───────────────┐ ┌───────────────┐ │ orders table │ ── SHARE ──────► │ (no copy!) │ │ (storage) │ (metadata │ queries live │ │ │ pointer │ data using own │ │ │ only) │ compute/warehouse│ └───────────────┘ └───────────────┘ Billed for storage Billed for their + own query compute own query compute

Sharing Mechanisms

MechanismScopeUse Case
Direct ShareAccount-to-account, same cloud regionShare curated tables with a known partner or internal BU
Snowflake MarketplacePublic/private listing across any Snowflake accountMonetize or consume third-party datasets (market data, weather, demographics)
Data Clean RoomGoverned, privacy-preserving joint queriesTwo parties analyze combined data (e.g., ad matching) without exposing raw rows
Cross-cloud/region auto-fulfillmentSnowflake replicates automatically to consumer's regionGlobal distribution without manual replication pipelines

Creating a Share

CREATE SHARE sales_share;
GRANT USAGE ON DATABASE sales_db TO SHARE sales_share;
GRANT USAGE ON SCHEMA sales_db.public TO SHARE sales_share;
GRANT SELECT ON TABLE sales_db.public.orders TO SHARE sales_share;
ALTER SHARE sales_share ADD ACCOUNTS = ('partner_account_id');

-- Consumer side — creates a read-only database backed by the share
CREATE DATABASE shared_sales FROM SHARE provider_account.sales_share;
Why this beats traditional data export No file transfer, no staleness (consumer always sees live data), no duplicated storage cost for the provider, and the provider retains full governance (revoke access instantly, row-access policies still apply). This is the mechanism behind the entire Snowflake Marketplace.
Section 08

Cost Optimization

Snowflake bills separately for compute (per-second warehouse credits) and storage (compressed bytes/month), plus serverless features like Snowpipe and automatic clustering. Cost control is mostly about compute governance.

Levers, Ranked by Impact

Aggressive auto-suspend

60s suspend on dev/ad-hoc warehouses. Idle compute is the single largest source of waste.

Right-size, don't over-provision

Start small, scale up only when query profile shows spillage to local/remote disk — a common sign of an undersized warehouse.

Resource monitors

Set credit-quota alerts/suspensions per warehouse or account to hard-cap runaway spend.

Separate warehouses per workload

Isolate ETL, BI, and data science onto distinct warehouses so a heavy job doesn't force-scale a shared cluster.

Use the result cache

Identical repeated queries (24hr window) return free, instantly, from Cloud Services — no warehouse spin-up.

Prune Time Travel retention

Set DATA_RETENTION_TIME_IN_DAYS to the minimum needed per table, especially on high-churn staging tables.

Resource Monitor

CREATE RESOURCE MONITOR monthly_cap
  WITH CREDIT_QUOTA = 5000
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 90 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND        -- stops new queries, lets running ones finish
    ON 110 PERCENT DO SUSPEND_IMMEDIATE;

ALTER WAREHOUSE etl_wh SET RESOURCE_MONITOR = monthly_cap;

Diagnosing an Expensive Query

-- Query History + credits consumed
SELECT query_text, warehouse_name, total_elapsed_time,
       credits_used_cloud_services, bytes_scanned, partitions_scanned, partitions_total
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD(day, -7, CURRENT_TIMESTAMP())
ORDER BY total_elapsed_time DESC
LIMIT 20;

-- Low partitions_scanned/partitions_total ratio = good pruning
-- High "bytes spilled to local/remote storage" in query profile = undersized warehouse
The "always-on" mistake A BI warehouse serving a dashboard with AUTO_SUSPEND = 3600 (1 hour) that only gets queried a few times an hour will burn 55+ minutes of pure idle credits per query. This single misconfiguration is the most common source of surprise Snowflake bills.
Section 09

Interview Questions

Frequently asked Snowflake interview questions, with the reasoning an interviewer is actually listening for.

"Explain Snowflake's architecture and why it matters."

Three independently-scaling layers: storage (compressed micro-partitions on cloud object storage), compute (elastic virtual warehouses that read that shared storage), and cloud services (metadata, optimization, security, result cache). Because compute and storage are decoupled, you can scale either independently and run many isolated warehouses against the same physical data with zero contention — the core advantage over shared-nothing MPP systems like a traditional on-prem Teradata/Vertica cluster.

"How does Snowflake achieve fast query performance without indexes?"

Instead of user-managed indexes, Snowflake relies on automatic micro-partitioning: every table is split into 50–500MB immutable columnar blocks, each with stored min/max metadata per column. The optimizer prunes partitions that can't match the query's filter before scanning any data — for well-ordered data this eliminates most of the table from consideration without any DBA index tuning.

"When would you use a clustering key?"

Only on large tables (rule of thumb: 100GB+) where query filters consistently hit a column whose natural (load-order) clustering has degraded — commonly from frequent updates or out-of-order backfills. Check SYSTEM$CLUSTERING_INFORMATION first; adding a clustering key has an ongoing background re-clustering cost, so it's not a default choice.

"What's the difference between scaling up and scaling out a warehouse?"

Scaling up (bigger warehouse size) adds more compute nodes to a single cluster, speeding up individual heavy queries. Scaling out (multi-cluster warehouses) adds more clusters of the same size to handle more concurrent queries, reducing queuing. Confusing the two is a classic mistake — a queuing problem under high concurrency isn't fixed by making the warehouse bigger, it's fixed by allowing more clusters.

"How would you build a near-real-time pipeline entirely in Snowflake?"

Snowpipe auto-ingests files from a cloud stage as they land (serverless, no warehouse needed). A Stream on the raw table tracks row-level changes since last consumed offset. A Task on a schedule (or chained to another task) runs a MERGE using the stream, guarded by SYSTEM$STREAM_HAS_DATA so it's a no-op when nothing changed. This gets you CDC-driven ELT without an external orchestrator.

"How is Secure Data Sharing different from replicating/exporting data to a partner?"

Data Sharing grants live, read-only access to the provider's actual storage via metadata pointers — no file is copied, no ETL job runs, and the consumer always sees current data. Traditional export (S3 drop, SFTP, API pull) duplicates storage, goes stale between syncs, and requires a pipeline to maintain. The tradeoff is that both parties must be on Snowflake (or use cross-cloud auto-fulfillment).

Follow-up trap: "Is Snowflake a database or a data warehouse?" Snowflake markets itself as a "Data Cloud" — beyond classic warehousing it also supports semi-structured/unstructured data, data sharing, data engineering (Streams/Tasks), and even application workloads (Snowpark, Native Apps). Framing it as only an OLAP warehouse undersells the platform and is a common interviewer gotcha.
