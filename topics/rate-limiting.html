SECTION 01

Rate Limiting & Throttling Fundamentals

Rate limiting and throttling are the primary defences against resource exhaustion, abuse, and cascade failures. Every production API needs them — the question is where to enforce them and at what granularity.

Rate Limiting vs Throttling

Rate Limiting

Hard ceiling on request volume per time window. Requests exceeding the limit are rejected immediately with HTTP 429. Protects the server from being overwhelmed. The client must retry later.

Throttling

Soft control that slows down processing rather than rejecting. Excess requests are queued or delayed. Provides a smoother experience but consumes memory for the queue. Often combined with rate limiting.

Why Rate Limiting is Non-Negotiable

DDoS / Brute Force Protection

A single malicious client sending 50,000 req/s can exhaust all database connections and memory before a human can react.

Fair Resource Distribution

Without limits, one power user can consume 90% of capacity, degrading service for all others. Rate limits enforce fairness.

Cost Control

APIs calling paid third-party services (LLM APIs, payment processors, SMS) need hard limits to prevent runaway billing from bugs or abuse.

SLA Preservation

Downstream services have their own limits. Propagating excess load causes cascading 429s and circuit breaker trips. Rate limit at the source.

HTTP 429 Response Standard

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 30                    # seconds until limit resets
X-RateLimit-Limit: 1000            # total allowed per window
X-RateLimit-Remaining: 0           # remaining in current window
X-RateLimit-Reset: 1714500000      # Unix timestamp of window reset

{
  "error": "rate_limit_exceeded",
  "message": "You have exceeded 1000 requests per hour. Retry after 30 seconds.",
  "retry_after": 30
}
Always return Retry-After Without Retry-After, clients in a retry loop will hammer your API continuously, creating a self-amplifying load spike. With it, clients back off intelligently and the load naturally spreads out.
SECTION 02

Rate Limiting Algorithms — Deep Dive

The choice of algorithm determines how precisely you control traffic, how much memory you consume, and whether clients experience sudden cliffs or smooth degradation.

1. Fixed Window Counter

How it works

Divide time into fixed windows (e.g., 00:00–01:00). Count requests per key per window. Reset counter at window boundary.

  Window: 12:00:00 - 12:01:00   Limit: 100 req/min
  ─────────────────────────────────────────────────
  12:00:30 ──── 100 requests arrive ──── counter=100 (ALLOWED)
  12:00:59 ────   1 request arrives  ──── counter=101 (REJECTED ✗)
  12:01:00 ──── counter RESETS to 0
  12:01:00 ──── 100 requests arrive ──── counter=100 (ALLOWED)

  Problem: 200 requests in 1 second straddling the boundary (burst exploit)

Pros

O(1) space per key. Trivially implemented with Redis INCR + EXPIRE. Simple to reason about for billing (hourly/daily quotas).

Cons

Boundary burst: a client can send 2× limit in 2× period straddling the boundary. Counters reset synchronously — thundering herd at window start.

2. Sliding Window Log

How it works

Store a timestamp for each request in a sorted set. On each request, remove timestamps older than the window, count remaining — if < limit, allow and add new timestamp.

# Redis sorted set implementation
ZADD rate:user123 <now_ms> <request_id>
ZREMRANGEBYSCORE rate:user123 0 <(now_ms - window_ms)>
count = ZCARD rate:user123
EXPIRE rate:user123 <window_seconds>

Pros

Perfectly accurate — no boundary burst. The count at any moment reflects the true sliding window.

Cons

O(requests) space per user. A high-volume user stores thousands of timestamps. Expensive ZREMRANGEBYSCORE on every request.

3. Sliding Window Counter (Hybrid) — Recommended

How it works

Blend the current fixed window count with the previous window count, weighted by how far into the current window we are. Approximates sliding window with O(1) space.

  Elapsed = position in current window / window size

  estimated_count = prev_window_count * (1 - elapsed) + current_window_count

  Example: window=60s, elapsed=30s (50%)
  prev_count=80, current_count=40
  estimated = 80 * 0.5 + 40 = 80  (vs limit 100 → ALLOWED)

Pros

O(1) space (only 2 counters per key). Very accurate — Cloudflare uses this and reports <0.003% error rate vs true sliding window.

Cons

Slight approximation error near window boundaries. Not suitable for strict financial rate limiting where exact counts are auditable requirements.

4. Token Bucket — Best for Burst-Tolerant APIs

How it works

A bucket holds up to capacity tokens. Tokens refill at a fixed rate. Each request consumes one token. If the bucket is empty, the request is rejected. The bucket can accumulate tokens up to capacity, allowing short bursts.

  Capacity: 10 tokens   Refill rate: 1 token/second
  ─────────────────────────────────────────────────
  t=0   bucket=10
  t=0   5 requests arrive ──── bucket=5 (ALLOWED)
  t=0   6 requests arrive ──── 5 allowed, 1 REJECTED (bucket=0)
  t=5   5 tokens refill ────── bucket=5
  t=5   3 requests arrive ──── bucket=2 (ALLOWED)

  Allows bursts up to bucket capacity, then enforces sustained rate
    
# Token bucket with Redis Lua script (atomic)
local key = KEYS[1]
local capacity = tonumber(ARGV[1])     -- 10
local refill_rate = tonumber(ARGV[2])  -- 1 token/second
local now = tonumber(ARGV[3])          -- current timestamp (ms)
local tokens_requested = tonumber(ARGV[4])  -- usually 1

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Calculate tokens to add based on elapsed time
local elapsed = (now - last_refill) / 1000.0
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

if new_tokens >= tokens_requested then
  redis.call('HMSET', key, 'tokens', new_tokens - tokens_requested, 'last_refill', now)
  redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 1)
  return 1  -- allowed
else
  redis.call('HMSET', key, 'tokens', new_tokens, 'last_refill', now)
  return 0  -- rejected
end

5. Leaky Bucket — Best for Smooth Output Rate

How it works

Requests fill a queue (the "bucket"). A processor drains the queue at a fixed rate. If the queue is full, new requests are dropped. Unlike token bucket, outbound processing is always at constant rate — no bursts reach the backend.

Best for

Protecting rate-sensitive downstream systems (payment processors, rate-limited 3rd-party APIs). Output is always smooth regardless of input spikes.

Trade-off

Requests wait in queue under load — adds latency. Queue overflow still drops requests. Requires persistent queue storage (Redis list, Kafka).

Algorithm Comparison

FastAPI Implementation — All Patterns

FastAPI offers multiple levels for implementing rate limiting, from simple in-process counters for development to production-grade Redis-backed distributed limiters.

Pattern 1 — slowapi (Simplest)

slowapi is a Starlette/FastAPI port of Flask-Limiter using token bucket algorithm in memory or Redis.

from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

limiter = Limiter(key_func=get_remote_address)  # key by IP
app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.get("/search")
@limiter.limit("10/minute")        # 10 requests per minute per IP
async def search(request: Request, q: str):
    return {"results": await do_search(q)}

@app.get("/report")
@limiter.limit("2/hour")           # expensive endpoint
async def report(request: Request):
    return {"data": await generate_report()}

Pattern 2 — Redis Token Bucket Middleware (Production)

import time, redis.asyncio as aioredis
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import JSONResponse

app = FastAPI()
redis_client = aioredis.from_url("redis://localhost:6379")

# Lua script for atomic token bucket check
TOKEN_BUCKET_SCRIPT = """
local key      = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])

local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local last_ts = tonumber(data[2]) or now

local delta   = math.max(0, now - last_ts)
local refill  = math.min(capacity, tokens + delta * rate / 1000)

if refill < 1 then
    redis.call('HMSET', key, 'tokens', refill, 'ts', now)
    return {0, math.ceil((1 - refill) / rate * 1000)}
end

redis.call('HMSET', key, 'tokens', refill - 1, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity / rate * 1000) + 5000)
return {1, 0}
"""

bucket_script = redis_client.register_script(TOKEN_BUCKET_SCRIPT)

class RateLimitConfig:
    def __init__(self, capacity: int, rate_per_sec: float):
        self.capacity = capacity
        self.rate_per_sec = rate_per_sec

# Per-endpoint limits
LIMITS = {
    "/api/search":  RateLimitConfig(capacity=20,  rate_per_sec=5),
    "/api/infer":   RateLimitConfig(capacity=5,   rate_per_sec=1),
    "/api/report":  RateLimitConfig(capacity=2,   rate_per_sec=0.1),
    "default":      RateLimitConfig(capacity=100, rate_per_sec=20),
}

@app.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    api_key = request.headers.get("X-API-Key", request.client.host)
    path = request.url.path
    cfg = LIMITS.get(path, LIMITS["default"])

    key = f"rl:{api_key}:{path}"
    now_ms = int(time.time() * 1000)

    result = await bucket_script(
        keys=[key],
        args=[cfg.capacity, cfg.rate_per_sec, now_ms]
    )
    allowed, retry_after_ms = result

    if not allowed:
        return JSONResponse(
            status_code=429,
            content={"error": "rate_limit_exceeded", "retry_after_ms": retry_after_ms},
            headers={
                "Retry-After": str(retry_after_ms // 1000 + 1),
                "X-RateLimit-Limit": str(cfg.capacity),
                "X-RateLimit-Remaining": "0",
            }
        )

    response = await call_next(request)
    response.headers["X-RateLimit-Limit"] = str(cfg.capacity)
    return response

Pattern 4 — Dependency-Based Rate Limit (per route)

from fastapi import Depends

class RateLimiter:
    def __init__(self, requests: int, window: int):
        self.requests = requests
        self.window = window  # seconds

    async def __call__(self, request: Request):
        key = f"rl:{request.client.host}:{request.url.path}"
        count = await redis_client.incr(key)
        if count == 1:
            await redis_client.expire(key, self.window)
        remaining = max(0, self.requests - count)
        if count > self.requests:
            raise HTTPException(
                status_code=429,
                detail="Rate limit exceeded",
                headers={
                    "Retry-After": str(await redis_client.ttl(key)),
                    "X-RateLimit-Remaining": "0"
                }
            )
        return remaining

# Reusable rate limit dependencies
search_limit  = RateLimiter(requests=10, window=60)
infer_limit   = RateLimiter(requests=5,  window=60)

@app.get("/search", dependencies=[Depends(search_limit)])
async def search(q: str):
    return {"results": await do_search(q)}

@app.post("/infer", dependencies=[Depends(infer_limit)])
async def infer(payload: InferRequest):
    return {"output": await model.predict(payload)}

Distributed Rate Limiting with Redis

In-process rate limiters break when you scale horizontally — each pod has its own counter, so N pods allow N times the intended limit. Redis provides a single shared counter visible to all instances.

The Problem with Local Rate Limiting

  WITHOUT distributed rate limiting (WRONG):
  ────────────────────────────────────────────────
  Client ─── 100 req/min limit ─── Load Balancer
                                       │
                          ┌────────────┼────────────┐
                          ▼            ▼            ▼
                       Pod A         Pod B         Pod C
                      counter:33   counter:33   counter:33
                      (each allows 100 → total: 300 requests slip through)

  WITH Redis distributed rate limiting (CORRECT):
  ─────────────────────────────────────────────────────
  Client ─── 100 req/min limit ─── Load Balancer
                                       │
                          ┌────────────┼────────────┐
                          ▼            ▼            ▼
                       Pod A         Pod B         Pod C
                          └──────────▶ Redis ◀──────┘
                                   counter:100
                               (shared across all pods)

Redis Sliding Window Counter (Atomic Lua)

SLIDING_WINDOW_SCRIPT = """
local key = KEYS[1]
local window = tonumber(ARGV[1])     -- seconds
local limit  = tonumber(ARGV[2])     -- max requests
local now    = tonumber(ARGV[3])     -- current time (ms)

-- Two keys: current window counter and previous window counter
local curr_key = key .. ':' .. math.floor(now / (window * 1000))
local prev_key = key .. ':' .. (math.floor(now / (window * 1000)) - 1)

local curr_count = tonumber(redis.call('GET', curr_key) or 0)
local prev_count = tonumber(redis.call('GET', prev_key) or 0)

-- Weight: how far through current window (0.0 to 1.0)
local elapsed_frac = (now % (window * 1000)) / (window * 1000)
local estimated = prev_count * (1 - elapsed_frac) + curr_count

if estimated >= limit then
    return {0, math.ceil((1 - elapsed_frac) * window)}  -- rejected, retry_after
end

redis.call('INCR', curr_key)
redis.call('EXPIRE', curr_key, window * 2)
return {1, 0}  -- allowed
"""

Layered Rate Limiting Architecture Best practice is three layers: (1) HAProxy/Istio at ingress for coarse IP-based protection, (2) Redis-backed application rate limiter for per-user/per-key precision, (3) circuit breaker per downstream call. Each layer catches a different abuse pattern.
SECTION 05

Queue Design: Kafka & RabbitMQ

Queues decouple the rate at which requests arrive from the rate at which they are processed. This is the single most effective tool for absorbing traffic bursts without dropping requests or overloading backends.

When to Queue Instead of Reject

StrategyClient ExperienceWhen to Use
Reject (429)Immediate failure, must retryStateless reads, cheap ops, abuse prevention
Queue + Async response202 Accepted, poll for resultExpensive jobs: ML inference, report generation
Queue + WebSocket pushWait, receive result when readyInteractive tools, real-time dashboards
Queue + Webhook callbackFire and forget, notified on completionB2B integrations, long-running workflows

Kafka — Architecture & Design Decisions

Topics & Partitions

A topic is split into partitions. Each partition is an ordered, immutable log. Max parallelism = number of partitions (one consumer per partition in a group).

Consumer Groups

Multiple consumers sharing a group each process different partitions. Scale consumers by adding instances — up to partition count. Beyond that, consumers idle.

Retention

Messages persist even after consumption (configurable: time or size). Replay events, feed multiple consumers independently, recover from failures by re-reading.

Ordering

Ordering guaranteed within a partition. Use partition key (e.g., user_id) to ensure all events for a user go to the same partition and are processed in order.

Kafka FastAPI Producer Pattern

from aiokafka import AIOKafkaProducer
from fastapi import FastAPI, BackgroundTasks
import json, uuid

app = FastAPI()
producer: AIOKafkaProducer = None

@app.on_event("startup")
async def startup():
    global producer
    producer = AIOKafkaProducer(
        bootstrap_servers="kafka:9092",
        value_serializer=lambda v: json.dumps(v).encode(),
        compression_type="gzip",
        acks="all",                       # wait for all replicas to acknowledge
        max_batch_size=65536,             # 64KB batch for throughput
        linger_ms=5,                      # wait 5ms to batch more messages
        enable_idempotence=True,          # exactly-once semantics on producer
    )
    await producer.start()

@app.on_event("shutdown")
async def shutdown():
    await producer.stop()

@app.post("/infer", status_code=202)
async def submit_inference(request: InferRequest):
    job_id = str(uuid.uuid4())

    await producer.send_and_wait(
        topic="inference-jobs",
        key=request.model_id.encode(),   # partition by model for ordering
        value={
            "job_id": job_id,
            "model": request.model_id,
            "payload": request.data,
            "submitted_at": time.time(),
            "callback_url": request.webhook_url,
        }
    )

    return {
        "job_id": job_id,
        "status": "queued",
        "status_url": f"/jobs/{job_id}",
        "estimated_wait_s": await estimate_wait()
    }

Kafka Consumer — Idempotent Worker

from aiokafka import AIOKafkaConsumer

async def start_workers(num_workers: int = 4):
    consumer = AIOKafkaConsumer(
        "inference-jobs",
        bootstrap_servers="kafka:9092",
        group_id="inference-workers",
        auto_offset_reset="earliest",
        enable_auto_commit=False,         # manual commit for at-least-once
        max_poll_records=10,              # process 10 at a time
        session_timeout_ms=30000,
        heartbeat_interval_ms=3000,
    )
    await consumer.start()

    async for msg in consumer:
        job = json.loads(msg.value)
        job_id = job["job_id"]

        # Idempotency check: skip if already processed
        if await redis.exists(f"processed:{job_id}"):
            await consumer.commit()
            continue

        try:
            result = await run_inference(job["payload"], job["model"])
            await store_result(job_id, result)
            await redis.setex(f"processed:{job_id}", 86400, "1")  # 24h dedup window

            # Notify client via webhook if provided
            if job.get("callback_url"):
                await send_webhook(job["callback_url"], job_id, result)

            await consumer.commit()

        except Exception as e:
            # Don't commit: Kafka will redeliver to another consumer
            await send_to_dead_letter_queue(job, str(e))
            await consumer.commit()  # prevent infinite redelivery after DLQ

RabbitMQ — Architecture & Design Decisions

When to Choose RabbitMQ

Complex routing logic (topic exchanges, header-based routing). Task queues where each message processed by exactly one consumer. Per-message TTL and priority queues. Smaller scale (<50k msg/s).

When to Choose Kafka

Event streaming with replay. Multiple independent consumers reading same events. Very high throughput (>100k msg/s). Event sourcing / audit log. Long retention (days to weeks).

import aio_pika

async def publish_job(channel, job: dict):
    await channel.default_exchange.publish(
        aio_pika.Message(
            body=json.dumps(job).encode(),
            content_type="application/json",
            delivery_mode=aio_pika.DeliveryMode.PERSISTENT,  # survive broker restart
            priority=job.get("priority", 0),                  # 0-9 priority
            expiration=str(300 * 1000),                       # 5 min TTL in ms
            headers={"x-job-id": job["job_id"]},
        ),
        routing_key="inference.jobs",
    )

# Consumer with prefetch (flow control)
async def start_consumer(channel):
    await channel.set_qos(prefetch_count=5)  # max 5 unacked messages at once

    queue = await channel.declare_queue(
        "inference.jobs",
        durable=True,
        arguments={
            "x-dead-letter-exchange": "dlx",   # failed msgs go here
            "x-dead-letter-routing-key": "inference.dead",
            "x-max-priority": 9,
        }
    )

    async with queue.iterator() as q_iter:
        async for message in q_iter:
            async with message.process(requeue=False):  # ack on success, nack on exception
                job = json.loads(message.body)
                await process_job(job)

Response Channels: Webhook / WebSocket / SSE

Once a request is queued for async processing, the client needs to receive the result. The choice of delivery channel depends on client type, latency requirements, and connection persistence needs.

Channel Selection Guide

  Is the client a server (B2B)?
       |
       Yes ──> Webhook (push to client's endpoint)
       |
       No (browser / app)
          |
          +── Does client need bi-directional communication?
          |        Yes ──> WebSocket
          |
          +── Does client need server-push updates only?
          |        Yes ──> SSE (Server-Sent Events)
          |
          +── Can client poll?
                   Yes ──> REST polling with Retry-After header

WebSocket — Real-Time Bi-Directional

WebSocket upgrades an HTTP connection to a persistent full-duplex TCP connection. Both client and server can send messages at any time without request-response overhead.

from fastapi import FastAPI, WebSocket, WebSocketDisconnect
import asyncio, json

app = FastAPI()

# Connection manager: tracks all active connections
class ConnectionManager:
    def __init__(self):
        self.connections: dict[str, WebSocket] = {}

    async def connect(self, job_id: str, ws: WebSocket):
        await ws.accept()
        self.connections[job_id] = ws

    def disconnect(self, job_id: str):
        self.connections.pop(job_id, None)

    async def send_update(self, job_id: str, data: dict):
        ws = self.connections.get(job_id)
        if ws:
            try:
                await ws.send_json(data)
            except Exception:
                self.disconnect(job_id)

manager = ConnectionManager()

@app.websocket("/ws/jobs/{job_id}")
async def job_updates(websocket: WebSocket, job_id: str):
    await manager.connect(job_id, websocket)
    try:
        while True:
            # Server pushes progress updates
            status = await get_job_status(job_id)
            await websocket.send_json({
                "job_id": job_id,
                "status": status.state,
                "progress": status.progress,

            })
            if status.state in ("done", "failed"):
                break
            await asyncio.sleep(0.5)   # push every 500ms
    except WebSocketDisconnect:
        manager.disconnect(job_id)

async def notify_completion(job_id: str, result: dict):
    await manager.send_update(job_id, {"status": "done", "result": result})

Webhook — Async Push to Client's Server

import httpx

async def send_webhook(callback_url: str, job_id: str, result: dict, max_retries: int = 3):
    payload = {
        "event": "job.completed",
        "job_id": job_id,
        "result": result,
        "timestamp": time.time(),
    }

    # Sign payload for security (HMAC-SHA256)
    import hmac, hashlib
    body = json.dumps(payload, sort_keys=True).encode()
    signature = hmac.new(WEBHOOK_SECRET.encode(), body, hashlib.sha256).hexdigest()

    for attempt in range(max_retries):
        try:
            async with httpx.AsyncClient(timeout=10) as client:
                resp = await client.post(
                    callback_url,
                    content=body,
                    headers={
                        "Content-Type": "application/json",
                        "X-Webhook-Signature": f"sha256={signature}",
                        "X-Webhook-ID": job_id,
                        "X-Webhook-Timestamp": str(int(time.time())),
                    }
                )
                if resp.status_code < 300:
                    return  # success
                if resp.status_code < 500:
                    break   # client error, don't retry 4xx
        except Exception:
            pass

        # Exponential backoff: 1s, 2s, 4s, ...
        await asyncio.sleep(2 ** attempt)

Ray Distributed Platform

Ray is a distributed Python framework for scaling compute across a cluster. It transforms a FastAPI endpoint into a parallelised, autoscaling workload that can handle 10,000s of concurrent requests by distributing work across CPU/GPU nodes.

Ray Core Primitives

@ray.remote (Tasks)

Any Python function decorated with @ray.remote executes asynchronously in a worker process (potentially on a different node). Returns a Future (ObjectRef).

@ray.remote (Actors)

Stateful workers — classes decorated with @ray.remote. Each actor instance is a long-lived process holding state. Used for model serving, connection pools, counters.

ray.get()

Synchronously wait for a list of ObjectRefs to complete. ray.wait() for non-blocking partial completion. Both support batching for efficient retrieval.

Placement Groups

Reserve CPU/GPU resources across nodes in "bundles". Used to co-locate actors that communicate frequently, or to reserve GPU for model replicas.

Ray Serve Batching — GPU Efficiency

Batching is critical for GPU throughput. A single GPU processes a batch of 64 inputs in nearly the same time as 1 input. Ray Serve's @serve.batch decorator accumulates concurrent requests into a single batch call:

from ray import serve
import asyncio

@serve.deployment(num_replicas=2, ray_actor_options={"num_gpus": 1})
class BatchedInference:
    def __init__(self):
        self.model = load_model()

    @serve.batch(max_batch_size=64, batch_wait_timeout_s=0.05)
    async def handle_batch(self, inputs: list[str]) -> list[dict]:
        # Called with up to 64 requests batched together
        # GPU processes 64 at cost of ~1 — massive throughput gain
        results = self.model.predict_batch(inputs)  # single GPU call
        return [{"result": r} for r in results]

    async def __call__(self, request: Request) -> dict:
        data = (await request.json())["input"]
        return await self.handle_batch(data)   # transparently batched

Ray Tasks for Parallel CPU Work

@ray.remote
def process_record(record: dict) -> dict:
    # Runs in parallel worker process — CPU-bound work
    return heavy_computation(record)

@app.post("/batch-process")
async def batch_process(records: list[dict]):
    # Submit all records to Ray in parallel
    futures = [process_record.remote(r) for r in records]

    # Collect as they complete (not all at once — avoid OOM)
    results = []
    while futures:
        ready, futures = ray.wait(futures, num_returns=min(10, len(futures)))
        results.extend(ray.get(ready))

    return {"results": results}

Database Patterns for High RPS

Read Replicas

Route all SELECT queries to read replicas. Write to primary only. 80% of most APIs are reads — this alone multiplies read capacity by replica count.

Write-Behind Cache

Write to Redis (instant), return 200. Background job flushes to DB. Suitable for non-critical writes (analytics, view counts). Risk: data loss on cache failure.

Connection Pooling (PgBouncer)

PostgreSQL max_connections ~500. 80 pods × 10 workers × 10 pool = 8000 connections — DB crashes. PgBouncer multiplexes thousands of app connections onto 100 real DB connections.

Partial Caching (Redis + TTL)

Cache hot query results in Redis. Pattern: cache-aside (read-through). Invalidate on write. 99% cache hit ratio reduces DB load by 100×.

Little's Law — The Fundamental Formula

L = λ × W

L = average number of requests in the system (concurrency)
λ = arrival rate (requests/second)
W = average time a request spends in the system (latency in seconds)

Example: 1,000 req/s, 200ms avg latency → 200 concurrent requests in-flight at any moment.
Your connection pool, thread pool, and in-flight request limit must all be ≥ 200.

Headroom Rules

  • Design for 3× peak load — peaks are often 2–3× the average, and load tests miss pathological patterns
  • Keep CPU utilisation under 60% at peak — the last 40% headroom absorbs spikes before autoscaler responds (30s lag)
  • Set maxReplicas to 2× expected peak pods — autoscaler is reactive, not predictive
  • Rate limit at 80% of measured capacity — the 20% buffer absorbs measurement variance and prevents cliff-edge degradation
  • Pre-scale with KEDA Cron 5 minutes before known traffic events (market open, batch job trigger)
