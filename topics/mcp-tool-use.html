Section 01

LLM Tool Use Fundamentals

Tool use allows LLMs to call external functions — APIs, databases, calculators, search engines — turning them from text generators into action-capable agents. Both OpenAI and Anthropic support tool use natively through their APIs.

User: "What's Apple's stock price and today's weather in London?" │ ▼ LLM decides to call tools: ┌─────────────────────────────────┐ │ tool_call: get_stock("AAPL") │ │ tool_call: get_weather("London")│ └─────────────────────────────────┘ │ ▼ Application executes tools (in parallel) │ ▼ Results sent back to LLM as tool_result messages │ ▼ LLM generates final grounded answer

OpenAI vs Anthropic Tool Calling API

AspectOpenAIAnthropic Claude

Parallel callsYes — multiple tool_calls in one responseYes — multiple tool_use blocks

Full Tool Calling Example (OpenAI)

from openai import OpenAI
import json

client = OpenAI()

tools = [{
    "type": "function",
    "function": {
        "name": "get_stock_price",
        "description": "Get the current stock price for a given ticker symbol.",
        "parameters": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker, e.g. AAPL"},
                "currency": {"type": "string", "enum": ["USD", "GBP", "EUR"], "default": "USD"}
            },
            "required": ["ticker"]
        }
    }
}]

messages = [{"role": "user", "content": "What is Apple's stock price?"}]

# First call — model decides to use a tool
response = client.chat.completions.create(
    model="gpt-4o-mini", tools=tools, tool_choice="auto", messages=messages
)
tool_call = response.choices[0].message.tool_calls[0]
args = json.loads(tool_call.function.arguments)  # {"ticker": "AAPL"}

# Execute the tool
result = {"price": 213.45, "currency": "USD"}

# Second call — submit result
messages += [
    response.choices[0].message,  # assistant message with tool_calls
    {"role": "tool", "tool_call_id": tool_call.id, "content": json.dumps(result)}
]
final = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
print(final.choices[0].message.content)
Tool descriptions are part of your prompt The quality of your tool's description field directly determines how accurately the model selects and invokes it. Write descriptions as if explaining to a junior developer which function to call and when.
Section 02

Tool Design Patterns

Good tool design is as important as good prompt design. Poorly named, vague, or overlapping tools cause the model to select the wrong tool, pass wrong arguments, or fail silently.

Atomic Tools

One tool, one responsibility. search_documents not search_and_summarise_documents. Compose in application code.

Read vs Write

Separate read tools (no side effects) from write tools (create/update/delete). Annotate clearly in descriptions.

Idempotent Writes

Write tools should be safe to call twice. Accept an optional idempotency_key for critical operations.

Rich Error Messages

Return structured errors: {"error": "not_found", "message": "...", "suggestion": "..."}. Models use these to self-correct.

Well-Designed Tool Definition

search_tool = {

                },
                "top_k": {
                    "type": "integer",
                    "description": "Number of results to return (1-10). Default 5.",
                    "default": 5,
                    "minimum": 1,
                    "maximum": 10
                },
                "category": {
                    "type": "string",
                    "enum": ["policy", "product", "procedure", "all"],

}

Section 03

Model Context Protocol (MCP)

MCP is an open standard (created by Anthropic, Nov 2024) for connecting AI models to external tools and data sources. It standardises the interface between AI hosts (Claude, Cursor, VS Code) and MCP servers (tools, databases, APIs) using JSON-RPC 2.0.

┌─────────────────────────────────────────────────────────────────┐ │ MCP ARCHITECTURE │ │ │ │ HOST (Claude Desktop / Claude Code / Cursor) │ │ │ │ │ └──► MCP CLIENT (manages connections) │ │ │ │ │ │ JSON-RPC 2.0 │ │ │ (stdio or SSE transport) │ │ │ │ │ ┌─────────┼──────────────────────────┐ │ │ │ │ │ │ │ MCP Server MCP Server MCP Server │ │ (filesystem) (GitHub API) (Postgres) │ │ │ │ │ │ │ [Tools] [Resources] [Prompts] │ └─────────────────────────────────────────────────────────────────┘

MCP Primitives

PrimitiveDirectionDescriptionExample
ToolsServer → ClientFunctions the LLM can call to take actionscreate_file, run_query
ResourcesServer → ClientData the LLM can read (like files or DB rows)file://README.md, db://users/42
PromptsServer → ClientPre-built prompt templates with argumentscode_review, summarise_doc
SamplingClient → ServerServer asks the LLM to generate text (agentic)Server requests LLM completion mid-flow

filesystem

Read/write local files and directories.

github

Search repos, read files, manage issues/PRs.

postgres

Read-only SQL queries against a Postgres DB.

slack

Read channels, post messages, manage threads.

puppeteer

Browser automation — screenshots, clicks, forms.

memory

Persistent key-value memory across sessions.

MCP = USB-C for AI tools Write one MCP server and it works with any MCP-compatible host: Claude Desktop, Claude Code, Cursor, Cline, VS Code Copilot. No more per-integration glue code.
Section 04

Building MCP Servers (Python)

The mcp Python SDK (by Anthropic) provides a decorator-based API for exposing tools, resources, and prompts. A minimal server is under 30 lines of code.

from mcp.server.fastmcp import FastMCP
import httpx

mcp = FastMCP("Weather Service")

@mcp.tool()
async def get_weather(city: str, units: str = "celsius") -> dict:
    """Get current weather for a city. Units: celsius or fahrenheit."""
    async with httpx.AsyncClient() as client:
        r = await client.get(
            "https://wttr.in/{city}",
            params={"format": "j1"},
        )
        data = r.json()
        temp = data["current_condition"][0]["temp_C"]
        if units == "fahrenheit":
            temp = int(temp) * 9 // 5 + 32
        return {"city": city, "temperature": temp, "units": units}

@mcp.resource("weather://forecast/{city}")
async def weather_forecast(city: str) -> str:
    """3-day forecast resource for a city."""
    return f"Forecast data for {city}..."

@mcp.prompt()
def weather_report_prompt(city: str) -> str:
    """Generate a weather report prompt template."""
    return f"Write a friendly weather report for {city} based on the current conditions."

if __name__ == "__main__":
    mcp.run()  # stdio transport (default)

Section 05

Building MCP Servers (TypeScript)

The TypeScript SDK is the reference implementation — most official Anthropic MCP servers are written in TypeScript. It provides full type safety and is the best choice for production servers.

import { McpServer, ResourceTemplate } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "todo-server", version: "1.0.0" });
const todos: { id: number; text: string; done: boolean }[] = [];

// Tool: add a todo
server.tool(
  "add_todo",
  "Add a new todo item to the list",
  { text: z.string().describe("The todo item text") },
  async ({ text }) => {
    const todo = { id: todos.length + 1, text, done: false };
    todos.push(todo);
    return { content: [{ type: "text", text: `Added todo #${todo.id}: ${text}` }] };
  }
);

// Tool: list todos
server.tool("list_todos", "List all todo items", {}, async () => {
  const list = todos.map(t => `${t.done ? "✓" : "○"} #${t.id}: ${t.text}`).join("\n");
  return { content: [{ type: "text", text: list || "No todos yet." }] };
});

// Resource: expose todos as a resource
server.resource(
  "todos://all",
  new ResourceTemplate("todos://all", { list: undefined }),
  async () => ({
    contents: [{ uri: "todos://all", text: JSON.stringify(todos, null, 2), mimeType: "application/json" }]
  })
);

// Start server
const transport = new StdioServerTransport();
await server.connect(transport);
Use Zod for input schemas The TypeScript SDK accepts Zod schemas for tool parameters. Zod provides runtime validation + auto-generated JSON Schema — the best of both worlds.
Section 06

Structured Outputs

Structured outputs guarantee the LLM returns valid JSON matching a precise schema. This eliminates brittle regex parsing and makes LLM output a first-class typed object in your application.

User Request → LLM → [JSON mode / Structured Output] → Validated Schema │ ┌─────────────────────┤ │ │ Valid JSON Validation Error │ │ Pydantic model Retry with error │ (Instructor) Application logic

Instructor — Pydantic Extraction

import instructor
from openai import OpenAI
from pydantic import BaseModel, Field
from typing import Optional

client = instructor.from_openai(OpenAI())

class CompanyInfo(BaseModel):
    name: str = Field(description="Company legal name")
    founded: Optional[int] = Field(description="Year founded, if mentioned")
    headquarters: str = Field(description="City and country of HQ")
    employees: Optional[int] = Field(description="Approximate employee count")
    sector: str = Field(description="Primary business sector")

result = client.chat.completions.create(
    model="gpt-4o-mini",
    response_model=CompanyInfo,
    messages=[{
        "role": "user",
        "content": "Anthropic is an AI safety company founded in 2021, "
                   "headquartered in San Francisco, USA, with ~500 employees."
    }]
)
print(result)
# CompanyInfo(name='Anthropic', founded=2021, headquarters='San Francisco, USA', ...)

Section 07

Parallel Tool Calls

Modern LLMs can request multiple tool calls in a single response. Your application should execute them concurrently with asyncio.gather, then return all results in a single follow-up message.

LLM Response: tool_calls = [ {"id": "call_1", "function": "get_stock", "args": {"ticker": "AAPL"}}, {"id": "call_2", "function": "get_stock", "args": {"ticker": "MSFT"}}, {"id": "call_3", "function": "get_weather", "args": {"city": "London"}} ] │ ▼ asyncio.gather() — all 3 in parallel [result_1, result_2, result_3] (~100ms total vs ~300ms sequential) │ ▼ Submit all results in one message LLM generates final answer
import asyncio
import json
from openai import AsyncOpenAI

client = AsyncOpenAI()

async def execute_tool(tool_call) -> dict:
    name = tool_call.function.name
    args = json.loads(tool_call.function.arguments)
    # Route to actual tool implementation
    if name == "get_stock_price":
        return {"price": 213.45, "ticker": args["ticker"]}
    if name == "get_weather":
        return {"temp": 18, "city": args["city"], "condition": "Cloudy"}
    return {"error": f"Unknown tool: {name}"}

async def handle_parallel_tools(messages: list) -> str:
    response = await client.chat.completions.create(
        model="gpt-4o-mini", tools=tools, tool_choice="auto", messages=messages
    )
    msg = response.choices[0].message

    if not msg.tool_calls:
        return msg.content

    # Execute all tool calls in parallel
    results = await asyncio.gather(*[execute_tool(tc) for tc in msg.tool_calls])

    # Submit all results at once
    messages.append(msg)
    for tc, result in zip(msg.tool_calls, results):
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": json.dumps(result)
        })

    final = await client.chat.completions.create(model="gpt-4o-mini", messages=messages)
    return final.choices[0].message.content
Claude makes sequential calls by default OpenAI models tend to batch parallel tool calls in one response; Claude often makes sequential calls. Test both. For Claude, you may need to explicitly instruct it to gather multiple pieces of information simultaneously.
Section 08

Tool Security

Tools that interact with external systems introduce attack surface. The three main threats are prompt injection (malicious content in tool results), tool abuse (LLM calling dangerous tools unexpectedly), and data exfiltration via tool outputs.

User Input → [Input sanitisation] → LLM │ tool_call decision │ [Authorisation check] │ ┌─────────────────┴──────────────────┐ Allowed Denied │ │ [Sandboxed execution] Return error to LLM │ Tool result │ [Output filtering] ← strip secrets / PII │ Return to LLM
AttackDescriptionMitigation
Prompt injectionTool result contains "Ignore previous instructions..."Wrap results in XML tags; instruct model to treat tool results as data only
Tool abuseModel calls delete_database unexpectedlyRequire user confirmation for destructive tools; whitelist allowed tools per session
Data exfiltrationModel encodes secrets in a web_search queryLog all tool calls; block outbound tool calls with sensitive data patterns
Resource exhaustionModel calls an expensive tool in a loopPer-session tool call budget; rate limiting per tool
 
from functools import wraps
import logging

ALLOWED_TOOLS = {"search_documents", "get_weather", "calculate"}
DANGEROUS_TOOLS = {"delete_records", "send_email", "execute_code"}

def require_confirmation(tool_name: str) -> bool:
    """Prompt user before executing high-risk tools."""
    if tool_name in DANGEROUS_TOOLS:
        answer = input(f"⚠️  Allow tool '{tool_name}'? [y/N]: ")
        return answer.lower() == "y"
    return True

def sanitise_tool_result(result: str) -> str:
    """Strip injection attempts from tool results."""
    injection_patterns = [
        "ignore previous instructions",
        "system prompt:",
        "new instructions:",
    ]
    lowered = result.lower()
    for pattern in injection_patterns:
        if pattern in lowered:
            logging.warning(f"Potential prompt injection detected in tool result")
            return "[Tool result redacted due to security policy]"
    return result
Never pass unsanitised LLM outputs to shell tools If you have a run_shell_command tool, the LLM could be tricked into running arbitrary commands via a crafted document. Always sandbox code execution in Docker or a language-level sandbox (e.g., RestrictedPython).
Section 09

Agent Integration

MCP tools integrate cleanly into LangChain, LangGraph, CrewAI, and Pydantic AI. The key pattern is wrapping MCP tool calls as framework-native tool objects so the orchestrator can invoke them transparently.

Agent (LangGraph) │ ├─ State: messages, tool_results │ ├─ llm_node: call LLM with tools registered │ │ │ └─► LLM returns tool_call(s) │ └─ tool_node: execute tool calls │ ├─ MCP Client → stdio/SSE → MCP Server │ └─► execute tool → return result │ └─► Add tool_results to state → back to llm_node

Wrapping MCP Tools in LangChain

from langchain_core.tools import StructuredTool
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def create_langchain_mcp_tools(server_script: str) -> list:
    """Wrap all tools from an MCP server as LangChain StructuredTools."""
    server_params = StdioServerParameters(command="python", args=[server_script])

    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            mcp_tools = await session.list_tools()

            lc_tools = []
            for tool in mcp_tools.tools:
                async def call_tool(name=tool.name, **kwargs):
                    async with stdio_client(server_params) as (r, w):
                        async with ClientSession(r, w) as s:
                            await s.initialize()
                            result = await s.call_tool(name, arguments=kwargs)
                            return result.content[0].text

                lc_tools.append(StructuredTool(
                    name=tool.name,
                    description=tool.description,
                    func=call_tool,
                    coroutine=call_tool,
                ))
    return lc_tools

Dynamic Tool Registration

Discover available MCP servers at runtime. Register only the tools relevant to the current task context.

Tool Retrieval with RAG

With 100+ tools, embed tool descriptions. At query time, retrieve the top-K relevant tools to pass to the LLM — avoids token bloat.

Graceful Degradation

Catch tool execution errors and return structured error messages. The LLM can self-correct or inform the user rather than crashing.

Audit Logging

Log every tool call: timestamp, tool name, arguments, result, latency. Essential for debugging multi-step agent traces.
