Section 01

Basics of the .NET Framework

.NET is a managed platform: your source code never runs directly on the CPU. It's compiled to an intermediate, platform-neutral bytecode (IL), packaged into an assembly with metadata, and only turned into real machine code at load/run time by the CLR's JIT compiler. That indirection is what buys you cross-language interop, automatic memory management, and type safety.

From source to native code

C#.cs
F#.fs
VB.NET.vb
Language Compiler (Roslyn, etc.)enforces the language's own rules
Assembly (.dll / .exe)CIL (MSIL) + metadata + manifest
CLR — Common Language Runtimeloader, type-checker, JIT, GC
JIT CompilerIL → native machine code, per method, on first call
Native code executing on the CPU
Why the IL indirection matters Because every .NET language compiles down to the same IL + CTS type model, a C# class can inherit from an F# class, a VB.NET assembly can implement a C# interface, and tools like decompilers, profilers, and the debugger all work identically regardless of source language. This is the entire point of the CLR: one runtime, many front-end languages.

Core building blocks

ComponentWhat it actually does
CLRThe execution engine: loads assemblies, verifies IL type-safety, JIT-compiles methods, manages the GC heap, handles exceptions/threads.
BCL (Base Class Library)The System.* namespaces — collections, I/O, strings, threading, networking. Ships inside the runtime.
FCL (Framework Class Library)BCL + the higher-level frameworks built on top (ASP.NET, WPF, WCF, EF).
CTS (Common Type System)The universal type rulebook — defines what a "class", "struct", "interface", "delegate" is at the runtime level, independent of source language.
CLS (Common Language Specification)A stricter subset of CTS. A library that only exposes CLS-compliant members is guaranteed usable from any .NET language (e.g., no unsigned types in a public API, since VB.NET historically lacked them).
AssemblyThe unit of deployment and versioning — a .dll/.exe containing IL, a manifest (name, version, referenced assemblies), and type metadata.
GAC (Global Assembly Cache)Machine-wide store for strong-named, shared assemblies. A .NET Framework-only concept — modern .NET uses local, side-by-side NuGet-restored dependencies instead.
AppDomainLegacy in-process isolation boundary (unload code without killing the process). Removed from the runtime model in .NET Core — replaced by AssemblyLoadContext.

What the CLR is responsible for at runtime

Memory management

Allocates objects on the managed heap and reclaims them via the garbage collector — no manual free().

Type safety & verification

IL is verified before execution; you can't reinterpret a string as an int* the way you can in unsafe C/C++.

Exception handling

A unified exception model (try/catch/finally) works the same across all managed languages.

JIT compilation

Compiles IL to native code per-method on first invocation (or ahead-of-time with NativeAOT/ReadyToRun — see §2).

Thread & task scheduling

Owns the managed ThreadPool that the TPL and async/await build on (see §5).

Security

Historically enforced Code Access Security (CAS) sandboxing; modern .NET relies on OS-level sandboxing instead (CAS is effectively retired).

Section 02

.NET Framework vs .NET Core vs Modern .NET

There have been effectively three eras of .NET. Getting the timeline straight matters for interviews because it explains why certain APIs exist twice, why "port to .NET Core" was a multi-year industry migration, and why the version number jumped from 4.8 straight to 5.

Timeline

One brand, three runtimes over 20+ years
.NET Framework2002 – 2019 (4.8, last version)
Windows only · closed-source runtime
.NET Core2016 – 2020 (1.0 → 3.1)
Cross-platform rewrite, open source
.NET 5, 6, 7, 8, 9…2020 → present, yearly
Unified — "Core" dropped from the name
.NET 5 was deliberately numbered to skip "4" so nobody would confuse it with .NET Framework 4.x. Since .NET 5, there is exactly one .NET going forward — "modern .NET" — released every November, with every even number (6, 8, 10…) as a 3-year LTS release and odd numbers as 18-month STS/current releases.

.NET Standard — the bridge, not a runtime

.NET Standard is a specification (a set of APIs a library promises to implement), not a runtime you execute. A library targeting netstandard2.0 can be referenced from both .NET Framework 4.6.1+ and .NET Core 2.0+, which is how the ecosystem shared class libraries during the multi-year migration window. Since .NET 5 unified the runtimes, new class libraries typically just multi-target modern TFMs (e.g. net8.0) directly and only reach for netstandard2.0 if they must still support .NET Framework consumers.

Runtime flavors you'll meet in the wild

CoreCLR

The default modern .NET runtime — what you get from dotnet run.

Mono

Lighter runtime used by Xamarin, Unity, and Blazor WebAssembly (interpreter/AOT hybrid, small footprint).

NativeAOT

Compiles straight to a self-contained native executable ahead of time — no JIT, near-instant startup, smaller memory, but no runtime reflection-heavy dynamic code.

ReadyToRun (R2R)

Pre-JITs IL into native code stored alongside the assembly to cut cold-start time, while still allowing the JIT to re-optimize hot paths.

Where you'll still run into .NET Framework in 2026 Legacy WCF services (not fully ported — use CoreWCF or gRPC when modernizing), classic WebForms apps, and COM/Windows-specific interop (e.g. Office automation) that never had a reason to move. Everything net-new should target the current LTS of modern .NET.
Section 03

C# Fundamentals

The fundamentals that everything else in this guide leans on: how value and reference types actually live in memory, what boxing costs, the property/exception idioms that show up in every C# codebase, and the two abstraction mechanisms — interfaces and delegates — that the rest of the language (LINQ, events, DI, async) is built on top of.

Value types vs reference types

Stack
int x = 42value types: struct, enum, primitives
Person p ──┐reference variable lives here
points to
Managed Heap
Person objectreference types: class, string, array, delegate

Copying a value type copies the bits (a new, independent 42). Copying a reference type copies the pointer — both variables now point at the same heap object, so mutating through one is visible through the other.

Boxing and unboxing

int i = 42;
object boxed = i;        // boxing: heap-allocates a wrapper, copies the value in
int back = (int)boxed;   // unboxing: type-checked copy back out

// Every non-generic collection member access on a value type boxes:
ArrayList list = new ArrayList();
list.Add(42);             // boxes
int x = (int)list[0];     // unboxes
Why this matters in interviews Boxing is a hidden heap allocation and a hidden copy — a classic cause of GC pressure in hot loops. It's exactly the problem generics (List<int> instead of ArrayList) were introduced to eliminate, since a generic collection is specialized per value type at JIT time and never boxes.

Properties

public class Order
{
    public int Id { get; set; }                     // auto-implemented property
    public decimal Total { get; init; }              // settable only at construction (C# 9+)
    public string Summary => $"{Id}: {Total:C}";      // expression-bodied, read-only, computed

    private string _status = "Pending";
    public string Status                              // full property with backing field
    {
        get => _status;
        set => _status = value ?? throw new ArgumentNullException(nameof(value));
    }
}

Interfaces

An interface is a pure contract — a set of members a type promises to implement, with no state of its own. It's the mechanism that makes abstraction (§9) concrete in C#: code depends on IShape, never on which concrete shape it got.

IShapedouble Area(); double Perimeter();
Circle : IShape
Rectangle : IShape
Triangle : IShape
public interface IShape
{
    double Area();
    double Perimeter();

    // default interface method (C# 8+) — a body ships WITH the interface;
    // implementers get it for free unless they choose to override it
    string Describe() => $"Area = {Area():F2}, Perimeter = {Perimeter():F2}";
}

public class Circle : IShape
{
    public double Radius { get; init; }
    public double Area() => Math.PI * Radius * Radius;
    public double Perimeter() => 2 * Math.PI * Radius;
}

// Code depends on the abstraction, not the concrete type:
void PrintShape(IShape shape) => Console.WriteLine(shape.Describe());
PrintShape(new Circle { Radius = 3 });

Why default interface methods exist Before C# 8, adding a new member to a published interface was a breaking change for every implementer. Default interface methods let library authors extend an interface (e.g. adding a new LINQ-style method) without breaking existing implementations that simply inherit the default body.

Delegates, Func, Action & Predicate

A delegate is a type-safe reference to a method — effectively a type-checked function pointer. You rarely declare your own delegate type in modern C#; the BCL's generic Func/Action/Predicate families cover almost every case, and this is exactly what every LINQ operator in §4 takes as an argument. 

// Declaring your own delegate type (uncommon today, but this is what a delegate IS)
public delegate int Operation(int a, int b);
Operation add = (a, b) => a + b;
int result = add(2, 3);   // 5 — invoking the method through the delegate

// The built-in generic delegates cover almost everything in practice:
Func<int, int, int> multiply = (a, b) => a * b;     // has a return value
Action<string> log = msg => Console.WriteLine(msg); // no return value (void)
Predicate<int> isEven = n => n % 2 == 0;             // returns bool — used by List<T>.Find/FindAll

var evens = new List<int> { 1, 2, 3, 4 }.FindAll(isEven);
TypeSignature shapeTypical use
Func<T1,...,TResult>Takes 0-16 params, returns TResultLINQ projections/predicates, any "compute and return a value" callback
Action<T1,...>Takes 0-16 params, returns voidCallbacks/handlers that perform a side effect
Predicate<T>bool Predicate(T obj)Legacy List<T> methods (Find, RemoveAll) — Func<T,bool> is the modern equivalent used everywhere else, including LINQ's Where
Where this goes next A delegate variable can hold more than one method at once (a multicast delegate) — that's the mechanism C#'s event keyword builds on, and it's covered in depth in §7 alongside variance and expression trees.

Exception handling

try
{
    ProcessOrder(order);
}
catch (ValidationException ex) when (ex.Severity == Severity.Warning)
{
    // exception filter: only catches when the "when" predicate is true —
    // the exception keeps its original stack trace if the filter fails
    Log.Warn(ex.Message);
}
catch (ValidationException ex)
{
    throw new OrderProcessingException("Order failed validation", ex); // wrap, preserve inner exception
}
finally
{
    connection.Dispose();   // always runs, even if the catch block re-throws
}
throw; vs throw ex; throw; re-throws and preserves the original stack trace. throw ex; resets the stack trace to the current line — almost always a bug when rethrowing inside a catch block.
Section 04

LINQ

LINQ (Language Integrated Query) lets you query in-memory collections, databases, XML, and more with the same syntax. The two things that separate a senior engineer's understanding from a junior's: deferred execution, and the IEnumerable vs IQueryable distinction.

The query pipeline

SourceIEnumerable<T>
.Where()
.Select()
.OrderBy()
.ToList()materializes — executes now
Everything before .ToList() builds up a lazy query description. No row has been touched yet — the pipeline only runs when something enumerates it (ToList, foreach, First(), etc.).

Deferred vs immediate execution

var query = orders.Where(o => o.Total > 100);   // nothing executes yet — just builds an iterator

orders.Add(new Order { Total = 500 });          // mutate the source BEFORE enumerating…

foreach (var o in query) { /* ... */ }          // …and the new order IS included here!

var list = orders.Where(o => o.Total > 100).ToList();  // executes immediately, snapshot taken now
Classic gotcha Forgetting that a query variable is a re-runnable recipe, not a result, leads to "why did this LINQ query see data I added after I built it?" — and the opposite bug: re-enumerating an expensive query twice (e.g. once for Count(), once for foreach) silently re-executes the whole pipeline (or re-hits the database) twice.

IEnumerable<T> vs IQueryable<T>

IEnumerable<T>IQueryable<T>
RepresentsAn in-memory sequence (LINQ to Objects)An expression tree to be translated by a provider (LINQ to Entities/SQL)
Where filtering happensIn .NET process memoryTranslated to SQL and run in the database
Typical sourceList<T>, arrays, in-memory collectionsDbSet<T> in Entity Framework Core
Danger—Calling .ToList() too early pulls the whole table into memory before filtering
 
// BAD: .ToList() materializes ALL rows first, then filters in memory
var expensive = dbContext.Orders.ToList().Where(o => o.Total > 100);

// GOOD: filter stays part of the expression tree, translated to a SQL WHERE clause
var cheap = dbContext.Orders.Where(o => o.Total > 100).ToList();

Method syntax vs query syntax

// Method syntax (far more common in real codebases)
var result = employees.Where(e => e.Department == "Eng")
                       .OrderBy(e => e.Salary)
                       .Select(e => new { e.Name, e.Salary });

// Query syntax — sugar that compiles to the exact same method calls
var result2 = from e in employees
              where e.Department == "Eng"
              orderby e.Salary
              select new { e.Name, e.Salary };

Expression trees & PLINQ, briefly IQueryable works because a lambda can be compiled either to a delegate (executable code) or to an expression tree (a data structure describing the code) depending on context — that's the mechanism EF Core uses to turn your C# lambda into SQL. Separately, .AsParallel() (PLINQ) partitions a query across multiple cores for CPU-bound in-memory workloads — it doesn't help with I/O-bound work, which is what async/await is for (see §5).
Section 05

Multithreading, TPL & Async/Await

The most interview-tested area of .NET. The key mental model: async/await is about not blocking a thread while waiting on I/O; it is not, by itself, about running things on other threads — that's what the Task Parallel Library and Parallel/PLINQ are for.

Thread vs Task

ThreadTask
RepresentsAn actual OS threadA unit of work that may run on a pooled thread — a promise of a future result
Cost~1MB stack, expensive to createLightweight, scheduled onto the shared ThreadPool
ComposabilityManual (join, signal)await, ContinueWith, WhenAll/WhenAny
Typical use todayRare — long-lived, dedicated background workDefault for essentially everything else

The ThreadPool

Global Work QueueTasks queued here
Worker 1
Worker 2
Worker 3
Worker N
The pool grows/shrinks based on load. Blocking a pool thread (e.g. calling .Result synchronously) starves the pool — that thread can't pick up other queued work while it waits.

What async/await actually compiles to

The compiler rewrites an async method into a state machine: each await becomes a suspend point. When the awaited task isn't finished yet, the method returns control to its caller immediately — the calling thread is freed to do other work — and a continuation is registered to resume the state machine (potentially on a different pooled thread) once the awaited operation completes. 

public async Task<Order> GetOrderAsync(int id)
{
    var order = await _db.Orders.FindAsync(id);   // suspend point 1 — thread released while DB I/O runs
    var pricing = await _pricingApi.GetAsync(order.SkuId); // suspend point 2
    order.Total = pricing.Price;
    return order;
}

SynchronizationContext & ConfigureAwait

UI apps (WPF/WinForms)
await someTask;
Continuation posted back tothe captured UI SynchronizationContext
Resumes on the UI threadsafe to touch controls
ASP.NET Core / libraries
await someTask.ConfigureAwait(false);
No context to return to
Resumes on any pool threadavoids a pointless context hop
The classic deadlock In a UI or old ASP.NET (System.Web) app, calling .Result or .Wait() synchronously on the UI/request thread blocks that thread while it waits for the continuation — but the continuation needs to resume on that exact same captured context, which is busy blocking. Deadlock. Fix: await all the way up the call stack ("async all the way"), or add ConfigureAwait(false) in library code that doesn't need the original context. Note: ASP.NET Core has no SynchronizationContext at all, so this specific deadlock mostly disappeared there — but blocking still starves the thread pool under load.

Parallel.For / PLINQ & combinators

Section 06

Advanced .NET Concepts

The runtime and hosting mechanics that separate "I can write C#" from "I understand what my C# is actually doing to memory, threads, and the process."

Garbage collection & generations

Gen 0new objects, collected constantly, cheap
Gen 1survived one collection — buffer zone
Gen 2long-lived objects, expensive full collection
LOH — Large Object Heapobjects ≥ 85,000 bytes, collected with Gen 2

The GC is generational because most objects die young (the "generational hypothesis"). Gen 0 collections are extremely fast; objects that survive get promoted, so the GC spends effort proportional to how long-lived an object turns out to be. Workstation GC optimizes for low latency on a client machine; Server GC (default for ASP.NET Core) uses per-core heaps for higher throughput under concurrent load.

IDisposable, using, and finalizers

public sealed class FileWriterWrapper : IDisposable
{
    private readonly FileStream _stream;
    private bool _disposed;

    public FileWriterWrapper(string path) => _stream = File.OpenWrite(path);

    public void Dispose()
    {
        if (_disposed) return;
        _stream.Dispose();       // release the unmanaged file handle deterministically
        _disposed = true;
        GC.SuppressFinalize(this); // no finalizer needed once explicitly disposed
    }
}

using var writer = new FileWriterWrapper("out.txt"); // Dispose() called automatically at scope exit
GC ≠ resource cleanup The GC only reclaims managed memory. File handles, sockets, DB connections, and other unmanaged/OS resources need deterministic cleanup via IDisposable — relying on a finalizer alone means the resource is held until the next Gen 2 collection, which is unpredictable and slow.

Span<T> and Memory<T>

ReadOnlySpan<char> span = "Hello, World".AsSpan(7, 5); // "World" — no allocation, no copy
int total = ParseInts(numberString.AsSpan());              // parse directly over a slice

Span<T> is a stack-only (ref struct) view over contiguous memory (array, string, stackalloc'd buffer) that lets you slice and parse without allocating new arrays/substrings — critical in high-throughput parsing (JSON, HTTP) code paths. Memory<T> is the heap-allowed counterpart, usable in async methods and fields where a ref struct can't go.

Reflection, attributes & configuration

  • Reflection inspects types/members at runtime — powers serializers, DI containers, and ORMs, at a real perf cost versus compiled code.
  • Attributes ([Required], [JsonPropertyName]) attach declarative metadata that reflection-based frameworks read.
  • Options pattern (IOptions<T> / IOptionsSnapshot<T>) binds strongly-typed settings from appsettings.json, env vars, and secrets, with IOptionsSnapshot supporting per-request reload.
  • Source generators (e.g. System.Text.Json's source-gen serializer) do at compile time what reflection used to do at runtime — trading flexibility for startup speed and NativeAOT compatibility.

Generics & variance

public interface IProducer<out T>   { T Produce(); }          // covariant — can widen the return type

IProducer<string> strings = ...;

Array covariance is a trap string[] is implicitly convertible to object[] (arrays are covariant), but this is not type-safe: object[] arr = new string[3]; arr[0] = 42; compiles but throws ArrayTypeMismatchException at runtime. Orleans Framework

Microsoft Orleans is a virtual actor model framework for building distributed, stateful services without hand-rolling distributed locks, sharding, or cache invalidation. It was built at Microsoft Research for Halo's cloud services and now powers parts of Azure, Xbox, and Skype's backend.

The virtual actor model

A grain is Orleans's unit of state + behavior — conceptually always "existing" (virtual), regardless of whether it's currently loaded in memory anywhere. You never explicitly create or destroy a grain, and you never manually decide which silo hosts it — the runtime activates it on-demand, on whichever silo makes sense, and deactivates it after idling. This is the key difference from the classic actor model (like Akka), where you explicitly manage actor lifecycle.

Not activatedlogically "exists" but no memory footprint
First call arrivesruntime activates it on a silo
Active in memoryprocesses calls one at a time
Idle timeoutstate persisted, then deactivated
Why no locks inside a grain Orleans guarantees single-threaded, turn-based execution per grain activation — the runtime never lets two calls run concurrently against the same grain instance. That single guarantee eliminates the entire class of race conditions and manual locking you'd otherwise need for per-entity state (e.g. a player's inventory, a shopping cart) in a distributed system.

A grain, end to end

public interface IPlayerGrain : IGrainWithIntegerKey
{
    Task<int> GetScoreAsync();
    Task AddScoreAsync(int delta);
}

public class PlayerGrain : Grain, IPlayerGrain
{
    private readonly IPersistentState<PlayerState> _state;
    public PlayerGrain([PersistentState("player")] IPersistentState<PlayerState> state) => _state = state;

    public Task<int> GetScoreAsync() => Task.FromResult(_state.State.Score);

    public async Task AddScoreAsync(int delta)
    {
        _state.State.Score += delta;
        await _state.WriteStateAsync();   // persisted via the configured storage provider
    }
}

// Calling it — grain "42" is transparently activated wherever the runtime decides to place it
var player = client.GetGrain<IPlayerGrain>(42);
await player.AddScoreAsync(10);

Reminders vs Timers

TimerReminder
DurabilityIn-memory only — lost if the grain deactivatesPersisted, survives deactivation and silo restarts

Streams add a pub/sub layer on top of grains for event-driven pipelines without every producer/consumer needing a direct grain reference.

Orleans vs "just microservices on Kubernetes" Orleans shines when your domain is naturally entity-per-actor with per-entity state (games, IoT device twins, per-user session state, digital twins) and you want that state held in memory close to the logic instead of round-tripping to a database on every call. It's not a replacement for service boundaries at the macro-architecture level — teams commonly run an Orleans cluster as one stateful service within a broader microservice/K8s estate.
Section 09

OOP Principles & SOLID

The four pillars aren't academic trivia — each maps to a concrete C# language feature, and SOLID is the set of principles that keeps a large C# codebase changeable over years rather than years-old and fragile.

The four pillars

Encapsulation

Hide internal state behind a controlled surface. In C#: private fields + public properties/methods that enforce invariants.

Abstraction

Expose what without how. In C#: interfaces and abstract classes define a contract; callers depend on IRepository, not SqlRepository.

Inheritance

Reuse and specialize behavior via a base type. In C#: class Dog : Animal; overusing it creates rigid hierarchies — prefer composition when there's no true is-a relationship.

Polymorphism

One interface, many implementations, resolved at runtime. In C#: virtual/override (runtime dispatch) vs method overloading (compile-time dispatch — a different, weaker form).

Runtime polymorphism in practice

Animalvirtual Speak()
Dogoverride Speak() → "Woof"
Catoverride Speak() → "Meow"
List<Animal> animals = new() { new Dog(), new Cat() };
foreach (var a in animals) a.Speak(); // dispatches to the ACTUAL runtime type via the vtable, not the declared type

SOLID

PrincipleIn one lineC# smell it prevents
Single ResponsibilityA class should have one reason to changeA UserService that also formats emails and writes logs
Open/ClosedOpen for extension, closed for modificationA giant switch on a type enum that grows every sprint — use polymorphism/strategy instead
Liskov SubstitutionSubtypes must be usable wherever the base type is expectedA Square : Rectangle that overrides SetWidth in a way that breaks callers expecting Rectangle semantics

Composition over inheritance When you find yourself asking "is a Penguin really-and-truly a Bird if it can't Fly()?", that's the Liskov principle telling you inheritance is the wrong tool. Injecting an IFlightBehavior strategy composed into the object is usually more robust than deepening a class hierarchy to work around the exception.

SignalR

ASP.NET Core SignalR is a library for real-time, bidirectional communication between server and client — the server can push to connected clients the instant something happens, instead of clients polling for updates.

Transport negotiation

Client connects
1. WebSocketspreferred — full duplex, lowest overhead
2. Server-Sent Eventsfallback — server→client stream over HTTP
3. Long Pollinglast resort — works through almost any proxy

SignalR negotiates the best available transport automatically and falls back down this list transparently if a proxy or firewall blocks the better options.

A minimal hub

public class ChatHub : Hub
{
    public async Task SendMessage(string user, string message) =>
        await Clients.All.SendAsync("ReceiveMessage", user, message);

    public async Task JoinRoom(string room) =>
        await Groups.AddToGroupAsync(Context.ConnectionId, room);
}

// Program.cs
app.MapHub<ChatHub>("/chatHub");
// JS client
const connection = new signalR.HubConnectionBuilder().withUrl("/chatHub").build();
connection.on("ReceiveMessage", (user, msg) => appendToChat(user, msg));
await connection.start();
await connection.invoke("SendMessage", "Alice", "hello");

Groups & users

  • Connections — one per physical client connection (a user with two tabs open has two).
  • Groups — server-managed named sets of connections (Clients.Group("room-42")) — no client-side awareness needed.
  • Users — Clients.User(userId) targets every connection belonging to one authenticated identity, across devices/tabs.

Scaling out

Server Aholds Client 1's connection
Server Bholds Client 2's connection
BackplaneRedis / Azure SignalR Service
A single server only knows about its own connections. Once you scale to N instances behind a load balancer, Server A has no way to reach Client 2 directly — every server publishes outgoing messages to the backplane, and every server subscribes to it, so a broadcast reaches connections regardless of which instance they landed on.
Sticky sessions still matter Because a client's WebSocket connection is pinned to whichever server accepted it, the load balancer needs sticky sessions (or you use the managed Azure SignalR Service, which removes this constraint entirely by decoupling connection management from your app servers).

Section 11

Advanced Interview Questions

The questions that actually separate a mid-level from a senior C#/.NET engineer — with the reasoning interviewers are listening for, not just the one-liner answer.

Q1. Why is async void dangerous, and when is it the right choice?

Exceptions thrown inside an async void method can't be awaited or caught by the caller — they're raised directly on the SynchronizationContext, which typically crashes the process. It also can't be composed with Task.WhenAll or awaited. The one legitimate use is top-level UI event handlers (button.Click) which must return void to match the delegate signature — everywhere else, return Task.

Q2. Where exactly does a "filter after materialize" bug bite with EF Core?

var big = dbContext.Orders.ToList().Where(o => o.Total > 100); // pulls EVERY row into memory first

Because ToList() is called before Where, the entire table is materialized in-process and the filter runs in C#, not SQL — on a large table this is a production incident waiting to happen. The fix is ordering: keep everything as IQueryable until the final materialization call.

Q3. When would you choose a struct over a class, and what's the cost if you get it wrong?

Prefer a struct for small (rule of thumb: ≤ 16 bytes), immutable, short-lived, frequently-created value-like data (a Point, a Money amount) — it avoids heap allocation and GC pressure. Get it wrong (a large mutable struct passed around by value) and you pay for silent, expensive copies on every assignment/parameter pass, plus surprising "I mutated it but the original didn't change" bugs. A readonly struct prevents the latter by making mutation a compile error.

Q4. Walk through exactly why .Result deadlocks a UI thread.

Calling an async method from the UI thread and immediately blocking on .Result holds the UI thread hostage. The awaited task's continuation was captured to resume on that same UI SynchronizationContext — but the UI thread is now blocked waiting for .Result, so the continuation can never run, so .Result never returns. Fix: await the whole way up, or use ConfigureAwait(false) in library code so the continuation doesn't need the original context at all.

Q5. Why can two objects be != by reference but "equal" for your business logic, and what breaks if you override Equals without GetHashCode?

Default reference equality compares identity, not content — two separate Money(100, "USD") objects are different references even though they represent the same value. If you override Equals to compare values but leave the inherited GetHashCode (identity-based) untouched, you violate the contract that equal objects must have equal hash codes — the object will silently fail to be found in a Dictionary/HashSet even though Equals says it matches an existing key.

Q6. .NET has a garbage collector — how do memory leaks still happen?

The GC only reclaims objects with no reachable reference. The most common real leak: a long-lived publisher (often a singleton or static event) holding a subscription to a short-lived object's event handler — the subscriber can never be collected because the publisher's invocation list still references it. Other culprits: static collections that only ever grow, and captured closures in cached delegates holding onto large objects indirectly.

Q7. Give an example where array covariance causes a runtime exception that generics would have caught at compile time.

object[] objects = new string[3];   // legal — arrays are covariant
objects[0] = 42;                    // compiles, throws ArrayTypeMismatchException at runtime

List<object> list = new List<string>(); // COMPILE ERROR — generics are invariant by default, caught immediately

Q8. How does Orleans avoid the race conditions a normal multi-threaded service would need locks for?

Every grain activation processes one request at a time by runtime guarantee — Orleans serializes calls into a single-threaded turn per activation, so there's never concurrent mutation of a grain's own state to guard against. The trade-off is you must not block synchronously inside a grain method (it stalls that grain's entire turn queue) and cross-grain calls should go through grain references, not shared mutable objects.

Q9. A SignalR chat app works locally but messages don't reach all clients once you scale to 3 instances behind a load balancer — why, and how do you fix it?

Each server instance only tracks the connections it physically accepted; broadcasting to "all clients" from Server A never reaches clients connected to Server B or C. The fix is a backplane (Redis, SQL Server, or the managed Azure SignalR Service) that every instance publishes to and subscribes from, so a broadcast fans out across the whole cluster regardless of which instance a client landed on.

Q10. Task.Run vs Task.Factory.StartNew — what's the difference in their defaults, and why does it matter?

Task.Run is effectively a safe-default shorthand: it always schedules to the thread pool and, if given an async delegate, automatically unwraps the outer/inner task so awaiting it awaits actual completion. Task.Factory.StartNew exposes more knobs (custom scheduler, creation options) but does not unwrap a Task<Task> automatically — awaiting it without .Unwrap() gives you the outer task's completion (scheduling), not the inner work's completion, a classic subtle bug when someone "upgrades" old StartNew code to be async.

Q11. What's the practical difference between .NET Standard, framework-dependent deployment, and NativeAOT when someone asks "how do I ship this?"

.NET Standard is a compile-time contract for sharing libraries across runtimes — it says nothing about deployment. Framework-dependent deployment ships just your app, relying on a shared runtime already installed on the target machine (smaller artifact, requires runtime provisioning). Self-contained deployment bundles the runtime with your app (larger, no external dependency). NativeAOT goes further and compiles everything ahead-of-time into one native binary with no JIT at all — fastest startup and lowest memory, at the cost of losing runtime reflection-heavy features (so some serializers/DI patterns need source-generator equivalents).

Q12. Why does IEnumerable<out T> compile but IList<out T> wouldn't (if you tried to mark it covariant)?

Covariance is only sound for interfaces that exclusively produce T (methods that return T, never accept it as an input) — that's exactly IEnumerable<T>'s shape (just GetEnumerator). IList<T> has Add(T item) — an input position — so allowing IList<object> x = new List<string>() would let you call x.Add(42) against a real List<string>, which is exactly the unsound scenario array covariance allows (Q7) and the compiler correctly refuses to permit for generic interfaces.
