7. FastAPI: Publishing Metrics for Autoscaling

This section covers how to instrument a FastAPI application to expose Prometheus metrics, which can then drive KEDA-based autoscaling in OpenShift.

7.1 Option A: Instrument FastAPI with Prometheus

The prometheus-fastapi-instrumentator library automatically adds Prometheus metrics to your FastAPI application with minimal code changes.

Step 1: Install the Library

pip install prometheus-fastapi-instrumentator

Step 2: Instrument Your App

from fastapi import FastAPI
from prometheus_fastapi_instrumentator import Instrumentator
app = FastAPI(title="My API")
# Create and configure instrumentator
instrumentator = Instrumentator(
should_group_status_codes=True,
should_ignore_untemplated=True,
excluded_handlers=["/healthz", "/readyz", "/metrics"],
)
instrumentator.instrument(app)
# Expose /metrics endpoint on startup
@app.on_event("startup")
async def _startup():
instrumentator.expose(app, endpoint="/metrics", include_in_schema=False)
@app.get("/")
async def root():
return {"message": "Hello World"}
@app.get("/items/{item_id}")
async def read_item(item_id: int):
return {"item_id": item_id}

This automatically exposes at /metrics:

  • http_requests_total: Counter with labels: handler, status, method.
  • http_request_duration_seconds: Histogram of request latencies.
  • http_request_size_bytes: Summary of incoming request sizes.
  • http_response_size_bytes: Summary of outgoing response sizes.

Step 3: Custom Business Metrics (Optional)

from prometheus_client import Counter, Histogram, Gauge
# Custom business metrics
orders_processed = Counter(
'orders_processed_total',
'Total orders processed',
['order_type']
)
active_connections = Gauge(
'active_websocket_connections',
'Number of active WebSocket connections'
)
# Use in your endpoints
@app.post("/orders")
async def create_order(order: OrderModel):
orders_processed.labels(order_type=order.type).inc()
return process_order(order)

Step 4: ServiceMonitor (Tell Prometheus to Scrape)

# Enable user workload monitoring (one-time, cluster admin)
apiVersion: v1
kind: ConfigMap
metadata:
name: cluster-monitoring-config
namespace: openshift-monitoring
data:
config.yaml: |
enableUserWorkload: true
---
# ServiceMonitor for your FastAPI app
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
name: my-api-monitor
labels:
app: my-api
spec:
selector:
matchLabels:
app: my-api
endpoints:
- port: http
path: /metrics
interval: 15s

Step 5: KEDA ScaledObject

Now connect KEDA to the Prometheus metrics to autoscale:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
name: my-api-scaler
spec:
scaleTargetRef:
name: my-api
minReplicaCount: 1
maxReplicaCount: 15
triggers:
- type: prometheus
metadata:
serverAddress: https://thanos-querier.openshift-monitoring.svc.cluster.local:9092
query: |
sum(rate(http_requests_total{namespace="my-ns",service="my-api"}[2m]))
threshold: "50"
authModes: "bearer"
authenticationRef:
name: keda-trigger-auth-prometheus

7.2 Option B: Autoscale WITHOUT Code Changes

If you cannot modify your FastAPI application code, you have three viable approaches:

Approach 1: HPA on CPU (Indirect Traffic Proxy)

More HTTP traffic naturally causes higher CPU usage. HPA scales on CPU utilisation as a proxy for traffic load. No code changes required — just set resource requests on your pods.

# Just set resource requests and create HPA
oc autoscale deployment/my-api --min=2 --max=10 --cpu-percent=60

Pros: Simplest setup. No operators needed beyond default. Cons: Indirect — CPU is not always proportional to traffic (e.g., I/O-bound APIs). Cannot scale to zero.

Approach 2: Knative Serverless (Concurrency-Based)

Deploy your FastAPI as a Knative Service. Knative counts concurrent requests externally — no /metrics endpoint needed. Supports scale to zero.

apiVersion: serving.knative.dev/v1
kind: Service
metadata:
name: my-api
spec:
template:
metadata:
annotations:
autoscaling.knative.dev/target: "30"
autoscaling.knative.dev/metric: "concurrency"
spec:
containers:
- image: my-registry/my-api:latest
ports:
- containerPort: 8000

Pros: True traffic-based scaling. Scale to zero. No code changes. Cons: Requires OpenShift Serverless Operator. Cold-start latency when scaling from zero.

Approach 3: KEDA with Istio/Service Mesh Metrics

If Service Mesh is deployed, the Envoy sidecar already collects request metrics (istio_requests_total). KEDA can scale on these without any changes to your application.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
name: my-api-mesh-scaler
spec:
scaleTargetRef:
name: my-api
minReplicaCount: 1
maxReplicaCount: 15
triggers:
- type: prometheus
metadata:
serverAddress: https://thanos-querier.openshift-monitoring.svc.cluster.local:9092
query: |
sum(rate(istio_requests_total{destination_service_name="my-api"}[2m]))
threshold: "100"
authModes: "bearer"
authenticationRef:
name: keda-trigger-auth-prometheus
