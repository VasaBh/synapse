Section 01

Core Concepts & Trade-offs

A system is data-intensive (rather than compute-intensive) when the hard problems are volume, velocity, variety, and correctness of data — not raw CPU cycles. Market data platforms are a canonical example: millions of price updates per second, decades of history to retain, dozens of source formats, and consumers (risk, trading, settlement) who cannot tolerate a wrong number.

Four axes every data-intensive design decision sits on: Throughput ◄──────────────────────────────► Latency (batch, EOD close-of-day pricing) (intraday ticks, sub-second) Consistency ◄──────────────────────────────► Availability (golden settlement price — must be right) (best-effort live quote feed) Durability ◄──────────────────────────────► Cost (regulatory retention, replay for audit) (hot storage is expensive) Schema rigidity ◄──────────────────────────► Source variety (one canonical model) (Bloomberg ≠ Refinitiv ≠ ZEMA)

Batch, Streaming, and the Hybrid Middle Ground

ArchitectureModelWhere it fits in market data
Batch (classic ETL)Extract → Transform → Load on a scheduleEOD settlement prices, reference/static data, regulatory reporting extracts
Streaming (event-driven)Continuous processing of an unbounded event logIntraday ticks/quotes, real-time curve rebuilds, alerting
Lambda architectureSeparate batch layer (accuracy) + speed layer (freshness), merged at query timeIntraday "live" price backed by a nightly-reconciled EOD layer that is the audit source of truth
Kappa architectureSingle streaming pipeline; batch is just "replay the log from offset 0"Simpler ops when EOD can be derived as a snapshot of the same event stream (e.g., last tick before market close)
Design principle used throughout this guide Treat every incoming price as an immutable, timestamped event appended to a log (Kafka). EOD is a materialized view of that log ("last valid tick per instrument before the close snapshot time"); intraday is the log consumed live. This is a Kappa-leaning design — it avoids maintaining two divergent codepaths for "the same number computed two ways," which is the single most common source of EOD-vs-intraday discrepancies in real trading desks.

Reference Architecture

Figure 1 — Every vendor is one adapter, every consumer is one API client; nothing in between knows which vendor a price came from.

Why this shape, not a point-to-point integration per consumer Every new vendor is one adapter; every new consumer is one API client — neither touches the other. Without the ingestion bus and canonical schema in the middle, N sources × M consumers becomes N×M bespoke integrations, and a single bad Bloomberg tick has no single place to be caught before it reaches a trader's screen.

Source Adapter Layer

The single most important adaptability decision: no downstream component should know which vendor a price came from. Every adapter's job is to translate a vendor-specific wire format into one canonical event schema.

Adapter Interface (Plugin Pattern)

class MarketDataAdapter(ABC):
    """One implementation per vendor. Adding ZEMA v2 later = one new class,
    zero changes to ingestion, validation, storage, or API layers."""

    @abstractmethod
    def connect(self, config: SourceConfig) -> None: ...

    @abstractmethod
    def subscribe(self, instruments: list[str]) -> None: ...

    @abstractmethod
    def normalize(self, raw_message: bytes) -> CanonicalEvent:
        """Vendor wire format -> canonical schema. All symbology mapping,
        unit conversion, and field-entitlement checks happen here."""

    def publish(self, event: CanonicalEvent, producer: KafkaProducer) -> None:
        topic = f"md.raw.{event.commodity.lower()}"
        producer.send(topic, key=event.instrument_id, value=event.to_json())


class BloombergAdapter(MarketDataAdapter):
    def normalize(self, raw_message: bytes) -> CanonicalEvent:
        msg = blpapi.parse(raw_message)
        return CanonicalEvent(
            instrument_id=symbology.to_internal("BLOOMBERG", msg.security),
            price=msg.get("LAST_PRICE"),
            unit=unit_map.resolve(msg.security),
            exchange_ts=msg.get("TRADE_UPDATE_STAMP_RT"),
            source="BLOOMBERG",
        )

class ZemaAdapter(MarketDataAdapter):
    def normalize(self, raw_message: bytes) -> CanonicalEvent:
        row = json.loads(raw_message)
        return CanonicalEvent(
            instrument_id=symbology.to_internal("ZEMA", row["curveId"]),
            price=row["value"],
            unit=row["uom"],
            exchange_ts=row["asOfDate"] + "T00:00:00Z",
            event_type="CURVE_POINT",
            source="ZEMA",
        )
Symbology is the hidden project inside this project Bloomberg tickers, Refinitiv RICs, ZEMA curve IDs, and exchange product codes never agree. Build a dedicated symbology/instrument master service (internal ID ↔ every vendor ID) as its own component with its own reference-data lifecycle — do not let mapping logic leak into individual adapters, or every adapter re-solves the same problem differently.
Section 04

ETL: EOD Batch vs. Intraday Streaming

EOD and intraday are not two products — they're two consumption modes of the same canonical event log, with different SLAs, volumes, and correctness bars.

Figure 2 — Kappa-style: EOD is a materialized snapshot of the same validated log the intraday path consumes.

IntradayEOD
Latency target< 250ms source-to-screenAvailable within minutes of close; correctness > speed
VolumeVery high (every tick), bursty at open/closeLow — one settlement record per instrument per day
OrderingPer-instrument order matters; global order usually doesn'tMust reflect the single official close-of-day snapshot
Replay needShort window (minutes) for recovery/reconnectFull history replay for audit, backtesting, restatement
Failure toleranceCan drop/skip stale ticks and self-heal on next updateCannot silently miss a value — must alert and backfill

Intraday Streaming Pipeline

# Kafka Streams / Flink-style job — conceptually identical in either engine
def build_intraday_pipeline():
    raw = source_topics("md.raw.*")                  # from adapters, Section 03

    validated, quarantined = raw.branch(
        predicate=lambda e: validation_engine.check(e).passed
    )

    quarantined.to_topic("md.quarantine")             # Section 06 exception flow

    enriched = (validated
        .map(enrich_with_reference_data)               # contract specs, FX rate
        .map(compute_derived_fields))                   # spreads, rolling VWAP

    # Windowed aggregation for OHLC bars, keyed per instrument
    bars = enriched.group_by_key().window(TumblingWindow.minutes(1)).aggregate(ohlc)

    enriched.to_topic("md.intraday.ticks")             # low-latency live consumers
    bars.to_topic("md.intraday.bars")                  # charting/algos
    enriched.to_store("hot_cache")                      # Section 08 — latest-price cache
One pipeline, two views — the Kappa payoff The EOD "settle" record is produced by the same validation engine and canonical schema as the intraday tick — it's just the event where event_type == "SETTLE" or the last validated tick before the exchange's official close-snapshot time. That guarantees EOD and intraday can never silently disagree about what a raw price was — only about which snapshot in time is being shown.

Messaging & Storage Technology Choices

Pick technology per data class, not one tool for everything — tick data, EOD facts, and reference data have incompatible access patterns.

Messaging Layer

OptionStrengthsWatch out forFit here
Apache KafkaOrdered log per partition, long retention, replay by offset, huge ecosystem (Kafka Streams, ksqlDB, Connect)Ops overhead if self-managed; partition key design determines ordering guaranteesChosen backbone — partition by instrument_id so per-instrument order is preserved
Solace / IBM MQBattle-tested in banks, strong topic-based entitlements, low-latency binary transportLess natural log-replay model than Kafka; licensing costCommon where it's already the firm's standard market-data bus — fine as the transport under the same canonical-schema design
Cloud-native (Kinesis / Pub/Sub)Zero ops, elastic scalingShorter retention windows, per-vendor semantics differ from KafkaGood fit if already all-in on one cloud and volumes are moderate
PulsarTiered storage built in (hot BookKeeper + cold object storage), multi-tenancySmaller talent pool / ecosystem than KafkaWorth it specifically for the hot/cold tiering story if operating at very large tick volumes

Decision rule of thumb If a query asks "what is it right now" → hot key-value cache. If it asks "give me every tick between two timestamps" → time-series engine. If it asks "give me the settle for every day last quarter" → columnar warehouse. Using one general-purpose database for all three is the most common over-engineering-by-simplification mistake in market data platforms.

Section 06

Data Validation Engine

No price reaches a consumer, a curve build, or the golden-source merge without passing through a rules engine. Design it as a pluggable, configurable pipeline of independent checks — not a monolithic if ladder — so new rules (a new commodity, a new source's quirks) can be added without redeploying the whole pipeline.

Validation Categories

Schema & type

Required fields present, correct types, enum values (currency, unit) are in the known set.

Range / sanity

Price within a configurable band vs. last known good value or a static bound (e.g., crude oil futures > -$100 and < $500/bbl).

Spike / outlier detection

Move exceeds N standard deviations or N% in one tick — flag, don't necessarily reject (real market gaps happen).

Staleness / timeliness

No update received within expected interval for a liquid instrument during market hours → feed-health alert, not a per-tick rejection.

Referential integrity

Instrument ID exists in the instrument master; contract hasn't already expired; currency/unit pair is valid for that commodity.

Cross-source reconciliation

If two sources report the same instrument, do they agree within tolerance? Disagreement routes to Section 07's golden-source logic.

Validation & Exception Flow

Figure 4 — Every event is scored by the whole chain; the worst severity decides where it goes, and nothing is ever silently discarded.

Rule Engine Design

class ValidationRule(ABC):
    severity: Literal["REJECT", "QUARANTINE", "WARN"]

    @abstractmethod
    def check(self, event: CanonicalEvent, context: ValidationContext) -> RuleResult: ...


class PriceRangeRule(ValidationRule):
    severity = "QUARANTINE"
    def check(self, event, context):
        bounds = context.static_data.price_bounds(event.instrument_id)
        if not (bounds.min <= event.price <= bounds.max):
            return RuleResult(passed=False, reason=f"price {event.price} outside [{bounds.min},{bounds.max}]")
        return RuleResult(passed=True)


class SpikeDetectionRule(ValidationRule):
    severity = "WARN"
    def check(self, event, context):
        last = context.last_good_price(event.instrument_id)
        if last and abs(event.price - last.price) / last.price > context.config.spike_threshold_pct:
            return RuleResult(passed=False, reason="move exceeds spike threshold", auto_action="FLAG_FOR_REVIEW")
        return RuleResult(passed=True)


class ValidationEngine:
    def __init__(self, rules: list[ValidationRule]):
        self.rules = rules                      # order/config-driven, per commodity class

    def validate(self, event: CanonicalEvent, context: ValidationContext) -> ValidationOutcome:
        results = [rule.check(event, context) for rule in self.rules]
        failures = [r for r in results if not r.passed]
        if any(r.severity == "REJECT" for r in failures):
            return ValidationOutcome(status="REJECTED", event=event, failures=failures)
        if any(r.severity == "QUARANTINE" for r in failures):
            return ValidationOutcome(status="QUARANTINED", event=event, failures=failures)
        return ValidationOutcome(status="PASSED", event=event.with_quality("VALIDATED"), failures=failures)

Sample Rule Catalog (config-driven)

Rules live in versioned config, not code. Each has an id, a scope (applies_to), a severity, and parameters — so tightening the crude-oil spike threshold before an OPEC meeting is a config change with an audit trail, not a deployment.

Henry Hub settle 2.90 → 3.42 (+18 %) after a hurricaneSPIKE_002QUARANTINED → approved in 4 minReal market move. The 15 % threshold is deliberately tight for settles because a wrong settle is far costlier than a 4-minute review
Never silently drop a quarantined price Every quarantined or rejected event is retained (dead-letter topic + audit log) even if it never reaches consumers. In a regulated market data pipeline, "we discarded a bad tick" must always be reconstructable after the fact — silent drops are an audit failure waiting to happen.
Section 07

Golden Source & Multi-Source Reconciliation

When Bloomberg, Refinitiv, and the exchange all report a price for the same instrument and they disagree — even slightly — something has to decide which one is "the" price. That decision must be config-driven, auditable, and source-agnostic so a new vendor slots in without code changes.

Source Priority (Waterfall) Configuration

# golden_source_config.yaml — adding a new vendor = adding a block here, no code change
CRUDE_OIL:
  settlement:
    priority: [CME_DIRECT, BLOOMBERG, REFINITIV, ZEMA]
    tolerance_pct: 0.05          # sources within 0.05% are considered "agreeing"
    on_disagreement: QUARANTINE_FOR_REVIEW
  intraday:
    priority: [BLOOMBERG, REFINITIV]
    tolerance_pct: 0.15
    on_disagreement: USE_HIGHEST_PRIORITY_AND_FLAG

NATURAL_GAS:
  settlement:
    priority: [CME_DIRECT, ZEMA, BLOOMBERG]
    tolerance_pct: 0.10
    on_disagreement: QUARANTINE_FOR_REVIEW

Caching Strategy by Endpoint

Figure 5 — Reads go through one gateway and one cache; the validation engine is the only writer, so the cache can never hold an unvalidated price.

def get_latest_price(instrument_id: str) -> Price:
    cached = redis.get(f"price:latest:{instrument_id}")
    if cached:
        return Price.from_json(cached)

    price = timeseries_db.query_latest(instrument_id)   # cache-aside fallback
    redis.set(f"price:latest:{instrument_id}", price.to_json(), ex=5)  # short TTL safety net
    return price

# Validation engine writes straight into the cache on every VALIDATED event —
# this is the primary update path; the 5s TTL above only guards against a
# missed write, it is not the main freshness mechanism.
def on_validated_event(event: CanonicalEvent):
    redis.set(f"price:latest:{event.instrument_id}", event.to_json())
    redis.publish(f"price:stream:{event.instrument_id}", event.to_json())

Restatement handling "Immutable" EOD caching still needs an escape hatch: exchanges occasionally restate a settlement. Model this as a new event with a restated_from pointer rather than mutating history in place, and push an explicit cache-invalidation message — this keeps the audit trail (Section 06) intact while still fixing what's served going forward.
Section 09

Scalability & Reliability

Market data platforms fail loudly and expensively when they fail quietly — a missed price is worse than a slow one. Design for horizontal scale on the ingestion side and for observability everywhere.

Scaling the Ingestion Layer

  • Run redundant feed handlers per source in active-active pairs — dedupe downstream by (source, source_native_id, exchange_ts), don't rely on a single handler instance
  • Partition Kafka topics by instrument_id so a hot instrument doesn't starve others, and consumer parallelism scales with partition count
  • Isolate the validation engine as its own scaled consumer group — it's the one component every event must pass through, so it's the natural bottleneck to watch first
  • Separate the EOD batch cluster from the intraday streaming cluster — a slow nightly backfill job should never compete for resources with live tick processing

Disaster recovery for feed connections Vendor sessions (Bloomberg B-PIPE, Refinitiv Elektron) are stateful and can drop. Design feed handlers to reconnect and resubscribe automatically, and use Kafka's retained log to backfill the gap on reconnect (replay from last committed offset) rather than treating a reconnect as "start fresh" — otherwise a 30-second network blip becomes a silent data gap.
Section 10

Interview Questions

Common system design interview questions for a market data / data-intensive platform role, with the reasoning an interviewer is listening for.

"Design a market data system that ingests from multiple vendors and serves both real-time and historical queries."

Lead with the shape, not the tools: a vendor-agnostic adapter layer normalizing to one canonical schema, an append-only event log (Kafka) as the backbone, a validation stage every event passes through before being trusted, and storage tiered by access pattern (hot cache, time-series store, columnar warehouse, cold archive) fronted by a single API layer. Naming Kafka/kdb+/Redis is good, but the interviewer is really testing whether you decouple sources from consumers and whether you have one source of truth for "what actually happened," not two divergent EOD/intraday codepaths.

"How do you handle two vendors reporting different prices for the same instrument?"

Config-driven priority waterfall per instrument class, with a tolerance check before blindly trusting the top-priority source, and human-in-the-loop review (data steward queue) when sources disagree beyond tolerance — never silently pick one and discard the disagreement without recording it. Mention the WTI negative-price case if asked why hardcoded bounds are dangerous.

"Batch or streaming for end-of-day pricing?"

The strong answer is "neither exclusively" — model EOD as a query over the same streamed, validated event log used intraday (a Kappa-style design), rather than a separate batch pipeline that re-implements validation and normalization. This avoids the classic failure mode where EOD and intraday numbers for the same instrument quietly diverge because they were computed by two different code paths.

"How would you add a new data source without disrupting the running system?"

Because sources are isolated behind an adapter interface and referenced only by symbolic priority in config (Section 07), onboarding is: implement the adapter's normalize() method, register symbology mappings, add a priority-config entry. No change to validation, storage, or the API layer — this is the concrete proof point for "the design is adaptable to new sources," which is usually exactly what the interviewer wants to hear you demonstrate, not just claim.

"Where would you put caching, and what would you never cache?"

Cache the latest-price lookup (write-through from the validation engine, short TTL as a safety net) and reference/static data (long TTL, event-invalidated) — these dominate read volume. Never cache in a way that could serve a value the validation engine hasn't yet approved, and treat "immutable" EOD caching carefully — build in an explicit invalidation path for the rare settlement restatement rather than assuming history never changes.

"Roughly how much data would 100 instruments generate, and what dominates?"

Show your assumptions out loud: ~60 liquid futures at ~5 updates/s over a 20-hour session plus ~40 slow curve points gives ≈ 22 million events/day per vendor — ≈ 2 GB/day on the bus in Avro, < 1 GB/day at rest compressed, ≈ 200 GB/year in the tick store. EOD settlements and 36-tenor curves for the same 100 instruments are under 1 GB per year all-in. Then make the two key points: tick data is > 99 % of the bytes, and Kafka is sized by the settlement-window burst (3–5 K msg/s per vendor) × retention × replication, not by the daily average.

Follow-up trap: "So intraday and EOD are basically the same pipeline?" Yes for correctness (same events, same validation, same canonical schema) — no for operations (different SLAs, different scaling profile, different failure tolerance, often different consuming clusters). A strong answer distinguishes "same data model" from "same runtime deployment," which interviewers often use to check you're not oversimplifying.
