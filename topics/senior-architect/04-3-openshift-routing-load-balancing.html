3. OPENSHIFT – ROUTING & LOAD BALANCING

3.1 OpenShift Router vs Kubernetes Ingress

FeatureOpenShift RouteKubernetes Ingress
Object typeRoute (OpenShift-native)Ingress (K8s standard)
Default controllerHAProxy RouterVarious (NGINX, Traefik, etc.)
TLS terminationEdge / Passthrough / Re-encryptTLS via Secret annotation
Weight-based routingNative (route weights)Via annotations (controller-specific)
Wildcard routesSupported nativelyController-dependent

3.2 TLS Termination Modes

  • Edge – TLS terminates at the router; internal traffic is plain HTTP
  • Passthrough – TLS passes all the way to the pod; router cannot inspect traffic
  • Re-encrypt – router terminates TLS, re-encrypts for pod; full encryption end-to-end

3.3 Service Types & Load Balancing

Service TypeScopeUse Case
ClusterIPInternal onlyService-to-service communication
NodePortExternal via node IP:portDev/test; not for production
LoadBalancerExternal via cloud LBProduction external access (cloud providers)
ExternalNameDNS aliasAccess external services via K8s DNS

Load Balancing Algorithms

  • Round Robin (default) – requests distributed evenly across pods
  • Least Connections – route to pod with fewest active connections
  • Session Affinity (Sticky Sessions) – route same client to same pod via cookie/IP hash
  • Random – useful for stateless services with unpredictable load

3.4 Traffic Splitting & Deployment Strategies

Blue-Green Deployment

  • Two identical environments (blue=live, green=new version)
  • Switch traffic by changing route target; instant rollback by switching back
  • Requires double the resources during cutover

Canary Deployment via Route Weights

  • Split traffic between stable and canary service using weight property
  • Example: 90% → stable, 10% → canary
  • Gradually shift weight as confidence grows; roll back by setting canary weight to 0

A/B Testing

  • Route specific users (by header, cookie) to different versions
  • Requires custom annotations or service mesh (Istio) for fine-grained control

3.5 Health Checks

ProbePurposeFailure Action
Liveness ProbeIs the container alive?Restart the container
Readiness ProbeIs the container ready for traffic?Remove from load balancer endpoint
Startup ProbeHas the app finished initialising?Block liveness/readiness checks

3.6 Network Policies & Security

  • Network Policies – pod-level firewall rules; whitelist ingress/egress per pod label
  • Default deny all – create explicit allow rules for each communication path
  • mTLS via Istio service mesh – encrypt and authenticate pod-to-pod traffic
  • RBAC – control who can create/modify Routes, Services, NetworkPolicies
  • SCC (Security Context Constraints) – OpenShift-specific; controls pod privileges, volume types, user IDs
💡 Interview Tip: Know the difference between Route and Ingress. OpenShift supports both, but Routes are more feature-rich and native. Explain when you'd use each.
