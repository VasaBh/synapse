5. Canary Deployments in OpenShift

A canary deployment is a progressive delivery strategy where a new version of an application is rolled out to a small percentage of production traffic first. The new version is monitored, and if it performs well, traffic is gradually increased until 100% flows to the new version. If issues are detected, the canary is rolled back with minimal user impact.

Canary Deployment Traffic Flow
100% traffic           90/10 split            50/50 split          100% to v2
+--------+          +--------+             +--------+           +--------+
|   v1   |    -->   | v1 90% |     -->     | v1 50% |   -->    |   v2   |
|  100%  |          | v2 10% |             | v2 50% |          |  100%  |
+--------+          +--------+             +--------+          +--------+
Phase 1             Phase 2                Phase 3              Phase 4
(before)          (canary start)         (ramping up)         (full rollout)

5.1 Method 1: Native OpenShift Routes (Simple Canary)

The simplest approach uses Route weight manipulation. No additional tooling is needed beyond the oc CLI.

# Step 1: Ensure roundrobin algorithm (required for weighted backends)
oc annotate route/my-api haproxy.router.openshift.io/balance=roundrobin
# Step 2: Start canary - 95% stable, 5% canary
oc set route-backends my-api my-api-stable=95 my-api-canary=5
# Step 3: Monitor metrics, increase if healthy
oc set route-backends my-api my-api-stable=80 my-api-canary=20
# Step 4: Continue ramping
oc set route-backends my-api my-api-stable=50 my-api-canary=50
# Step 5: Full rollout
oc set route-backends my-api my-api-stable=0 my-api-canary=100
# ROLLBACK (if issues detected):
oc set route-backends my-api my-api-stable=100 my-api-canary=0

5.2 Method 2: Service Mesh (Istio) Canary

Service Mesh provides more powerful canary deployments with percentage-based traffic splitting independent of replica counts, and header-based routing for targeted testing.

Example — Percentage-based canary:

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
name: my-api
spec:
hosts:
- my-api
http:
- route:
- destination:
host: my-api
subset: stable
weight: 90
- destination:
host: my-api
subset: canary
weight: 10

Example — Header-based canary (only testers see canary):

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
name: my-api
spec:
hosts:
- my-api
http:
# Match: requests with x-canary: true header go to canary
- match:
- headers:
x-canary:
exact: "true"
route:
- destination:
host: my-api
subset: canary
# Default: everything else goes to stable
- route:
- destination:
host: my-api
subset: stable

5.3 Method 3: Argo Rollouts (Automated Canary)

Argo Rollouts automates the entire canary lifecycle. It integrates with both OpenShift Service Mesh (Istio) and native OpenShift Routes to progressively shift traffic through defined steps, with optional automated analysis and rollback.

Argo Rollouts Automated Canary Flow
Rollout      VirtualService /           Monitoring /      Decision
Controller   Route Update                Analysis
|                                         |
+--> setWeight: 10% -----> Monitor -----> OK? ---> Yes --+
|                                                        |
+--> setWeight: 30% <-----------------------------------+
|                          Monitor -----> OK? ---> Yes --+
|                                                        |
+--> setWeight: 60% <-----------------------------------+
|                          Monitor -----> OK? ---> Yes --+
|                                                        |
+--> setWeight: 100% (promote) <------------------------+
|
+--> [If FAIL at any step] --> Rollback to 0% canary

Example — Argo Rollout with Istio traffic management:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
name: my-api
spec:
replicas: 5
strategy:
canary:
canaryService: my-api-canary
stableService: my-api-stable
trafficRouting:
istio:
virtualServices:
- name: my-api-vsvc
routes:
- primary
steps:
- setWeight: 10
- pause: { duration: 5m }      # Wait 5 mins, monitor
- setWeight: 30
- pause: { duration: 5m }
- setWeight: 60
- pause: { duration: 5m }
# After final step, auto-promotes to 100%

Example — Argo Rollout with native OpenShift Routes (no Service Mesh):

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
name: my-api
spec:
strategy:
canary:
canaryService: my-api-canary
stableService: my-api-stable
trafficRouting:
plugins:
argoproj-labs/openshift:
routes:
- my-api-route
steps:
- setWeight: 20
- pause: {}                    # Pause indefinitely, manual promote
- setWeight: 40
- pause: { duration: 10 }
- setWeight: 80
- pause: { duration: 10 }
