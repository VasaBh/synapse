10. End-to-End Autoscaling Architecture

The following diagram shows how all autoscaling components work together in a production OpenShift deployment:

COMPLETE END-TO-END AUTOSCALING FLOW
[1] Traffic hits the application
|
v
[2] FastAPI exposes /metrics (http_requests_total)
OR Istio/Envoy sidecar captures istio_requests_total
OR Knative activator counts concurrent requests
|
v
[3] Prometheus scrapes metrics (via ServiceMonitor)
Stores time-series data in Thanos
|
v
[4] KEDA queries Prometheus (PromQL: rate of requests)
OR Knative Autoscaler reads concurrency from activator
OR HPA reads CPU/memory from Metrics Server
|
v
[5] Autoscaler decides: scale up or down
KEDA -> feeds external metrics -> HPA -> adjusts replicas
Knative -> directly adjusts ReplicaSet
HPA -> directly adjusts replicas
|
v
[6] New pods created, but no node has capacity?
|
v
[7] Cluster Autoscaler detects pending pods
Machine Autoscaler provisions new VM in MachineSet
New worker node joins, pods get scheduled
|
v
[8] Meanwhile, VPA monitors actual resource usage
Right-sizes CPU/memory requests for optimal efficiency
[SCALE DOWN: reverse flow]
Traffic drops -> fewer replicas needed -> pods terminated
-> nodes become underutilised -> Cluster AS removes nodes
