1. API & Traffic Load Balancing Fundamentals

1.1 What is Load Balancing?

Load balancing is the process of distributing incoming network traffic across multiple backend servers or service instances so that no single server becomes a bottleneck. In the context of APIs, every HTTP/HTTPS request hitting your API endpoint is intelligently spread across multiple replicas of your application, ensuring high availability, fault tolerance, and optimal performance.

Without load balancing, a single server handles all traffic. If that server crashes or becomes overloaded, the entire service goes down. With load balancing, if one server fails, the load balancer detects this through health checks and routes traffic only to healthy servers, providing seamless failover.

1.2 OSI Layer Classification

Load balancers operate at different layers of the OSI (Open Systems Interconnection) model. Understanding these layers is critical to choosing the right strategy:

LayerNameHow It WorksExamples
Layer 4Transport (TCP/UDP)Routes based on IP address and port number. Does not inspect packet content. Fastest.IPVS, Keepalived/LVS, HAProxy (TCP mode), AWS NLB
Layer 7Application (HTTP)Inspects HTTP headers, URL paths, cookies, and content. Enables intelligent routing decisions like path-based, header-based, and canary routing.HAProxy (HTTP mode), NGINX, Envoy Proxy, OpenShift Router, Istio VirtualService

1.3 Load Balancing Algorithms

These are the core algorithms used by load balancers to decide which backend server receives each request:

AlgorithmHow It WorksBest For
Round RobinRequests distributed sequentially to each server in order. Server 1, then 2, then 3, repeat.Servers with similar capacity. Simple, predictable distribution.
Weighted Round RobinLike round robin, but servers receive traffic proportional to their assigned weight. A server with weight 3 gets 3x more requests than weight 1.Heterogeneous server capacities. Gradual traffic shifting during deployments.
Least ConnectionsSends new requests to the server currently handling the fewest active connections.Long-lived connections like WebSockets, database connections, or LDAP sessions.
Source IP HashHashes the client IP address to deterministically map each client to a specific server. Same client always reaches the same server.Session affinity / sticky sessions without cookies. Stateful applications.
RandomRandomly selects a backend server for each request. Statistically even distribution at scale.Large-scale deployments. Default in OpenShift Router for non-passthrough routes.
Least Response TimeRoutes to the server with the fastest measured response time. Requires active monitoring.Performance-sensitive APIs. Geographically distributed backends.
