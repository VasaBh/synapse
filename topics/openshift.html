Section 01

Overview & Architecture

OpenShift Container Platform (OCP) is Red Hat's enterprise Kubernetes distribution — Kubernetes plus an opinionated developer experience, integrated CI/CD, stricter security defaults, and enterprise support. OCP 4.x is built on CoreOS and the Kubernetes Operator pattern.

OpenShift vs Vanilla Kubernetes

FeatureVanilla KubernetesOpenShift 4.x
InstallationManual / kubeadmInstaller Provisioned Infrastructure (IPI) or UPI
OSAny LinuxRHCOS (Red Hat CoreOS) — immutable, auto-updating
Container Runtimecontainerd / CRI-OCRI-O (default)
IngressNginx Ingress ControllerHAProxy-based Router + Route objects
RegistryExternalBuilt-in integrated image registry
CI/CDExternal (Jenkins, Tekton)OpenShift Pipelines (Tekton) built-in
SecurityPSA (Pod Security Admission)SCC (Security Context Constraints) — more granular
Web ConsoleDashboard (basic)Feature-rich developer + admin console
UpdatesManualCluster Version Operator (CVO) — over-the-air

Control Plane Components

API Server

Central REST endpoint for all cluster operations. Validates and persists state to etcd. All oc / kubectl commands talk here.

etcd

Distributed key-value store holding all cluster state. Typically 3 or 5 members for HA. Loss of quorum = read-only cluster.

Controller Manager

Runs reconciliation loops — ReplicaSet controller, Deployment controller, Node controller, etc. Drives actual state toward desired state.

Scheduler

Assigns pods to nodes based on resource requests, affinity/anti-affinity rules, taints/tolerations, and topology spread.

Cluster Version Operator

OpenShift-specific. Manages the lifecycle of all cluster operators and coordinates safe over-the-air updates.

Machine Config Operator

Manages RHCOS node configuration (kernel args, systemd units, files). Changes trigger a rolling node reboot.

Section 02

Pods & Containers

A Pod is the smallest deployable unit in Kubernetes — one or more containers sharing a network namespace, IPC namespace, and (optionally) storage volumes. Containers in a pod communicate via localhost and are always co-scheduled.

Pod Lifecycle

PhaseMeaning
PendingAccepted by cluster; waiting for scheduling or image pull
RunningBound to a node; at least one container is running
SucceededAll containers exited with code 0
FailedAll containers terminated; at least one exited non-zero or was killed
UnknownPod state cannot be determined (node communication lost)
CrashLoopBackOffContainer keeps crashing; kubelet backs off restarts exponentially

Pod Spec — Key Fields

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
    version: v1
spec:
  containers:
  - name: app
    image: registry.example.com/my-app:v1
    ports:
    - containerPort: 8080
    resources:
      requests:
        cpu: "250m"       # guaranteed minimum
        memory: "256Mi"
      limits:
        cpu: "500m"       # hard cap — throttled if exceeded
        memory: "512Mi"   # OOMKilled if exceeded
    env:
    - name: DB_HOST
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: host
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 15
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
  initContainers:
  - name: db-migrate
    image: registry.example.com/my-app:v1
    command: ["python", "manage.py", "migrate"]

Probes

ProbeFailure ActionUse For
livenessProbeContainer restartedDetect deadlocks, infinite loops — is the app alive?
readinessProbePod removed from Service endpointsIs the app ready to accept traffic?
startupProbeContainer restarted if not passing before failureThresholdSlow-starting apps — disables liveness until startup completes

Multi-Container Patterns

Sidecar

Extends main container. Examples: log shipper (Fluentd), service mesh proxy (Envoy/Istio), secrets agent (Vault).

Init Container

Runs to completion before app containers start. Used for DB migration, config generation, dependency checks.

Ambassador

Proxy for outbound network calls. Handles retry, timeout, circuit-breaking on behalf of the main container.

Adapter

Normalises output of the main container (e.g., converts proprietary metrics format to Prometheus exposition).

Resource Limits Are Critical in OpenShift OpenShift's LimitRange objects can enforce default requests/limits per namespace. Pods without resource requests are assigned the BestEffort QoS class and are the first to be evicted under node pressure. Always set both requests and limits.
Section 03

Deployments & DeploymentConfigs

Deployments are the standard Kubernetes workload abstraction for stateless applications. OpenShift's legacy DeploymentConfig (DC) adds image-change and config-change triggers, but Red Hat recommends migrating to standard Deployments in OCP 4.x.

Deployment vs DeploymentConfig

DeploymentDeploymentConfig (legacy)
API Groupapps/v1 (Kubernetes)apps.openshift.io/v1
Rollout controllerDeployment controller (control plane)DeploymentConfig controller (OpenShift)
Image-change triggerVia ImageStream + trigger annotationBuilt-in ImageChangeTrigger
Lifecycle hooksNot built-in (use init containers)pre/mid/post hooks supported
Recreate strategySupportedSupported
Custom strategiesNoCustom strategy image
Recommendation✓ Preferred (OCP 4.14+)Deprecated — migrate away

Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # extra pods above desired during rollout
      maxUnavailable: 0    # no downtime — all old pods stay until new are Ready
  template:
    metadata:
      labels:
        app: my-app
        version: v2
    spec:
      containers:
      - name: app
        image: registry.example.com/my-app:v2
        resources:
          requests: { cpu: 250m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }

Rollout Strategies

StrategyBehaviourDowntimeUse When
RollingUpdateGradually replaces old pods with newZero (if maxUnavailable=0)Default — stateless services
RecreateTerminates all old pods, then starts newYesSingle-instance, DB schema changes
Blue/GreenTwo full deployments; switch Service selectorZeroInstant rollback, need parallel environments
CanaryRoute a % of traffic to new version via weightsZeroValidate new version with subset of users

Rollout Commands

oc rollout status deployment/my-app          # watch rollout progress
oc rollout history deployment/my-app         # list revision history
oc rollout undo deployment/my-app            # rollback to previous revision
oc rollout undo deployment/my-app --to-revision=3
oc set image deployment/my-app app=registry.example.com/my-app:v3
oc scale deployment/my-app --replicas=5

Other Workload Types

StatefulSet

Stable pod identity and storage. Each pod gets a unique ordinal name (pod-0, pod-1) and persistent volume. Used for databases, queues, Elasticsearch.

DaemonSet

Runs one pod per node (or per selected nodes). Used for log collectors (Fluentd), monitoring agents (node-exporter), CNI plugins, storage daemons.

Job / CronJob

Run-to-completion workloads. Job: one-off tasks. CronJob: scheduled recurring tasks with standard cron syntax. Tracks completions and failures.

HorizontalPodAutoscaler

Scales replicas based on CPU, memory, or custom metrics. Works with Deployment, StatefulSet, ReplicaSet. Integrates with KEDA for event-driven scaling.

Section 04

Services & Routes

A Service provides a stable virtual IP (ClusterIP) and DNS name for a dynamic set of pods. A Route (OpenShift-specific) exposes a Service to external traffic via the cluster's HAProxy-based ingress router.

Service Types

TypeAccessibilityUse Case
ClusterIPInternal only (default)Service-to-service communication within cluster
NodePortExternal via <NodeIP>:<port> (30000–32767)Dev/test; not recommended for production in OpenShift
LoadBalancerExternal via cloud LB (AWS ELB, Azure LB)Cloud deployments needing dedicated external IP
ExternalNameCNAME to external DNSAlias external services inside the cluster
Headless (clusterIP: None)DNS returns pod IPs directlyStatefulSets, service discovery without load balancing
 
apiVersion: v1
kind: Service
metadata:
  name: my-app-svc
spec:
  selector:
    app: my-app           # routes to pods with this label
  ports:
  - name: http
    port: 80              # service port
    targetPort: 8080      # container port
  type: ClusterIP

OpenShift Routes

Routes are OpenShift's Ingress abstraction backed by HAProxy. They expose a Service at a hostname, with optional TLS termination.

apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: my-app-route
spec:
  host: my-app.apps.cluster.example.com
  to:
    kind: Service
    name: my-app-svc
    weight: 100
  port:
    targetPort: http
  tls:
    termination: edge          # edge | passthrough | reencrypt
    insecureEdgeTerminationPolicy: Redirect

TLS Termination Modes

ModeWhere TLS TerminatesTraffic to PodUse When
edgeAt the router (HAProxy)Plain HTTPApp doesn't handle TLS; cert managed at router
passthroughAt the pod (SNI routing)Encrypted (TLS)App handles its own TLS; router passes bytes through
reencryptAt router, re-encrypted to podDifferent TLS certEnd-to-end encryption with separate internal cert

DNS Resolution Inside the Cluster

# Service DNS:   <service>.<namespace>.svc.cluster.local
# Short form within same namespace: <service>

# Examples:
curl http://my-app-svc                                 # same namespace
curl http://my-app-svc.production.svc.cluster.local    # cross-namespace
curl http://my-app-svc.production                      # short cross-ns form

# StatefulSet pod DNS:
# <pod-name>.<headless-svc>.<namespace>.svc.cluster.local
# e.g.: postgres-0.postgres-headless.production.svc.cluster.local
Route vs Ingress OpenShift supports both Route (native) and Kubernetes Ingress objects. Both are handled by the OpenShift Router (HAProxy). Routes offer more features (per-route weights for canary, custom cert per route). Kubernetes Ingress is more portable across distributions.
Section 05

Storage & PVCs

Kubernetes storage decouples provisioning (PersistentVolume) from consumption (PersistentVolumeClaim). StorageClasses enable dynamic provisioning — pods request storage by size and access mode without knowing the underlying infrastructure.

Storage Object Hierarchy

StorageClass (defines provisioner + params) │ ▼ dynamic provisioning PersistentVolume (PV) — cluster-level resource │ ▼ bound (1:1) PersistentVolumeClaim (PVC) — namespace-level request │ ▼ mounted Pod (via volumes[].persistentVolumeClaim)

Access Modes

ModeShortMeaningTypical Storage
ReadWriteOnceRWOOne node can mount read-writeBlock: EBS, Ceph RBD, iSCSI
ReadOnlyManyROXMany nodes can mount read-onlyNFS, CephFS (read-only)
ReadWriteManyRWXMany nodes can mount read-writeNFS, CephFS, Azure Files
ReadWriteOncePodRWOPSingle pod only (k8s 1.22+)Block storage, strictest isolation

PVC Example

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: ocs-storagecluster-ceph-rbd   # ODF storage class
  resources:
    requests:
      storage: 50Gi
---
# Mount in a Pod
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: postgres-data
  containers:
  - name: postgres
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data

Storage Classes in OpenShift

Storage ClassProvisionerAccess ModesUse Case
ocs-storagecluster-ceph-rbdODF / Ceph RBDRWODatabases, stateful apps (block)
ocs-storagecluster-cephfsODF / CephFSRWO, RWXShared file storage, build artifacts
gp2 / gp3 (AWS)EBS CSIRWOAWS block storage
azurefileAzure File CSIRWXAzure shared file storage
local-storageLocal volumeRWOHigh-performance NVMe on bare metal

Reclaim Policies

Retain PV is not deleted when PVC is removed. Data persists. Admin must manually reclaim or delete the PV. Safe for production databases.
Delete PV and underlying storage (EBS volume, Ceph image) are deleted when PVC is deleted. Default for dynamic provisioning. Use carefully. 
# Check PVC status
oc get pvc -n production
# NAME            STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS
# postgres-data   Bound    pvc-abc1   50Gi       RWO            ceph-rbd

oc describe pvc postgres-data   # shows events, binding details
oc get pv pvc-abc1              # inspect the backing PersistentVolume
Section 06

Security & RBAC

OpenShift has a multi-layered security model: RBAC controls who can do what to Kubernetes API objects; Security Context Constraints (SCCs) control what a pod can do on the host. Understanding both is essential for production deployments.

RBAC Objects

ObjectScopeDescription
ClusterRoleCluster-wideDefines permissions (verbs on resources) across all namespaces
RoleNamespaceSame as ClusterRole but scoped to one namespace
ClusterRoleBindingCluster-wideGrants a ClusterRole to a user/group/SA cluster-wide
RoleBindingNamespaceGrants a Role (or ClusterRole) to a subject within one namespace
ServiceAccountNamespaceIdentity for pods to call the API server with least privilege
 
# Grant a user view access to a specific project
oc adm policy add-role-to-user view alice -n my-project

# Grant edit access cluster-wide
oc adm policy add-cluster-role-to-user edit bob

# Create a ServiceAccount and bind a Role
oc create serviceaccount my-app-sa -n production

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: my-app-sa-binding
  namespace: production
subjects:
- kind: ServiceAccount
  name: my-app-sa
  namespace: production
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io

Security Context Constraints (SCCs)

SCCs are OpenShift's policy engine that controls what a pod is allowed to do at the host level — more powerful than Kubernetes PodSecurityAdmission.

SCCPrivilege LevelTypical Use
restricted-v2Lowest (default)Standard application pods — no root, no host access
anyuidMediumApps needing a specific UID (e.g., most off-the-shelf images)
nonroot-v2MediumAny non-root UID; no privilege escalation
hostnetwork-v2HighPods that need to use the host's network stack
privilegedHighestFull host access; only for CNI/CSI DaemonSets, node agents
 
# Grant anyuid SCC to a ServiceAccount (allow non-root image)
oc adm policy add-scc-to-user anyuid -z my-app-sa -n production

# Check which SCC a pod is using
oc get pod my-pod -o jsonpath='{.metadata.annotations.openshift\.io/scc}'

# List all SCCs
oc get scc

Secrets Management

# Create a secret
oc create secret generic db-creds \
  --from-literal=username=admin \
  --from-literal=password=s3cr3t

# Create TLS secret from cert files
oc create secret tls my-tls-secret \
  --cert=tls.crt --key=tls.key

# Reference in a Deployment (env var)
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-creds
      key: password

# Reference as volume mount
volumes:
- name: tls
  secret:
    secretName: my-tls-secret
Secrets Are Not Secret by Default Kubernetes Secrets are base64-encoded, not encrypted, at rest by default. Enable etcd encryption at rest, use HashiCorp Vault via the Vault Agent Injector, or use OpenShift Secrets Store CSI Driver to inject secrets from an external vault into pods.
Section 07

Builds & CI/CD

OpenShift provides first-class build primitives: BuildConfigs (legacy S2I / Docker builds) and OpenShift Pipelines (Tekton-based). The integrated image registry and ImageStreams complete the inner loop of build → tag → deploy.

ImageStreams

An ImageStream is a pointer to a series of container images — an abstraction over the image registry that lets Deployments trigger automatic rollouts when a new image is pushed.

# Create ImageStream
oc create imagestream my-app

# Tag an external image into the ImageStream
oc tag docker.io/library/nginx:1.25 my-app:latest

# Trigger a Deployment on ImageStream change
oc set triggers deployment/my-app \
  --from-image=my-app:latest \
  -c app

# Import image metadata from registry
oc import-image my-app:latest --from=registry.example.com/my-app:latest --confirm

OpenShift Pipelines (Tekton)

Tekton is a Kubernetes-native CI/CD framework. Pipelines are composed of reusable Tasks, with data passed via Workspaces (PVCs) and Parameters.

Tekton ObjectDescription
TaskA sequence of Steps (each a container). Reusable unit of work.
TaskRunInstantiation of a Task with specific params and workspaces.
PipelineDAG of Tasks with shared workspaces and parameter passing.
PipelineRunInstantiation of a Pipeline. Creates TaskRuns for each Task.
WorkspaceShared storage (PVC, ConfigMap, Secret) between Tasks in a Pipeline.
Trigger / EventListenerHTTP endpoint that creates PipelineRuns in response to Git webhooks.
 
apiVersion: tekton.dev/v1
kind: Pipeline
metadata:
  name: build-and-deploy
spec:
  params:
  - name: image-tag
    type: string
  workspaces:
  - name: source
  tasks:
  - name: clone
    taskRef:
      name: git-clone
      kind: ClusterTask
    workspaces:
    - name: output
      workspace: source
    params:
    - name: url
      value: https://github.com/example/my-app
  - name: build-push
    runAfter: [clone]
    taskRef:
      name: buildah
      kind: ClusterTask
    params:
    - name: IMAGE
      value: registry.example.com/my-app:$(params.image-tag)
    workspaces:
    - name: source
      workspace: source
  - name: deploy
    runAfter: [build-push]
    taskRef:
      name: openshift-client
      kind: ClusterTask
    params:
    - name: SCRIPT
      value: oc rollout restart deployment/my-app

Source-to-Image (S2I)

S2I is OpenShift's original build mechanism — injects source code into a builder image and produces a runnable image without writing a Dockerfile.

# New app from Git using S2I builder image
oc new-app python:3.11~https://github.com/example/my-python-app

# Trigger a new build manually
oc start-build my-app-build --follow

# Watch build logs
oc logs -f bc/my-app-build
Tekton vs Jenkins vs GitHub Actions Tekton runs inside the cluster (no external CI server), uses standard Kubernetes resources, and has no single point of failure. Jenkins is feature-rich but requires managing a separate server. GitHub Actions is best for open-source / cloud-hosted workloads. For OpenShift-native workflows, Tekton with OpenShift GitOps (ArgoCD) is the recommended pattern.
Section 08

Networking

OpenShift 4.x uses OVN-Kubernetes (Open Virtual Network) as its default CNI plugin, replacing the older OpenShift SDN. OVN-K provides per-namespace network isolation, NetworkPolicies, egress IPs, and hardware offload support.

Network Stack

External Traffic │ ▼ HAProxy Router (ingress) │ Route/Ingress rules ▼ Service (ClusterIP / kube-proxy / OVN) │ label selector ▼ Pod ← → Pod (OVN-K overlay network: VXLAN/Geneve) │ ▼ Egress (EgressIP / EgressFirewall) │ ▼ External Services / Internet

NetworkPolicy

NetworkPolicies are namespace-scoped and default-deny when applied — any pod not matching an Ingress rule is isolated.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: postgres
    ports:
    - protocol: TCP
      port: 5432

EgressIP

EgressIP assigns a stable, predictable source IP to traffic leaving the cluster from a specific namespace or set of pods. Critical for firewall allowlisting.

apiVersion: k8s.ovn.org/v1
kind: EgressIP
metadata:
  name: production-egress
spec:
  egressIPs:
  - 10.0.0.100
  namespaceSelector:
    matchLabels:
      environment: production

DNS and Service Discovery

DNS Name PatternResolves To
<service>ClusterIP (same namespace only)
<service>.<namespace>ClusterIP (cross-namespace)
<service>.<namespace>.svcClusterIP
<service>.<namespace>.svc.cluster.localClusterIP (FQDN)
<pod-name>.<headless-svc>.<ns>.svc.cluster.localPod IP directly (StatefulSet)

OVN-Kubernetes Features

NetworkPolicy EgressIP EgressFirewall Multicast IPv4/IPv6 dual-stack Hardware offload (SmartNIC) Multi-network (Multus CNI) Cluster-scoped NetworkPolicy (Admin NP)
Service Mesh — OpenShift Service Mesh (Istio) For advanced traffic management (circuit breaking, retries, mutual TLS, traffic splitting) use OpenShift Service Mesh (based on Istio + Envoy). It adds a sidecar proxy to every pod and provides observability via Kiali, distributed tracing (Jaeger), and metrics (Prometheus).
Section 09

Monitoring & Logging

OpenShift ships with a fully managed monitoring stack (Prometheus + Alertmanager + Grafana) and a logging stack (OpenShift Logging based on Elasticsearch/Loki + Fluentd/Vector). Both are installed as Operators and are ready out of the box.

Monitoring Stack Components

Prometheus

Time-series metrics database. Scrapes targets via ServiceMonitor/PodMonitor. Two instances: platform metrics + user-defined workloads.

Alertmanager

Routes, deduplicates, and silences alerts fired by Prometheus rules. Supports PagerDuty, Slack, email, webhook receivers.

Grafana

Dashboards for visualising Prometheus metrics. OpenShift ships read-only managed Grafana; deploy a custom instance for editable dashboards.

Thanos Querier

Federates queries across platform and user-defined Prometheus instances. Powers the OpenShift console Observe page.

kube-state-metrics

Exposes Kubernetes object state as metrics (pod phases, deployment replicas, PVC capacity). Scraped automatically by platform Prometheus.

node-exporter

DaemonSet that exposes host-level hardware and OS metrics (CPU, memory, disk, network) per node.

Exposing Application Metrics

# Enable user-defined monitoring in cluster-monitoring-config
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
---
# ServiceMonitor — tells Prometheus how to scrape your app
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-app-monitor
  namespace: production
spec:
  selector:
    matchLabels:
      app: my-app
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s

PrometheusRule — Custom Alerts

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: my-app-alerts
  namespace: production
spec:
  groups:
  - name: my-app.rules
    rules:
    - alert: HighErrorRate
      expr: |
        rate(http_requests_total{status=~"5..",job="my-app"}[5m])
        / rate(http_requests_total{job="my-app"}[5m]) > 0.05
      for: 2m
      labels:
        severity: warning
      annotations:
        summary: "High error rate on {{ $labels.instance }}"
        description: "Error rate is {{ $value | humanizePercentage }}"

Logging Stack

ComponentRole
Vector / FluentdDaemonSet log collector. Reads container logs from /var/log/pods/ and enriches with k8s metadata.
LokiLog aggregation store (modern, label-indexed). Queried via LogQL. Preferred over Elasticsearch in OCP 5.x+.
ElasticsearchLegacy full-text log store. Supports JSON field queries. High memory footprint.
KibanaVisualization for Elasticsearch logs (legacy stack).
LokiStackOCP-managed Loki with multi-tenancy; query via OpenShift Console Logs tab or Grafana.

Useful Observability Commands

# View pod logs
oc logs -f deployment/my-app -c app     # follow, specific container
oc logs my-pod --previous               # logs from previous (crashed) instance
oc logs --tail=100 my-pod               # last 100 lines

# Events — often first place to look for failures
oc get events -n production --sort-by='.lastTimestamp'
oc describe pod my-pod | grep -A 20 Events

# Resource usage
oc adm top pods -n production
oc adm top nodes

# Debug a failing pod
oc debug pod/my-pod                     # start debug shell in pod copy
oc debug node/worker-0                  # start privileged debug pod on node
oc exec -it my-pod -- /bin/sh           # exec into running pod
Four Golden Signals Structure observability around Latency (how long requests take), Traffic (requests per second), Errors (rate of failed requests), and Saturation (how full the service is — CPU, queue depth). OpenShift's platform metrics provide all four out of the box for cluster components; instrument your application code for the same signals.
