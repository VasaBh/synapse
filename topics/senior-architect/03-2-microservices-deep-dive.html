2. MICROSERVICES – DEEP DIVE

2.1 Decomposition Strategies

  • Domain-Driven Design (DDD) – identify Bounded Contexts; each becomes a service
  • Subdomain types: Core (competitive differentiator), Supporting, Generic
  • Aggregates – cluster of related entities with a single root; don't split aggregates across services
  • Service granularity: too fine = chatty network; too coarse = monolith-in-disguise

2.2 Communication Patterns

PatternProtocolUse When
Sync request/replyREST / gRPCImmediate response required (user-facing reads)
Async messagingKafka / RabbitMQDecoupled workflows, high throughput
GraphQLHTTPFlexible queries; multiple clients with diff needs
Service Mesh (Istio)mTLS + sidecarCross-cutting: observability, auth, retries at infra level

2.3 Resilience Patterns

Circuit Breaker (Resilience4j / Hystrix)

  • CLOSED → OPEN (after N failures) → HALF-OPEN (test probe) → CLOSED
  • Prevents cascade failures; gives downstream time to recover

Other Patterns

  • Retry with exponential backoff + jitter – avoid thundering herd
  • Timeout – never wait indefinitely; set per-call and overall deadlines
  • Rate Limiting – protect services from being overwhelmed
  • Bulkhead – separate thread pools per downstream; failure in one doesn't starve others
  • Fallback – return cached/default data when dependency is unavailable

2.4 Data Management

⚠️ Key Concept: Each microservice must own its data store. Sharing databases couples services and defeats the purpose.
  • Database-per-service: each service chooses the right storage (SQL, NoSQL, Graph, Time-series)
  • API Composition – aggregate data from multiple services in a BFF or API Gateway
  • CQRS – separate read (Query) and write (Command) models for complex domains
  • Event Sourcing – persist state as immutable event log; derive current state by replaying events

Distributed Transactions – Saga Pattern

Saga TypeMechanismBest For
ChoreographyServices emit and react to events (no central coordinator)Simple flows; loosely coupled
OrchestrationCentral orchestrator directs each step and handles rollbackComplex flows; easier to visualise

2.5 Observability (The Three Pillars)

  • Logs – structured JSON logs; centralise with ELK Stack (Elasticsearch, Logstash, Kibana)
  • Metrics – Prometheus scrapes metrics; Grafana dashboards; alert on SLOs
  • Traces – OpenTelemetry instrumentation → Jaeger / Zipkin for distributed request tracing
  • Correlation IDs – inject at edge; propagate through every service for end-to-end tracing

2.6 Security

  • mTLS between services (via Istio / service mesh) – mutual authentication
  • OAuth2 / OIDC at API Gateway; JWT propagation internally
  • Secrets management – Vault, Kubernetes Secrets (encrypted at rest), external secrets operator
  • Principle of least privilege – each service has minimal permissions
💡 Interview Tip: Expect: 'How do you handle distributed transactions?' Answer: Saga (choreography for simple, orchestration for complex); eventual consistency with compensating transactions.
