2. Load Balancing Inside OpenShift

OpenShift provides multiple layers of load balancing built into the platform. Each layer operates at a different level and serves a different purpose. This section covers every mechanism available natively within an OpenShift cluster.

2.1 Kubernetes Service (ClusterIP) — Internal L4

This is the most fundamental load balancing mechanism. When you create a Kubernetes Service of type ClusterIP, the underlying network plugin (kube-proxy with iptables/IPVS, or OVN-Kubernetes in OpenShift 4) creates rules that distribute traffic across all pods matching the service selector. The default algorithm is random round-robin.

┌─────────────────────────────────────────────┐
│   Kubernetes Service (ClusterIP)            │
│   my-api-service:8080                       │
│                                             │
│   ┌──────┐  ┌──────┐  ┌──────┐             │
│   │ Pod  │  │ Pod  │  │ Pod  │             │
│   │  #1  │  │  #2  │  │  #3  │             │
│   └──────┘  └──────┘  └──────┘             │
└─────────────────────────────────────────────┘
kube-proxy / OVN-Kubernetes rules
distribute traffic randomly across all pods

Example YAML:

apiVersion: v1
kind: Service
metadata:
name: my-api
spec:
selector:
app: my-api
ports:
- port: 8080
targetPort: 8080
type: ClusterIP

Key characteristics: traffic only reachable within the cluster, no external access. For external exposure, you use Routes or Services of type LoadBalancer.

2.2 OpenShift Routes — L7 Ingress Load Balancing

The OpenShift Router is an HAProxy-based ingress controller that runs on infrastructure or worker nodes. It provides Layer 7 load balancing for external traffic entering the cluster. Every Route object you create configures a virtual host in HAProxy.

The router supports three load balancing algorithms that can be set per-route via annotations:

AlgorithmAnnotation ValueDefault For
roundrobinhaproxy.router.openshift.io/balance: roundrobinNot default. Best for weighted A/B deployments.
leastconnhaproxy.router.openshift.io/balance: leastconnLong-lived connections (LDAP, SQL, WebSockets).
sourcehaproxy.router.openshift.io/balance: sourceDefault for TLS passthrough routes. Session stickiness.
random(default - no annotation needed)Default for edge and re-encrypt routes in OCP 4.x.

Example — Route with weighted traffic split (A/B testing):

apiVersion: route.openshift.io/v1
kind: Route
metadata:
name: my-api
annotations:
haproxy.router.openshift.io/balance: roundrobin
spec:
host: my-api.apps.example.com
to:
kind: Service
name: my-api-v1
weight: 90            # 90% of traffic
alternateBackends:
- kind: Service
name: my-api-v2
weight: 10          # 10% of traffic

CLI shortcut for setting weights:

# Set 80/20 split
oc set route-backends my-api my-api-v1=80 my-api-v2=20
# Check current backends
oc set route-backends my-api

2.3 OpenShift Service Mesh (Istio) — Advanced L7

OpenShift Service Mesh, based on Istio, provides the most powerful and fine-grained traffic management. It works by injecting an Envoy sidecar proxy into each pod. All traffic in and out of the pod is intercepted by Envoy, which is centrally configured by the Istio control plane (istiod).

Istio Control Plane (istiod)
|          |          |
config push  config push  config push
|          |          |
+----------+ +----------+ +----------+
|  Pod A   | |  Pod B   | |  Pod C   |
| +------+ | | +------+ | | +------+ |
| |Envoy | | | |Envoy | | | |Envoy | |
| |Proxy | | | |Proxy | | | |Proxy | |
| +------+ | | +------+ | | +------+ |
| |  App | | | |  App | | | |  App | |
| +------+ | | +------+ | | +------+ |
+----------+ +----------+ +----------+
All traffic passes through Envoy

Service Mesh capabilities for load balancing:

  • Weighted traffic splitting: Route percentages of traffic to different service versions (canary, A/B).
  • Header-based routing: Route based on HTTP headers (user-agent, custom headers, cookies).
  • Load balancing algorithms: ROUND_ROBIN, LEAST_CONN, RANDOM, PASSTHROUGH per DestinationRule.
  • Circuit breaking: Prevent cascading failures by limiting connections to unhealthy services.
  • Fault injection: Inject delays or errors to test resilience.
  • Traffic mirroring: Send a copy of live traffic to a test service without affecting production.
  • Retries and timeouts: Automatic retries with configurable backoff and deadline.

Example — VirtualService with 90/10 weighted split:

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
name: my-api
spec:
hosts:
- my-api
http:
- route:
- destination:
host: my-api
subset: v1
weight: 90
- destination:
host: my-api
subset: v2
weight: 10

Example — DestinationRule with load balancer algorithm:

apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
name: my-api
spec:
host: my-api
trafficPolicy:
loadBalancer:
simple: ROUND_ROBIN
subsets:
- name: v1
labels:
version: v1
- name: v2
labels:
version: v2

2.4 MetalLB — L4 LoadBalancer Services (On-Premises)

In cloud environments, creating a Service of type LoadBalancer automatically provisions a cloud load balancer (AWS ELB, Azure LB, etc.). On-premises OpenShift clusters lack this cloud integration. MetalLB fills this gap by providing LoadBalancer-type services for bare metal or on-prem environments.

MetalLB operates in two modes:

  • Layer 2 (ARP/NDP): Announces the service IP via ARP on the local network. Simple setup, but a single node handles all traffic for each IP (failover, not true load balancing).
  • BGP (Layer 3): Announces routes via BGP to network routers. Enables true ECMP (Equal-Cost Multi-Path) load balancing across multiple nodes.

Example — MetalLB LoadBalancer Service:

apiVersion: v1
kind: Service
metadata:
name: my-database
annotations:
metallb.universe.tf/address-pool: production-pool
spec:
type: LoadBalancer
selector:
app: my-database
ports:
- port: 3306
targetPort: 3306

Note: MetalLB cannot replace the OpenShift API or Ingress VIP endpoints. It is designed for application-level LoadBalancer services, particularly useful for non-HTTP workloads like databases, message brokers, and custom TCP services.
