Section 01

Model Serving

Serving LLMs efficiently is an infrastructure challenge: GPU memory is expensive, requests are bursty, and a single large model can saturate a whole GPU. Modern serving frameworks like vLLM solve this with paged attention and continuous batching.

Client Requests (concurrent) │ ▼ Load Balancer (nginx / Kubernetes Service) │ ▼ vLLM Server (paged attention + continuous batching) ┌──────────────────────────────────────────────┐ │ KV Cache pages (non-contiguous memory) │ │ Request queue → dynamic batching │ │ GPU utilisation: 70-90% vs 30% naive │ └──────────────────────────────────────────────┘ │ ▼ GPU Cluster (A100/H100)

Serving Framework Comparison

FrameworkThroughputKey FeatureBest For
vLLMHighestPaged attention, continuous batching, OpenAI APIProduction self-hosted LLMs
TGI (HuggingFace)HighTensor parallelism, quantisation, gRPCHuggingFace ecosystem, enterprise
Triton Inference ServerVery HighMulti-model, GPU/CPU, ONNX/TensorRTMulti-model serving, NVIDIA shop
OllamaMediumOne-command local deploy, GGUF supportLocal dev, edge, MacOS
llama.cppCPU-optimised4-bit quant, no GPU requiredCPU-only servers, edge devices

vLLM: Launch & Query

# Launch vLLM server (OpenAI-compatible API)
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-3-8B-Instruct \
    --tensor-parallel-size 2 \
    --max-model-len 8192 \
    --port 8000
# Query with standard OpenAI SDK (drop-in replacement)
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="not-needed")

response = client.chat.completions.create(
    model="meta-llama/Llama-3-8B-Instruct",
    messages=[{"role": "user", "content": "Explain gradient descent."}],
    max_tokens=512,
    stream=True,
)
for chunk in response:
    print(chunk.choices[0].delta.content or "", end="", flush=True)
vLLM's paged attention reduces GPU waste by ~60% Traditional serving pre-allocates a contiguous KV cache per request, wasting memory on speculative lengths. vLLM's paged attention allocates cache in fixed-size pages on demand — 2–4x higher throughput on the same hardware.
Section 02

Observability & Tracing

LLM applications fail in non-deterministic ways. Observability — tracing every request end-to-end with inputs, outputs, latency, token counts, and tool calls — is the only way to debug production issues and measure quality over time.

LLM Request │ ├─► OpenTelemetry Span │ ├─ span.name: "llm.completion" │ ├─ attributes: model, input_tokens, output_tokens, latency_ms │ └─ events: prompt, completion, tool_calls │ └─► Trace Collector (OTEL Collector) │ ├──► LangSmith (LangChain native) ├──► Langfuse (open-source) ├──► Arize Phoenix (ML observability) └──► Grafana/Tempo (generic traces)

LangSmith Tracing

import os
from langsmith import traceable
from openai import OpenAI

os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "your-langsmith-key"
os.environ["LANGCHAIN_PROJECT"] = "production-chatbot"

client = OpenAI()

@traceable(name="chat_completion", run_type="llm")
def chat(messages: list, model: str = "gpt-4o-mini") -> str:
    response = client.chat.completions.create(
        model=model, messages=messages, max_tokens=512
    )
    return response.choices[0].message.content

# Every call to chat() is automatically traced in LangSmith
result = chat([{"role": "user", "content": "What is RAG?"}])

Section 03

Cost Optimization

LLM API costs scale linearly with token volume. At 10K requests/day, even small per-call savings compound to thousands of dollars per month. The highest-leverage techniques are model routing, caching, and prompt compression.

Incoming Request │ ├─► Complexity Classifier (lightweight model) │ │ │ ┌────┴──────────┐ │ Simple Complex │ │ │ │ Haiku/GPT-Nano Sonnet/GPT-Mini │ ($0.25/1M) ($3/1M) │ └─► Cached? ──► YES → return cached (free) └── NO → LLM call → cache result
StrategySavings EstimateComplexityImplementation
Model routing (tiered)60–80%MediumLiteLLM router, custom classifier
Semantic caching30–60% on repeat queriesMediumGPTCache, Redis + embeddings
Prompt compression30–50% token reductionLowLLMLingua, PromptCompressor
Prefix/prompt cachingUp to 90% on cached tokensLowAnthropic cache_control, OpenAI Prompt Cache
Batch API50% offLowOpenAI Batch API, Anthropic Batches
Quantised self-hosted70–90% vs APIHighvLLM + AWQ/GPTQ model

LiteLLM Cost-Based Router

from litellm import Router

router = Router(
    model_list=[
        {"model_name": "fast",    "litellm_params": {"model": "claude-haiku-4-5-20251001"}},
        {"model_name": "smart",   "litellm_params": {"model": "claude-sonnet-4-20250514"}},
        {"model_name": "premium", "litellm_params": {"model": "claude-opus-4-20250514"}},
    ],
    routing_strategy="cost-based-routing",
)

def route_request(prompt: str, task_type: str) -> str:
    model = {
        "classification": "fast",
        "summarisation":  "smart",
        "complex_reasoning": "premium",
    }.get(task_type, "smart")

    response = router.completion(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content
70/25/5 routing rule Route 70% of requests to the cheapest capable model, 25% to the mid-tier, and 5% to premium. This pattern cuts API spend by 60–80% with minimal quality impact for most applications.
Section 04

Caching Strategies

Caching is the highest-ROI optimisation in LLM applications. A cache hit returns the answer in under 1ms at zero cost. Two complementary levels: prefix caching (provider-level) and semantic caching (application-level).

Request → [Exact match cache] ──► HIT → return (0ms, free) │ MISS │ ▼ [Semantic cache (embedding similarity)] │ ┌───────┴───────┐ HIT MISS │ │ return (~5ms) LLM call (free) (~800ms, $$$) │ cache result (TTL: 1h–24h)

Anthropic Prompt Caching

import anthropic

client = anthropic.Anthropic()

# Mark static system prompt for caching (up to 90% savings on cached tokens)
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": "You are a helpful assistant with deep knowledge of...\n" + long_documentation,
        "cache_control": {"type": "ephemeral"}  # Cache this block
    }],
    messages=[{"role": "user", "content": "Summarise section 3."}]
)
# First call: full input tokens charged
# Subsequent calls: cache_read_input_tokens (10% of normal price)

Application-Level Semantic Cache

from langchain.cache import RedisSemanticCache
from langchain_openai import OpenAIEmbeddings
import langchain

# Set up semantic cache backed by Redis
langchain.llm_cache = RedisSemanticCache(
    redis_url="redis://localhost:6379",
    embedding=OpenAIEmbeddings(model="text-embedding-3-small"),
    score_threshold=0.95,  # cosine similarity threshold for cache hit
)

# All subsequent LLM calls check cache automatically
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o-mini")
result = llm.invoke("What is the capital of France?")  # cached after first call

Section 05

A/B Testing LLMs

Changing a model, prompt, or RAG configuration is a hypothesis. A/B testing validates it with real traffic before full rollout, preventing quality regressions that offline evals miss due to distribution shift.

Incoming Traffic │ ├──── 90% ──► Variant A (current production) ──► Log trace │ └──── 10% ──► Variant B (new prompt/model) ──► Log trace │ Statistical analysis (after N samples) │ ┌──────────────┴──────────────┐ B wins No sig. diff │ │ Ramp B to 100% Keep A / iterate
import random
import hashlib
from langsmith import Client

ls_client = Client()

def ab_test_completion(user_id: str, prompt: str) -> str:
    # Deterministic assignment by user_id (same user always gets same variant)
    variant = "B" if int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100 < 10 else "A"

    if variant == "A":
        model, system = "gpt-4o-mini", "You are a helpful assistant."
    else:
        model = "claude-haiku-4-5-20251001"
        system = "You are a concise, expert assistant. Answer in bullet points."

    # ... call LLM ...

    # Log variant for analysis
    ls_client.create_run(
        name="ab_test",
        inputs={"prompt": prompt, "variant": variant, "user_id": user_id},
        outputs={"response": response},
        extra={"variant": variant, "model": model},
    )
    return response
Minimum sample size matters For LLM quality A/B tests, aim for at least 200 samples per variant before drawing conclusions. LLM output variance is high — small samples produce misleading results. Use a power calculator with α=0.05 and desired effect size.
Section 06

Guardrails & Safety

Production LLM applications require both input and output validation layers. Guardrails catch harmful inputs before they reach the model, and validate outputs before they reach users — without retraining the underlying model.

User Input │ ├─► [PII Detection] → redact phone, email, SSN ├─► [Toxicity Filter] → block harmful inputs ├─► [Prompt Injection] → detect "ignore instructions" │ ▼ LLM │ ▼ LLM Output │ ├─► [Hallucination Check] → grounded in retrieved context? ├─► [Format Validation] → valid JSON / required fields? ├─► [PII Output Filter] → strip leaked PII └─► [Toxicity Output] → block harmful completions │ ▼ User
from guardrails import Guard
from guardrails.hub import DetectPII, ToxicLanguage, ValidLength

guard = Guard().use_many(
    DetectPII(pii_entities=["EMAIL_ADDRESS", "PHONE_NUMBER", "CREDIT_CARD"]),
    ToxicLanguage(threshold=0.5, on_fail="exception"),
    ValidLength(min=1, max=2000, on_fail="fix"),
)

def safe_completion(user_input: str) -> str:
    # Validate input
    validated_input, *_ = guard.validate(user_input)

    # Call LLM
    raw_output = call_llm(validated_input)

    # Validate output
    validated_output, *_ = guard.validate(raw_output)
    return validated_output
Guardrail TypeToolLatency AddNotes
PII detectionPresidio, Guardrails AI10–50msRun on both input and output
ToxicityPerspective API, LlamaGuard50–150msLlamaGuard is self-hostable
HallucinationRAGAS faithfulness, SelfCheckGPT200–500msOnly feasible for non-realtime flows
JSON validationInstructor, Pydantic<1msAlways use for structured outputs
Guardrails add 50–200ms latency Profile every guardrail before adding it to the hot path. For real-time chat, use lightweight classifiers (PII regex, embedding-based toxicity). Reserve heavy checks (LlamaGuard, hallucination detection) for async post-processing or batch flows.
Section 07

Model Versioning & Registry

Treating prompts and models as versioned artefacts — not inline strings — is what separates prototypes from production systems. A registry enables rollbacks, A/B testing, and audit trails.

Experiment │ (develop prompt / fine-tune model) ▼ Evaluate (evals pass ≥ threshold?) │ YES ▼ Register (MLflow / LangSmith Hub / HuggingFace Hub) │ ├─► Staging environment │ │ (smoke test, integration test) │ ▼ └─► Production (blue-green deploy) │ Monitor ──► quality regression? → rollback to prev version

MLflow LLM Run Logging

import mlflow

mlflow.set_experiment("rag-chatbot-v2")

with mlflow.start_run(run_name="prompt-v3-gpt4o-mini"):
    # Log parameters
    mlflow.log_params({
        "model": "gpt-4o-mini",
        "temperature": 0.3,
        "chunk_size": 512,
        "top_k": 4,
        "prompt_version": "v3",
    })

    # Run evaluation
    results = run_eval_suite()  # returns dict of metrics

    # Log metrics
    mlflow.log_metrics({
        "ragas_faithfulness": results["faithfulness"],
        "ragas_relevancy": results["answer_relevancy"],
        "avg_latency_ms": results["avg_latency"],
        "cost_per_query_usd": results["cost_per_query"],
    })

    # Log prompt as artefact
    mlflow.log_text(system_prompt, "system_prompt_v3.txt")

    # Register model if metrics pass threshold
    if results["faithfulness"] >= 0.80:
        mlflow.register_model("runs:/{run_id}/model", "rag-chatbot")
Treat prompts as code Version your prompts in git AND push them to a prompt registry (LangSmith Hub or Langfuse). Git gives you diffs and blame; a registry gives you runtime pull without redeploy, A/B testing, and rollback in seconds.
Section 08

Latency Optimization

LLM latency has two components: Time to First Token (TTFT) and generation speed (tokens/sec). Users perceive streaming as faster even when total latency is the same — always stream for interactive applications.

Request received │ ├─► TTFT (time to first token): 200–800ms │ Affected by: model size, batch pressure, prefill length │ └─► Generation: ~30–100 tok/sec (streaming hides this) Key insight: start streaming immediately. User sees first token at TTFT, not at completion.
TechniqueLatency ReductionTrade-off
StreamingPerceived: 50–70%Complex client handling
Semantic caching100% (cache hit = ~5ms)Stale responses possible
Smaller model (routing)30–60%Lower quality on hard tasks
Quantisation (INT8/AWQ)20–40%Minor quality regression
Speculative decoding20–40%Requires draft model, memory
Prompt compression10–30% (shorter prefill)May lose context

FastAPI Streaming Endpoint (SSE)

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from openai import AsyncOpenAI

app = FastAPI()
client = AsyncOpenAI()

@app.post("/chat/stream")
async def stream_chat(prompt: str):
    async def generate():
        stream = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            stream=True,
            max_tokens=512,
        )
        async for chunk in stream:
            delta = chunk.choices[0].delta.content
            if delta:
                yield f"data: {delta}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",
                                      "X-Accel-Buffering": "no"})
Section 09

CI/CD for LLM Apps

LLM application CI/CD differs from traditional software: you're not just testing code correctness, you're testing output quality. A CI pipeline that only runs unit tests will miss prompt regressions that ship to production.

Pull Request │ ├─► [Lint] prompt YAML schema validation ├─► [Unit tests] tool functions, parsers, routers ├─► [Eval suite] run DeepEval on 50-item golden dataset │ │ │ ├── faithfulness ≥ 0.80? → pass │ ├── answer_relevancy ≥ 0.75? → pass │ └── latency_p95 ≤ 2s? → pass │ ▼ All pass? → merge & deploy to staging │ ├─► [Staging] smoke test with real traffic sample ├─► [Canary] 5% real traffic → monitor metrics └─► [Full rollout] 100% traffic → monitor dashboards

GitHub Actions Eval Workflow

# .github/workflows/llm-eval.yml
name: LLM Eval Suite
on: [pull_request]

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: Install dependencies
        run: pip install deepeval langchain openai

      - name: Run evaluation suite
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
          LANGCHAIN_API_KEY: ${{ secrets.LANGSMITH_API_KEY }}
        run: python scripts/run_evals.py --golden-set data/golden_qa.json

      - name: Check quality gates
        run: python scripts/check_quality_gates.py \
               --min-faithfulness 0.80 \
               --min-relevancy 0.75 \
               --max-latency-p95 2000

Quality Gate Script

import json, sys

def check_gates(results_path: str, **thresholds):
    with open(results_path) as f:
        results = json.load(f)

    failures = []
    for metric, min_val in thresholds.items():
        score = results.get(metric, 0)
        if score < min_val:
            failures.append(f"{metric}: {score:.3f} < {min_val}")

    if failures:
        print("❌ Quality gates FAILED:")
        for f in failures: print(f"   {f}")
        sys.exit(1)
    else:
        print("✅ All quality gates passed")

check_gates("eval_results.json",
            faithfulness=0.80, answer_relevancy=0.75)

Golden Dataset

50–100 representative Q&A pairs with expected answers. Update it as your product evolves. Never delete passing test cases.

Regression Gate

Block merges if quality drops more than 5% from the baseline established on main. Alert on absolute thresholds too.

Canary Deploy

Route 5% of traffic to new version for 30 minutes. Monitor error rate, latency p99, and user feedback score before full rollout.

Rollback Playbook

Document the 3-step rollback procedure. Test it quarterly. When an LLM incident hits at 2am, you want a script, not a wiki page.
