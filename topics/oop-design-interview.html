Section 01

Approaching OOD Interviews

Object-oriented design ("low-level design" / LLD) interviews ask you to model a real-world system as classes — the bar isn't "does it run," it's whether your design is extensible, follows single-responsibility boundaries, and survives the interviewer's follow-up curveballs.

A repeatable approach

1. Clarify requirements & scope
2. Identify the core entities (nouns)
3. Identify behaviors & relationships (verbs)
4. Pick design patterns that fit naturally
5. Code the core classes, then extend for follow-ups

SOLID, in one line each

Single Responsibility

A class should have one reason to change — one job, one owner.

Open/Closed

Open for extension, closed for modification — add a new subclass instead of editing existing branches.

Liskov Substitution

A subclass must be usable anywhere its base class is expected, without breaking correctness.

Interface Segregation

Prefer several small, focused interfaces over one bloated one that forces unused methods on implementers.

Dependency Inversion

Depend on abstractions (interfaces/ABCs), not concrete classes — makes components swappable and testable.

What interviewers are actually scoring Clean entity boundaries, correct use of inheritance vs composition, whether you reach for a known pattern when one genuinely fits (not pattern-for-pattern's-sake), and how gracefully your design absorbs a follow-up requirement without a rewrite.
Section 02

Employee Hierarchy (Org Chart)

Prompt: "Design a class structure to represent a company's employee hierarchy. Support adding employees under a manager, counting total reports, computing team salary cost, and printing the org chart." This is a textbook Composite pattern — a manager is just an employee that happens to hold other employees.

Core classes

from abc import ABC, abstractmethod

class Employee(ABC):
    def __init__(self, name: str, salary: float):
        self.name = name
        self.salary = salary
        self.subordinates: list["Employee"] = []

    def add_subordinate(self, employee: "Employee") -> None:
        self.subordinates.append(employee)

    def remove_subordinate(self, employee: "Employee") -> None:
        self.subordinates.remove(employee)

    @abstractmethod
    def role(self) -> str:
        ...

    def total_reports(self) -> int:
        """Direct + indirect reports beneath this employee."""
        count = len(self.subordinates)
        for sub in self.subordinates:
            count += sub.total_reports()
        return count

    def total_team_cost(self) -> float:
        return self.salary + sum(sub.total_team_cost() for sub in self.subordinates)

    def print_org_chart(self, level: int = 0) -> None:
        print("  " * level + f"{self.name} ({self.role()}) — ${self.salary:,.0f}")
        for sub in self.subordinates:
            sub.print_org_chart(level + 1)


class Manager(Employee):
    def role(self) -> str:
        return "Manager"


class Developer(Employee):
    def role(self) -> str:
        return "Developer"


ceo   = Manager("Grace", 250_000)
vp    = Manager("Han", 180_000)
dev_a = Developer("Ivy", 120_000)
dev_b = Developer("Jax", 115_000)

ceo.add_subordinate(vp)
vp.add_subordinate(dev_a)
vp.add_subordinate(dev_b)

ceo.print_org_chart()
print("Total reports under CEO:", ceo.total_reports())     # 3
print("Total team cost:", ceo.total_team_cost())            # 665,000.0
Why this is the Composite pattern Employee is the shared component interface; Manager is a "composite" that holds children, and a leaf Developer just happens to have an empty subordinates list. Every method (total_reports, total_team_cost, print_org_chart) works identically whether it's called on the CEO or an individual contributor — no isinstance branching required.

Common follow-ups

from collections import deque

# 1. Find an employee by name — BFS across the tree
def find_employee(root: Employee, name: str) -> Employee | None:
    queue = deque([root])
    while queue:
        current = queue.popleft()
        if current.name == name:
            return current
        queue.extend(current.subordinates)
    return None

# 2. Find an employee's manager — needs a reverse (parent) map
def build_manager_map(root: Employee, parent: Employee | None = None,
                       out: dict[str, Employee] | None = None) -> dict[str, Employee]:
    out = {} if out is None else out
    if parent is not None:
        out[root.name] = parent
    for sub in root.subordinates:
        build_manager_map(sub, root, out)
    return out

# 3. Depth of the org chart (longest management chain)
def max_depth(employee: Employee) -> int:
    if not employee.subordinates:
        return 1
    return 1 + max(max_depth(sub) for sub in employee.subordinates)

# 4. Employee with the most DIRECT reports
def widest_manager(root: Employee) -> Employee:
    best = root
    queue = deque([root])
    while queue:
        current = queue.popleft()
        if len(current.subordinates) > len(best.subordinates):
            best = current
        queue.extend(current.subordinates)
    return best
Curveball: "What if an employee can report to two managers?" That breaks the tree assumption — it becomes a DAG. A list[Employee] of subordinates alone no longer lets you find all managers of a node in O(1); you'd need each employee to track its own managers: list[Employee] too, and any traversal (like total_reports) must now track visited nodes to avoid double-counting someone reachable through two paths.

Parking Lot System

Prompt: "Design a parking lot that supports multiple spot sizes and vehicle types, tracks availability, and issues a ticket on entry." Tests enums for fixed categories, encapsulating allocation logic, and separating the lot from its floors/spots. 

from enum import Enum, auto
from dataclasses import dataclass, field
from datetime import datetime

class SpotSize(Enum):
    MOTORCYCLE = auto()
    COMPACT = auto()
    LARGE = auto()

class VehicleType(Enum):
    MOTORCYCLE = SpotSize.MOTORCYCLE
    CAR = SpotSize.COMPACT
    BUS = SpotSize.LARGE

@dataclass
class Vehicle:
    license_plate: str
    vehicle_type: VehicleType

@dataclass
class ParkingSpot:
    spot_id: str
    size: SpotSize
    vehicle: Vehicle | None = None

    def is_available(self) -> bool:
        return self.vehicle is None

    def fits(self, vehicle: Vehicle) -> bool:
        return self.size.value >= vehicle.vehicle_type.value.value

@dataclass
class Ticket:
    vehicle: Vehicle
    spot: ParkingSpot
    entry_time: datetime = field(default_factory=datetime.now)

class ParkingLot:
    def __init__(self, spots: list[ParkingSpot]):
        self.spots = spots
        self.active_tickets: dict[str, Ticket] = {}   # license_plate -> Ticket

    def find_available_spot(self, vehicle: Vehicle) -> ParkingSpot | None:
        # smallest fitting spot first — don't waste a LARGE spot on a motorcycle
        candidates = [s for s in self.spots if s.is_available() and s.fits(vehicle)]
        return min(candidates, key=lambda s: s.size.value, default=None)

    def park(self, vehicle: Vehicle) -> Ticket | None:
        spot = self.find_available_spot(vehicle)
        if spot is None:
            return None                      # lot full for this vehicle class
        spot.vehicle = vehicle
        ticket = Ticket(vehicle=vehicle, spot=spot)
        self.active_tickets[vehicle.license_plate] = ticket
        return ticket

    def unpark(self, license_plate: str) -> float:
        ticket = self.active_tickets.pop(license_plate)
        ticket.spot.vehicle = None
        hours = max(1, (datetime.now() - ticket.entry_time).seconds // 3600)
        return hours * 5.0                    # flat $5/hour billing
Why SpotSize.value >= vehicle.vehicle_type.value.value Ordering the enum by physical size lets one comparison decide fit — a bus needs LARGE, a car fits COMPACT or LARGE, a motorcycle fits anywhere. Picking the smallest fitting spot (rather than the first available) keeps large spots free for vehicles that actually need them.

Common follow-ups

  • Multiple floors — add a ParkingFloor that owns a subset of spots; the lot iterates floors.
  • Concurrency — two cars arriving simultaneously must not claim the same spot; guard park() with a lock per spot or use atomic compare-and-swap on spot.vehicle.
  • Reservations — add a reserve(spot, vehicle, expiry) step before park() actually occupies it.
  • Dynamic pricing — replace the flat hours * 5.0 with a PricingStrategy interface (Strategy pattern) swapped per lot.

LRU Cache

Prompt: "Design a cache with a fixed capacity that evicts the Least Recently Used item when full — get and put must both run in O(1)." The canonical solution pairs a hash map (O(1) lookup) with a doubly linked list (O(1) reordering).

Quick version — OrderedDict

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache: OrderedDict[int, int] = OrderedDict()

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1
        self.cache.move_to_end(key)          # mark as most recently used
        return self.cache[key]

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)   # evict the LEAST recently used

What the interviewer usually wants — manual doubly linked list

class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=0, value=0):
        self.key, self.value = key, value
        self.prev: "Node | None" = None
        self.next: "Node | None" = None

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.map: dict[int, Node] = {}
        # sentinel head/tail avoid null-checks at the list boundaries
        self.head, self.tail = Node(), Node()
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node: Node) -> None:
        node.prev.next, node.next.prev = node.next, node.prev

    def _add_to_front(self, node: Node) -> None:
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        self._remove(node)
        self._add_to_front(node)
        return node.value

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            self._remove(self.map[key])
        node = Node(key, value)
        self.map[key] = node
        self._add_to_front(node)
        if len(self.map) > self.capacity:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
Why sentinel head/tail nodes Without them, removing the first or last real node requires special-casing None checks on both ends. Two dummy nodes that never hold real data mean _remove/_add_to_front work identically for every position — fewer edge cases, fewer bugs.

Elevator System

Prompt: "Design an elevator control system for a building with multiple elevators — dispatch the best elevator for a pickup request and serve floors efficiently." Tests modeling state machines and a dispatch strategy that can be swapped independently of the elevator itself. 

from enum import Enum, auto
import heapq

class Direction(Enum):
    UP = auto()
    DOWN = auto()
    IDLE = auto()

class Elevator:
    def __init__(self, elevator_id: int, capacity: int = 10):
        self.id = elevator_id
        self.current_floor = 0
        self.direction = Direction.IDLE
        self.capacity = capacity
        self._up_requests: list[int] = []      # min-heap of floors above
        self._down_requests: list[int] = []    # max-heap (negated) below

    def request_floor(self, floor: int) -> None:
        if floor > self.current_floor:
            heapq.heappush(self._up_requests, floor)
        elif floor < self.current_floor:
            heapq.heappush(self._down_requests, -floor)
        self._update_direction()

    def _update_direction(self) -> None:
        if self.direction == Direction.IDLE:
            if self._up_requests:
                self.direction = Direction.UP
            elif self._down_requests:
                self.direction = Direction.DOWN

    def step(self) -> None:
        """Advance one floor toward the next requested stop."""
        if self.direction == Direction.UP and self._up_requests:
            self.current_floor += 1
            if self.current_floor == self._up_requests[0]:
                heapq.heappop(self._up_requests)
        elif self.direction == Direction.DOWN and self._down_requests:
            self.current_floor -= 1
            if self.current_floor == -self._down_requests[0]:
                heapq.heappop(self._down_requests)
        if not self._up_requests and not self._down_requests:
            self.direction = Direction.IDLE

class ElevatorController:
    def __init__(self, num_elevators: int):
        self.elevators = [Elevator(i) for i in range(num_elevators)]

    def dispatch(self, pickup_floor: int, direction: Direction) -> Elevator:
        """Nearest-elevator strategy — swap this method to change dispatch policy."""
        idle_or_matching = [
            e for e in self.elevators
            if e.direction in (Direction.IDLE, direction)
        ]
        pool = idle_or_matching or self.elevators
        best = min(pool, key=lambda e: abs(e.current_floor - pickup_floor))
        best.request_floor(pickup_floor)
        return best
Two heaps model SCAN/elevator scheduling Separating "floors to visit while going up" from "floors to visit while going down" into two heaps means the elevator always serves the nearest stop in its current direction before reversing — the same algorithm as the OS disk-scheduling "elevator algorithm" this system is named after.

Common follow-ups

  • Capacity limits — reject a pickup for a full elevator, or model weight sensors.
  • Multiple dispatch strategies — extract dispatch into a DispatchStrategy interface (Strategy pattern) with "nearest," "least busy," and "zone-based" implementations.
  • Fairness — track wait time per request and prioritize floors waiting longest to avoid starvation.

Library Management System

Prompt: "Design a system to manage books, members, and borrowing — including due dates and overdue fines." Tests modeling a many-to-many relationship (books ↔ members, over time) with a join entity (Loan) rather than cramming state into either side. 

from dataclasses import dataclass, field
from datetime import date, timedelta

@dataclass
class Book:
    isbn: str
    title: str
    copies_total: int
    copies_available: int

@dataclass
class Member:
    member_id: str
    name: str
    active_loans: list["Loan"] = field(default_factory=list)

@dataclass
class Loan:
    book: Book
    member: Member
    checkout_date: date
    due_date: date
    returned_date: date | None = None

class Library:
    LOAN_PERIOD_DAYS = 14
    FINE_PER_DAY = 0.25

    def __init__(self):
        self.books: dict[str, Book] = {}
        self.members: dict[str, Member] = {}
        self.loans: list[Loan] = []

    def checkout(self, isbn: str, member_id: str, today: date) -> Loan:
        book, member = self.books[isbn], self.members[member_id]
        if book.copies_available == 0:
            raise ValueError(f"No copies of '{book.title}' available")
        book.copies_available -= 1
        loan = Loan(book, member, today, today + timedelta(days=self.LOAN_PERIOD_DAYS))
        member.active_loans.append(loan)
        self.loans.append(loan)
        return loan

    def return_book(self, loan: Loan, today: date) -> float:
        loan.returned_date = today
        loan.book.copies_available += 1
        loan.member.active_loans.remove(loan)
        overdue_days = max(0, (today - loan.due_date).days)
        return overdue_days * self.FINE_PER_DAY

    def overdue_loans(self, today: date) -> list[Loan]:
        return [l for l in self.loans if l.returned_date is None and today > l.due_date]
Why a separate Loan entity A book can be checked out by different members over time, and a member can hold multiple loans — that's a many-to-many relationship with its own attributes (checkout date, due date, fine). Modeling Loan as its own class instead of a flag on Book or Member is what makes history, fines, and concurrent multi-copy checkouts possible.

Vending Machine (State Pattern)

Prompt: "Design a vending machine that accepts coins, lets a user select an item, and dispenses it or returns change." A textbook fit for the State pattern — behavior for "insert coin," "select item," and "dispense" changes entirely depending on what state the machine is in. 

from abc import ABC, abstractmethod

class VendingMachine:
    def __init__(self):
        self.balance = 0
        self.selected_item: str | None = None
        self.inventory: dict[str, tuple[int, int]] = {  # name -> (price, stock)
            "soda": (150, 5), "chips": (200, 3),
        }
        self.state: "State" = IdleState(self)

    def insert_coin(self, cents: int) -> None:
        self.state.insert_coin(cents)

    def select_item(self, name: str) -> None:
        self.state.select_item(name)

    def dispense(self) -> None:
        self.state.dispense()


class State(ABC):
    def __init__(self, machine: VendingMachine):
        self.machine = machine

    def insert_coin(self, cents: int) -> None:
        raise ValueError(f"Cannot insert coins in state {type(self).__name__}")

    def select_item(self, name: str) -> None:
        raise ValueError(f"Cannot select an item in state {type(self).__name__}")

    def dispense(self) -> None:
        raise ValueError(f"Cannot dispense in state {type(self).__name__}")


class IdleState(State):
    def insert_coin(self, cents: int) -> None:
        self.machine.balance += cents
        self.machine.state = HasMoneyState(self.machine)


class HasMoneyState(State):
    def insert_coin(self, cents: int) -> None:
        self.machine.balance += cents

    def select_item(self, name: str) -> None:
        price, stock = self.machine.inventory[name]
        if stock == 0:
            raise ValueError("Item out of stock")
        if self.machine.balance < price:
            raise ValueError(f"Insufficient funds — need {price - self.machine.balance} more cents")
        self.machine.selected_item = name
        self.machine.state = DispensingState(self.machine)


class DispensingState(State):
    def dispense(self) -> None:
        name = self.machine.selected_item
        price, stock = self.machine.inventory[name]
        self.machine.inventory[name] = (price, stock - 1)
        change = self.machine.balance - price
        print(f"Dispensing {name}. Change returned: {change} cents")
        self.machine.balance = 0
        self.machine.selected_item = None
        self.machine.state = IdleState(self.machine)
Why State beats a pile of if self.status == "..." checks Each state class only implements the transitions valid from that state — calling select_item() while IdleState is active raises automatically via the base class, with no explicit guard needed. Adding a new state (e.g. MaintenanceState) means adding one class, not editing a growing conditional in every method.

Rate Limiter

Prompt: "Design a rate limiter that allows at most N requests per client per time window." Tests picking the right algorithm for the accuracy/memory trade-off and encapsulating it behind one allow_request() call.

Token bucket

import time

class TokenBucketLimiter:
    def __init__(self, capacity: int, refill_rate_per_sec: float):
        self.capacity = capacity
        self.refill_rate = refill_rate_per_sec
        self.tokens = float(capacity)
        self.last_refill = time.monotonic()

    def _refill(self) -> None:
        now = time.monotonic()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
        self.last_refill = now

    def allow_request(self) -> bool:
        self._refill()
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

Sliding window log (precise, more memory)

from collections import deque
import time

class SlidingWindowLimiter:
    def __init__(self, max_requests: int, window_seconds: float):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self.requests: dict[str, deque[float]] = {}   # per-client timestamps

    def allow_request(self, client_id: str) -> bool:
        now = time.monotonic()
        q = self.requests.setdefault(client_id, deque())
        while q and now - q[0] > self.window_seconds:
            q.popleft()                       # drop timestamps outside the window
        if len(q) < self.max_requests:
            q.append(now)
            return True
        return False
Algorithm Memory Accuracy
Fixed window counter O(1) per client Allows up to 2x burst at window boundaries
Sliding window log O(requests in window) per client Exact
Token bucket O(1) per client Exact rate, allows controlled bursts up to capacity
Interviewer curveball: distributed rate limiting Both implementations above are per-process, in-memory — across multiple API servers you'd need the counters in a shared store (Redis) with atomic increment + expiry, and should expect to discuss the consistency/latency trade-off of checking a remote store on every request.
Section 09

Design Patterns Cheat Sheet

The patterns that show up over and over in LLD interviews — recognize the shape of the problem, don't force-fit a pattern where plain composition would do.

Pattern Problem it solves Seen in this guide
Composite Treat a single object and a group of objects uniformly Employee hierarchy (§2)
State Behavior changes based on internal state, without giant conditionals Vending machine (§7)
Strategy Swap an algorithm at runtime behind one interface Elevator dispatch, pricing (§3, §5)
Observer Notify many dependents automatically when one object changes Notification systems, event buses
Factory Method Delegate object creation so callers don't depend on concrete classes Creating the right ParkingSpot/Vehicle subtype
Singleton Guarantee exactly one instance of a shared resource ParkingLot, ElevatorController (one per building)
Decorator Attach responsibilities to an object dynamically, without subclassing Wrapping a cache with logging/metrics

Observer — quick example

from abc import ABC, abstractmethod

class Observer(ABC):
    @abstractmethod
    def notify(self, event: str) -> None: ...

class EmailObserver(Observer):
    def notify(self, event: str) -> None:
        print(f"Emailing user: {event}")

class Subject:
    def __init__(self):
        self._observers: list[Observer] = []

    def subscribe(self, observer: Observer) -> None:
        self._observers.append(observer)

    def publish(self, event: str) -> None:
        for observer in self._observers:
            observer.notify(event)

# e.g. Library.publish("book_available") notifies everyone waiting on a hold

Singleton — the Pythonic way

class ElevatorController:
    _instance: "ElevatorController | None" = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# NOTE: in interviews, mention the trade-off — singletons make unit testing
# harder (global state persists across tests) and are often better replaced
# by dependency injection (pass one shared instance around explicitly).
Section 10

Tricky Follow-Ups & Trade-offs

The design itself is only half the interview — how you handle the follow-up "now what if..." questions is usually what separates a pass from a strong pass.

Q1. "The CEO retires — promote the VP to CEO." (Employee hierarchy)

def promote_to_root(new_root: Employee, old_root: Employee) -> Employee:
    old_root.remove_subordinate(new_root)          # detach from old parent
    for sibling in old_root.subordinates:
        new_root.add_subordinate(sibling)          # old root's other reports move under new_root
    new_root.add_subordinate(old_root)              # old CEO optionally becomes an advisor/report
    return new_root

This is why storing only a subordinates list (not a back-reference to one's manager) can bite you — re-parenting requires walking from the root to find and detach the promoted node, unless each Employee also tracks its own manager reference for O(1) lookups.

Q2. "Make the Parking Lot thread-safe." (Concurrency)

import threading

class ParkingSpot:
    def __init__(self, spot_id: str, size: SpotSize):
        self.spot_id, self.size = spot_id, size
        self.vehicle: Vehicle | None = None
        self._lock = threading.Lock()

    def try_claim(self, vehicle: Vehicle) -> bool:
        with self._lock:                     # atomic check-then-set per spot
            if self.vehicle is None:
                self.vehicle = vehicle
                return True
            return False

A per-spot lock (rather than one lock for the whole lot) keeps two cars claiming different spots from blocking each other — only genuine contention for the same spot serializes.

Q3. "Add contractors, who don't get benefits, without touching Employee/Manager." (Open/Closed)

class Contractor(Employee):
    def role(self) -> str:
        return "Contractor"

    def total_team_cost(self) -> float:
        return self.salary * 1.0   # e.g., no benefits multiplier applied here vs full-time

Because every consumer of Employee only depends on its abstract interface, adding Contractor requires zero changes to find_employee, print_org_chart, or any existing subclass — the definition of "open for extension, closed for modification."

Q4. "How would you unit test the vending machine's states in isolation?"

def test_cannot_select_item_while_idle():
    machine = VendingMachine()
    with pytest.raises(ValueError):
        machine.select_item("soda")   # IdleState.select_item raises by design

def test_insert_coin_transitions_to_has_money():
    machine = VendingMachine()
    machine.insert_coin(100)
    assert isinstance(machine.state, HasMoneyState)

Because each state is its own class with its own methods, you can assert on type(machine.state) directly instead of reverse-engineering a status string — a concrete benefit of the State pattern for testability.

General interview instinct Whenever a follow-up asks "what if X could have multiple Y" or "what if this needs to run concurrently," check whether your current data structure assumed a tree (one parent), a single owner, or single-threaded access — those three assumptions are where nearly every LLD follow-up question aims.
