4. Custom Metrics Autoscaler (KEDA)

KEDA (Kubernetes Event-Driven Autoscaler) is available as the Custom Metrics Autoscaler Operator in OpenShift from version 4.12+. It is a CNCF incubating project co-founded by Red Hat. KEDA extends HPA by providing access to 70+ external metric sources and enabling scale-to-zero.

How KEDA Works
+------------------+    +-----------------+    +--------+    +------------+
| External Metrics |    | KEDA Operator   |    |  HPA   |    | Deployment |
| Sources:         |--->| (ScaledObject)  |--->|        |--->| replicas   |
|                  |    |                 |    |        |    |            |
| - Prometheus     |    | Fetches metrics |    | Scales |    | 0..N pods  |
| - Kafka          |    | Feeds to HPA as |    | pods   |    |            |
| - RabbitMQ       |    | external metrics|    |        |    |            |
| - Cron           |    |                 |    |        |    |            |
| - HTTP/RPS       |    | Manages scale   |    |        |    |            |
| - 70+ triggers   |    | to/from zero    |    |        |    |            |
+------------------+    +-----------------+    +--------+    +------------+

4.1 Popular Trigger Sources

TriggerMetricExample Use Case
PrometheusAny PromQL query: request rate, error rate, latency, custom business metrics.Scale on HTTP requests/second from FastAPI /metrics endpoint.
KafkaConsumer group lag (messages in topic minus consumed).Scale consumers when message backlog grows.
RabbitMQQueue depth (number of messages in queue).Scale workers when queue fills up.
CronSchedule-based (time of day, day of week).Pre-scale before known traffic peaks (e.g., 9 AM rush).
CPU / MemoryPod resource utilisation (like HPA but with scale-to-zero).Same as HPA but allows scaling to 0 replicas.
AWS SQS / Azure SBCloud message queue depth.Serverless-style processing of cloud queue messages.

4.2 Example: Scale on Prometheus HTTP Requests

This example scales a FastAPI deployment based on total HTTP requests per second, as reported by Prometheus:

# Step 1: TriggerAuthentication for Prometheus/Thanos
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
name: keda-trigger-auth-prometheus
spec:
secretTargetRef:
- parameter: bearerToken
name: thanos-token
key: token
- parameter: ca
name: thanos-token
key: ca.crt
---
# Step 2: ScaledObject
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
name: my-api-scaler
spec:
scaleTargetRef:
name: my-api                    # Deployment name
minReplicaCount: 1                # Min pods (0 = scale to zero)
maxReplicaCount: 20               # Max pods
pollingInterval: 15               # Check metrics every 15s
cooldownPeriod: 300               # Wait 5 min before scaling to min
triggers:
- type: prometheus
metadata:
serverAddress: https://thanos-querier.openshift-monitoring.svc.cluster.local:9092
metricName: http_requests_per_second
query: |
sum(rate(http_requests_total{namespace="my-ns",service="my-api"}[2m]))
threshold: "50"             # Scale up when RPS > 50 per pod
authModes: "bearer"
authenticationRef:
name: keda-trigger-auth-prometheus

This means: if the average HTTP requests per second per pod exceeds 50, KEDA tells HPA to add more pods. When traffic drops, pods are removed. If minReplicaCount is set to 0, the deployment can scale to zero pods during idle periods.

4.3 Example: Kafka Consumer Lag

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
name: kafka-consumer-scaler
spec:
scaleTargetRef:
name: kafka-consumer
minReplicaCount: 0
maxReplicaCount: 30
triggers:
- type: kafka
metadata:
bootstrapServers: kafka-cluster-kafka-bootstrap:9092
consumerGroup: my-consumer-group
topic: orders
lagThreshold: "100"          # Scale when lag > 100 messages
