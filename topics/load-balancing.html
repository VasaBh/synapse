SECTION 01

API & Traffic Load Balancing Fundamentals

Load balancing distributes incoming traffic across multiple backend instances to maximise availability, throughput, and fault tolerance. Understanding the algorithms and layers is essential before tackling Kubernetes-specific implementations.

Core Algorithms

Round Robin

Requests distributed sequentially to each server in turn. Simple and stateless — best for homogeneous backends with similar response times.

Weighted Round Robin

Each server assigned a weight proportional to its capacity. A 4-core server can receive 2× the requests of a 2-core server.

Least Connections

New request routed to the server with fewest active connections. Excellent for long-lived connections (WebSocket, gRPC streams).

Least Response Time

Combines fewest connections with fastest historical response time. Used by Envoy/Istio outlier detection.

IP Hash / Consistent Hash

Client IP (or header) hashed to a fixed backend. Provides session affinity without sticky-session cookies.

Random with Two Choices

Pick 2 random backends, send to the less loaded one. Approaches optimal with O(1) overhead — used in modern service meshes.

Health Checks

Load balancers remove unhealthy backends via active probes (periodic HTTP GET to /health) and passive detection (tracking 5xx responses). In Kubernetes, readiness probes feed the endpoint slice; a pod not ready is removed from all service endpoints immediately.

Interview Key Point Distinguish between liveness (should this pod be killed?) and readiness (should traffic flow here?). A pod can be live but not ready — it stays alive but receives zero traffic until it passes the readiness probe.

Session Persistence (Sticky Sessions)

Required when application state lives in-process rather than in an external store. Implemented via:

  • Cookie-based: LB inserts a SERVERID cookie; subsequent requests route to same backend
  • IP-hash: same client IP always maps to same backend (breaks behind NAT/CGNAT)
  • Header-based: route on a custom header (e.g., X-Session-ID)
Caution Sticky sessions undermine horizontal scaling — a popular session concentrates load on one pod. Prefer externalising state to Redis or a database so any pod can serve any request.

Connection Draining (Graceful Removal)

When a pod is removed (scale-down, deployment rollout), the LB stops sending new connections but allows existing connections to complete — typically with a 30–60 second drain window. In OpenShift this is handled by the terminationGracePeriodSeconds field on the pod plus the router's connection drain setting.

SECTION 02

Load Balancing Inside OpenShift

OpenShift provides multiple layers of traffic distribution within the cluster, each serving a distinct purpose from pod-to-pod communication to external ingress.

kube-proxy / iptables / IPVS

At the lowest level, Kubernetes Services are implemented by kube-proxy which programs either iptables rules (random probabilistic selection) or IPVS virtual servers (true LB with multiple algorithms). IPVS is preferred at scale because iptables rule evaluation is O(n) while IPVS is O(1).

  Client Pod
      │
      ▼  (ClusterIP: 10.96.x.x)
  kube-proxy / IPVS
      │
      ├──▶ Pod A (10.244.1.5:8080)
      ├──▶ Pod B (10.244.2.7:8080)
      └──▶ Pod C (10.244.3.2:8080)

OpenShift HAProxy Router

The OpenShift Router is an HAProxy instance running in the openshift-ingress namespace. It watches Route resources and dynamically updates its configuration. By default it uses round-robin but supports:

  • leastconn — via haproxy.router.openshift.io/balance: leastconn annotation
  • random — via haproxy.router.openshift.io/balance: random
  • source — IP-based stickiness
  • cookie — session cookie stickiness via haproxy.router.openshift.io/disable_cookies: "false"
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: my-api
  annotations:
    haproxy.router.openshift.io/balance: leastconn
    haproxy.router.openshift.io/timeout: 60s
    haproxy.router.openshift.io/rate-limit-connections: "true"
spec:
  host: my-api.apps.cluster.example.com
  to:
    kind: Service
    name: my-api-svc
    weight: 100
  port:
    targetPort: 8080
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect

Route Weights — Traffic Splitting

A Route can reference multiple backends with weights, enabling A/B testing and canary rollouts natively:

spec:
  to:
    kind: Service
    name: my-api-v1
    weight: 90           # 90% to stable
  alternateBackends:
  - kind: Service
    name: my-api-v2
    weight: 10           # 10% to canary

Ingress Operator

The IngressController custom resource (managed by the Ingress Operator) configures the router deployment. You can run multiple router instances with different routeSelector labels to segregate traffic between teams or environments:

apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: internal
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  routeSelector:
    matchLabels:
      router: internal
  endpointPublishingStrategy:
    type: LoadBalancerService

Service Mesh (OpenShift Service Mesh / Istio)

For fine-grained L7 control, OpenShift Service Mesh (based on Istio) uses Envoy sidecar proxies to implement:

VirtualService

Header-based routing, percentage splits, retries, timeouts, fault injection.

DestinationRule

Load balancing algorithm, connection pool, outlier detection, mTLS policy per subset.

PeerAuthentication

mTLS between services — encrypts east-west traffic without application changes.

Gateway

Istio ingress gateway replaces HAProxy router for mesh-managed services.

apiVersion: networking.istio.io/v1alpha1
kind: DestinationRule
metadata:
  name: my-api
spec:
  host: my-api
  trafficPolicy:
    loadBalancer:
      simple: LEAST_CONN
    outlierDetection:
      consecutiveErrors: 5
      interval: 10s
      baseEjectionTime: 30s   # eject unhealthy pod for 30s
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
SECTION 03

Load Balancing Outside OpenShift (External)

Traffic reaching OpenShift from the internet or corporate network passes through one or more external load balancing layers before hitting the cluster's ingress. Understanding this chain is critical for diagnosing latency, SSL offload, and failover behaviour.

Hardware Load Balancers

F5 BIG-IP

Enterprise-grade appliance/virtual. Full L4–L7 control, iRules scripting, SSL offload, WAF, APM. Common in financial services. Integrates with OpenShift via the F5 BIG-IP Controller Operator.

Citrix ADC (NetScaler)

Similar capability to F5. Integrates via the Citrix Ingress Controller. Provides content switching, responder policies, and AppExpert scripting.

Fortinet FortiADC

Security-focused ADC with integrated DDoS protection and WAF. Used where security and compliance are primary drivers.

Global Server Load Balancing (GSLB)

GSLB operates at the DNS layer to route users to the closest or healthiest data centre. A DNS query for api.example.com is answered with the IP of the best available site based on health, latency, or geography.

  Client DNS query: api.example.com
          │
    ┌─────▼──────┐
    │  GSLB DNS  │  (F5 GTM / Route 53 / NS1)
    └─────┬──────┘
          │  Health probes to both sites
    ┌─────┴──────────────┐
    ▼                    ▼
  Site A (Primary)    Site B (DR/COB)
  10.0.0.1            10.0.0.2
  OpenShift Cluster 1  OpenShift Cluster 2

MetalLB — Bare-Metal Load Balancer

On bare-metal or on-premise OpenShift clusters without a cloud provider, MetalLB implements the LoadBalancer service type by advertising IPs via:

  • Layer 2 mode: ARP/NDP announcement — one node owns the IP, others are standby. Simple but single-node throughput limited.
  • BGP mode: Peered with routers; every node advertises the IP — true ECMP load balancing at the network layer.
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: production-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.10.100-192.168.10.120
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: l2-advert
  namespace: metallb-system
SECTION 04

How to Use External Load Balancers with OpenShift

Integrating corporate or cloud load balancers with OpenShift requires mapping external network constructs to Kubernetes Service and Route objects. There are three primary integration patterns.

Pattern 1 — External LB → OpenShift Router (HAProxy)

The most common enterprise pattern. The external LB (F5, Nginx) terminates client connections and forwards to the OpenShift Router's NodePort or LoadBalancer IP. The router then handles TLS re-encryption or passthrough and routes to the correct Service.

  Internet
      │
  F5 BIG-IP  (L7 — SSL offload, WAF, rate limiting)
      │
  OpenShift Router  (HAProxy — Route matching, LB across pods)
      │
  Service (ClusterIP)
      │
  Pod replicas

F5 BIG-IP Controller Operator

The F5 operator watches OpenShift Route and ConfigMap resources and automatically programs the BIG-IP virtual servers. This removes manual F5 configuration when services are created or scaled:

# ConfigMap tells F5 controller which BIG-IP partition to manage
apiVersion: v1
kind: ConfigMap
metadata:
  name: f5-bigip-ctlr-config
  namespace: kube-system
data:
  config: |
    {
      "bigip-partition": "openshift",
      "openshift-sdn-name": "/Common/openshift_vxlan",
      "pool-member-type": "cluster",
      "balance": "least-connections-member"
    }

Pattern 2 — External LB → NodePort Direct

The external LB forwards directly to a NodePort service, bypassing the OpenShift Router entirely. Useful for non-HTTP protocols (gRPC, database, MQTT) or when HAProxy's overhead is undesirable.

  • Each worker node exposes the NodePort (30000–32767 range) on its external IP
  • External LB health-checks each node and distributes TCP traffic
  • kube-proxy/IPVS then routes within the cluster
  • No URL-based routing — one NodePort per service

Pattern 3 — External LB → MetalLB LoadBalancer Service

MetalLB assigns a stable external IP to each Service of type LoadBalancer. The external LB points to these IPs. Best for bare-metal clusters needing per-service IP addresses.

SSL Termination Options
  • Edge: TLS terminated at the OpenShift Router; backend traffic is plain HTTP
  • Passthrough: TLS passed through unmodified to the pod (pod holds the cert)
  • Re-encrypt: TLS terminated at router, new TLS connection to backend pod
  • At external LB: External LB terminates TLS; sends HTTP to OpenShift Router

Health Check Coordination

Both the external LB and OpenShift must agree on pod health. Configure the external LB to probe /healthz on the OpenShift Router's NodePort. The router is healthy only when at least one backend pod passes its readiness probe. This creates a single health signal propagated outward.

SECTION 05

Canary Deployments in OpenShift

A canary deployment routes a small percentage of production traffic to a new version of a service, allowing real-world validation before full rollout. OpenShift supports multiple mechanisms with varying granularity.

Mechanism 1 — Route Weights (Native OpenShift)

The simplest approach — split traffic between two Services using the alternateBackends field on a Route:

apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
spec:
  host: payment.apps.example.com
  to:
    kind: Service
    name: payment-v1
    weight: 95
  alternateBackends:
  - kind: Service
    name: payment-v2
    weight: 5
  port:
    targetPort: http
Progressive Delivery Start at 5% → monitor error rate and p99 latency → move to 20% → 50% → 100%. If metrics degrade, set canary weight back to 0 immediately. The switch is instantaneous — no redeployment needed.

Mechanism 2 — Argo Rollouts

Argo Rollouts provides a Rollout CRD that replaces Deployment for advanced strategies:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-api
spec:
  replicas: 10
  strategy:
    canary:
      canaryService: payment-canary
      stableService: payment-stable
      trafficRouting:
        istio:
          virtualService:
            name: payment-vsvc
      steps:
      - setWeight: 5
      - pause: {duration: 5m}
      - analysis:
          templates:
          - templateName: error-rate
      - setWeight: 20
      - pause: {duration: 10m}
      - setWeight: 50
      - pause: {duration: 10m}

Mechanism 3 — Istio VirtualService

For header-based canary (e.g., internal users see new version, external see stable):

apiVersion: networking.istio.io/v1alpha1
kind: VirtualService
metadata:
  name: payment-api
spec:
  http:
  - match:
    - headers:
        x-canary:
          exact: "true"
    route:
    - destination:
        host: payment-api
        subset: v2
  - route:
    - destination:
        host: payment-api
        subset: v1
      weight: 95
    - destination:
        host: payment-api
        subset: v2
      weight: 5

Canary Metrics to Monitor

Error Rate

HTTP 5xx % for canary vs stable. Alert if canary error rate exceeds stable + 1%.

p99 Latency

99th percentile response time. Canary must not exceed stable + 50ms threshold.

CPU / Memory

New version may have a memory leak invisible in unit tests. Monitor over 30-minute soak window.

Business KPIs

Conversion rate, transaction success rate. Ultimate canary gate — technical metrics can lie.

Rollback Strategy

  • Route weights: set canary weight to 0 — instant traffic cutover
  • Argo Rollouts: kubectl argo rollouts abort payment-api — reverts to stable within seconds
  • Istio: revert VirtualService weight via GitOps (ArgoCD re-syncs in <30s)
  • Always keep the previous stable Deployment running until canary is fully promoted
SECTION 06

Load Balancing Between Production and COB/DR Environments

Continuity of Business (COB) and Disaster Recovery (DR) environments require load balancing that operates above the cluster level, directing traffic between geographically separated sites based on health and policy.

COB vs DR Distinction

COB (Continuity of Business)

Active-active or active-warm-standby. Both sites handle production traffic simultaneously. Used for planned maintenance windows — traffic is shifted before taking a site offline. RTO near-zero.

DR (Disaster Recovery)

Active-passive. DR site is cold or warm standby. Activated only on primary site failure. RTO typically 15–60 minutes for warm standby. Data replication lag is the primary risk.

GSLB Failover Patterns

PatternDNS TTLFailover TimeComplexity
Active-Active (equal weights)30sN/A (continuous)High — data sync required
Active-Passive (health check)30sTTL + probe interval ≈ 60sMedium
Active-Warm (ratio 90/10)30sRatio shift ≈ 30sMedium
Manual failover300sManual + TTL propagationLow

F5 GTM / BIG-IP DNS Configuration

# Simplified F5 GTM pool configuration concept
Wide IP: api.example.com
  Pool: primary-site
    Member: 10.10.1.100  (OpenShift Cluster A router VIP)
    Monitor: HTTP /healthz every 5s, 2 failures = down
    Priority: 10
  Pool: dr-site
    Member: 10.20.1.100  (OpenShift Cluster B router VIP)
    Monitor: HTTP /healthz every 5s
    Priority: 20  (lower priority = standby)
  Load Balancing Method: Global Availability (primary first)

Data Replication Considerations

The Split-Brain Problem In active-active setups, writes may occur at both sites simultaneously. You need a consensus mechanism (Galera, CockroachDB, Cassandra multi-region) or a primary-per-shard strategy to prevent conflicting writes. Load balancing alone cannot solve data consistency.
  • Database: PostgreSQL streaming replication (async lag risk) or synchronous (latency penalty)
  • Object storage: MinIO site replication or AWS S3 CRR
  • Cache (Redis): Redis Enterprise active-active (CRDT-based) for conflict-free replication
  • Kafka: MirrorMaker 2 for cross-datacenter topic replication

Traffic Shifting for Maintenance

## Pre-maintenance runbook — shift traffic from Site A to Site B
# 1. Reduce Site A weight to 10% (monitor error rates)
kubectl patch route production-api -p '{"spec":{"to":{"weight":10}}}'

# 2. Wait for in-flight requests to drain (check active connections)
watch -n5 "oc rsh -n openshift-ingress router-pod haproxy -c /var/lib/haproxy/conf/haproxy.config -vd"

# 3. Update GSLB to remove Site A
#    (F5 GTM UI or iControl REST API call)

# 4. Perform maintenance
# 5. Reverse steps to restore Site A

Observability Across the Stack

F5 Analytics

Virtual server throughput, connection rate, SSL transaction rate. Export to Splunk/Datadog via logging profiles.

HAProxy Stats

Built-in stats socket exposes req/s, error rates, queue depth per backend. Scraped by Prometheus via haproxy-exporter.

Istio Telemetry

Request duration histogram, upstream retries, circuit breaker state — all in Prometheus format. Visualised in Kiali.

Distributed Tracing

Jaeger/Zipkin traces span all layers when correlation headers (B3 / W3C traceparent) are propagated end-to-end.

Red Flags to Avoid

Common Mistakes
  • Setting external LB timeout shorter than the application's p99 — causes spurious 504s
  • Using sticky sessions with stateless microservices — creates hot spots, defeats auto-scaling
  • Running Istio service mesh without operators who can maintain it — complexity debt
  • Low DNS TTL (1s) for GSLB without understanding client DNS behaviour — may not reduce failover time if clients cache aggressively
  • Canary without automated analysis — human reaction time too slow for rapid error spikes

Interview Cheat Sheet

HAProxy balance leastconn

Use for long-lived connections (WebSocket, streaming) where round-robin would overload slow pods.

Route alternateBackends

Fastest canary mechanism in OpenShift — purely declarative, no mesh required.

Headless Service

DNS returns all pod IPs. Client does LB. Required for gRPC over HTTP/2 (h2c multiplexing defeats server-side LB).

GSLB TTL

Keep at 30s for active failover scenarios. Lower TTL amplifies DNS query load; higher slows failover.

Connection draining

Set terminationGracePeriodSeconds ≥ HAProxy timeout to prevent 503s during pod shutdown.

Outlier detection

Istio's passive health check — ejects pods returning consecutive errors for baseEjectionTime before retrying.
